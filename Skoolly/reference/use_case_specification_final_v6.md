# เอกสารข้อกำหนด Use Case (Use Case Specification) — v6 (ฉบับปรับตาม Wireframe)
## ระบบ AI แนะนำโรงเรียนนานาชาติสำหรับผู้ปกครองในประเทศไทย

**หมายเหตุเรื่องเลขเวอร์ชัน:** เดิมเอกสารนี้ใช้เลข "(v2)" ตาม Wireframe/Scope revision (ดู bullet ด้านล่าง) ซึ่งเป็น
คนละชุดเลขกับ System Architecture doc — ตั้งแต่รอบนี้จึงปรับหัวเอกสารมาใช้เลขเดียวกันคือ **v6** (ปรับให้สอดคล้องกับสถาปัตยกรรม
Microservices แบบ Schema-per-Service ตามแบบฟอร์ม คง.101, เพิ่ม DevOps & QA Plan ตอบข้อ 7.5-7.6
ของฟอร์ม, และเพิ่ม 3 ฟีเจอร์ใหม่: Guided Prompts, source_published_at, ลิงก์แชร์ผลเปรียบเทียบ) —
เอกสารนี้ถูกแก้ไขให้สอดคล้องกับ System Architecture v6 ล่าสุดแล้วทุกจุด และใช้เลขเวอร์ชันตรงกันแล้ว


> **การอ่านบันทึกการแก้ไขด้านล่าง:** รายการของ v6 ถึง v6.3 เขียนขึ้นตอนที่ยังใช้เลข ID แบบแยกกลุ่ม (UC-G / UC-U / UC-A)
> จึงยังอ้างเลขชุดเดิมตามสภาพ ณ เวลานั้น — ตั้งแต่ **v6.4 เป็นต้นไปเอกสารใช้เลข UC-01 ถึง UC-19 แบบเรียงเดียว**
> เทียบเลขเดิมกับเลขใหม่ได้ที่ **ตาราง mapping หัวข้อ 2.4**
**เอกสารฉบับนี้ปรับให้ตรงกับรายการความสามารถของแต่ละ Actor ตามภาพที่ให้มา บวกการปรับ scope รอบล่าสุด:**
- **Guest ไม่มีสิทธิ์ใช้ AI Chatbot อีกต่อไป** — ต้องสมัครสมาชิกก่อนเสมอ
- **เครื่องคำนวณค่าใช้จ่าย (เดิม UC-G03) ตัดออกจาก Guest เช่นกัน** — ต้องล็อกอินเป็นสมาชิกเท่านั้นถึงจะใช้ได้
- **ตัด "รับคำแนะนำโรงเรียนแบบ Personalized จาก AI" ออกเป็น Use Case แยก** — รวมความสามารถนี้เข้ากับ AI Chatbot แทน เพราะเป็นความสามารถเดียวกันในมุมมองผู้ใช้ (ขอคำแนะนำผ่านการแชทได้โดยตรง)
- **ตัด "ตั้งค่าการแจ้งเตือน/บันทึกเงื่อนไขค้นหา" ออก** — ยังไม่ทำในเฟสนี้
- **รวม "จัดการบัญชี" เข้ากับ "จัดการโปรไฟล์บุตรหลาน" เป็น Use Case เดียว** เพราะเป็นหน้าตั้งค่าส่วนตัวเหมือนกัน
- **Admin ตัด "จัดการสิทธิ์ผู้ใช้งาน/Role" ออก** — ระบบมีบทบาท Admin แบบเดียว
- **UC-A02 ระบุแหล่งข้อมูลชัดเจน:** ดึงรายชื่อจาก **OPEC** และหา URL เว็บไซต์ทางการด้วย **Serper API**
- ทุก Use Case เขียนเป็นแบบเต็มรูปแบบ (Main Flow / Exception Flow / Postcondition / Business Rule)
- **(v6) UC-U05 เพิ่ม Guided Prompts/Quick Replies** — ปุ่มคำถามนำทางตอนเริ่มแชท + คำถามต่อยอดท้ายทุกคำตอบ
- **(v6) เพิ่ม `source_published_at`** เป็นมิติเวลาที่ 2 (จากทั้งหมด 3 มิติ) ในหัวข้อ 7.3 แทรกระหว่าง system fetch timestamp กับ effective period เดิม
- **(v6) UC-U08 ขยายจาก "Export PDF" เป็น "Export/แชร์"** เพิ่มฟีเจอร์สร้างลิงก์แชร์ผลเปรียบเทียบ พร้อม Use Case ใหม่ **UC-G07** สำหรับ Guest ที่เปิดลิงก์

**(v6.3) ปรับหัวข้อ 7 ให้ตรงกับ schema ที่ implement จริงใน `db/schema.sql` แบบคอลัมน์ต่อคอลัมน์** —
รอบก่อนหน้าหัวข้อ 7 เขียนไว้ตั้งแต่ตอนยังไม่มีฐานข้อมูลจริง พอลงมือออกแบบ DDL จากข้อมูล OPEC/scraper
ของจริงแล้วพบว่าต้องมีตารางและคอลัมน์เพิ่มอีกหลายตัว (normalize หลักสูตร/ระดับชั้น, ค่าเทอมแบบ
`numeric`, read model ของหน้าค้นหา ฯลฯ) จึงเติมให้ครบเป็น **Data Dictionary เต็ม 28 ตาราง** และ

**(v6.4) รวบ/ลดรูป Use Case จาก 29 เหลือ 20 หลังไล่ตรวจ Main Flow ของทุก Use Case เทียบกันทีละตัว**
(ไม่ใช่การไล่จากตารางสรุปอย่างเดียว) — เกณฑ์ที่ใช้คือ **"Main Flow skeleton เดียวกัน และความต่างอธิบายได้
ด้วย Alternate Flow หรือ Business Rule เท่านั้น"** ถ้าต้องเขียน Main Flow ใหม่ทั้งชุดแปลว่าคนละ Use Case
รอบนี้จึงเปลี่ยนเลข ID จาก UC-G/U/A แบบแยกกลุ่ม มาเป็น **UC-01 ถึง UC-19 แบบเรียงเดียว** เพราะหลัง
รวบแล้วมี Use Case ที่ครอบคลุมทั้ง Guest และ Parent ในตัวเดียว (UC-03, UC-05, UC-10) ทำให้ prefix
แบบเดิมสื่อผิด — ตาราง mapping ย้อนกลับอยู่ในหัวข้อ 2.4 และอ้างอิงจากไฟล์อื่นในโปรเจกต์ถูกแก้ตามครบแล้ว
สิ่งที่เปลี่ยน 9 จุด:
- **รวบ Use Case ที่ Main Flow ซ้อนกันจริง 8 จุด:** G01+G03(มุมมองแผนที่หน้าค้นหา)→UC-01, G02+G04+G03(แท็บแผนที่)→UC-02,
  G05+U03→UC-03, G08+U09→UC-05, U01+U02→UC-06, U08+G07→UC-10, A06+A12→UC-16, A10+A08→UC-18
- **ลดรูป UC-A07 (RAG re-embed) จาก Use Case เป็น «include»** — เป็นจุดที่ผิดหลัก Use Case มาตั้งแต่ต้น

  ไม่มี Actor มนุษย์ทำอะไรเลย ส่วนข้อ 4 ที่ Admin ตรวจงานล้มเหลวก็ทำผ่าน Use Case อื่น (UC-18/UC-19)

  **ข้อกำหนดไม่ได้ถูกตัดทิ้ง** ยังบังคับใช้เหมือนเดิมทุกข้อ แค่ไม่นับเป็น Use Case เพราะไม่มี Actor เป็นเจ้าของ
- **ตรวจแล้วยืนยันว่า "ไม่ควรรวบ" 4 คู่** ที่ดูเผิน ๆ เหมือนรวบได้ พร้อมเหตุผลในหัวข้อ 2.6 — โดยเฉพาะ
  **A04+A11 ที่รวบไม่ได้** เพราะ UC-A11 E2 เดิมเขียนไว้ชัดว่าให้ "สั่ง UC-A03 แล้วรอผลผ่าน UC-A04"
  แปลว่า A11 เป็นงาน**ต้นน้ำ**ที่ส่งงานต่อให้ A04 ไม่ใช่คิวเดียวกัน

**(v6.5) ปรับตามการเปลี่ยนแนวทาง 3 เรื่องของทีมพัฒนา — เหลือ 19 Use Case**

  และ content filter ไว้ครบ เพิ่ม E11 (ชุดปุ่มโหลดไม่ขึ้น) และ E12 (กดหัวข้อที่ไม่มีข้อมูลรองรับ)

  Google ตอนแสดงผลพร้อม attribution, UC-16 เหลือขอบเขตเฉพาะฟอรัม, ตาราง 7.6 เปลี่ยนจาก `reviews`
  (เนื้อหาของผู้ใช้ ใน schema `community`) เป็น **`school_google_reviews`** ที่เป็น cache ชั่วคราว ใน schema `school_data` และเพิ่ม `schools.google_place_id`
  ในตาราง 7.1 — ฟอรัมยังคงไว้เหมือนเดิมทุกอย่าง และกลายเป็นเนื้อหาจากผู้ใช้ชนิดเดียวที่ระบบเป็นเจ้าของ
- **ลิงก์แชร์ผลเปรียบเทียบ** มีอยู่แล้วตั้งแต่ v6 และถูกรวบเข้ากับการ Export เป็น UC-10 ใน v6.4
  รอบนี้จึงไม่มีการเปลี่ยนแปลงเพิ่ม บันทึกไว้เพื่อยืนยันว่าข้อกำหนดนี้ครอบคลุมแล้ว
- **เลข ID เลื่อนหนึ่งตำแหน่งตั้งแต่ UC-10 เดิมเป็นต้นไป** เพราะ UC-09 เดิม (เขียนรีวิว) ถูกตัดออก
  ดูตารางเลื่อนเลขในหัวข้อ 2.5

**(v6.6) แก้สถานะของ RAG ให้ตรงกับความเป็นจริง — ระบบ "ไม่มี RAG ทำงานอยู่"**

และ v6.5 ที่เปลี่ยนมาใช้ Guided Prompts ยิ่งทำให้ทุกคำถาม map เข้า query ที่นิยามไว้ล่วงหน้า
- **ถอด «include» ออกจาก UC-11 และ UC-14** พร้อมขั้นตอน re-embed ใน Main Flow, Postcondition
  และ Exception E2 เรื่อง `re-embed-handler` ล้มเหลว — การ publish จบที่อัปเดต
  `current_published_version_id` และเขียน `audit_log` เท่านั้น
- **หัวข้อ 3.4 เปลี่ยนจาก "พฤติกรรมระบบอัตโนมัติ" เป็น "ส่วนขยายที่ออกแบบไว้แล้วแต่ยังไม่เปิดใช้"**
  โดย**เก็บการออกแบบไว้ครบทุกข้อ** (ตาราง `ai.school_embeddings` หัวข้อ 7.19, extension `pgvector`
  และ flow ทั้งหมด) พร้อมระบุ **เงื่อนไขที่ต้องเกิดก่อนถึงจะเปิดใช้** คือ Phase 3 ต้องขยายไปเก็บ
  เนื้อหาข้อความอิสระของโรงเรียน — ถ้าเปิดใช้เมื่อไหร่ เพิ่ม «include» กลับเข้าไปได้เลยโดยไม่ต้องรื้ออะไร
- ตารางและ extension ที่รองรับ **ไม่ได้ถูกตัดทิ้ง** เพราะการออกแบบเผื่อไว้ล่วงหน้าเป็นสิ่งที่ถูกต้อง
  สิ่งที่ผิดคือการเขียนว่ามันทำงานอยู่ทั้งที่ยังไม่ทำงาน

## 1. Actor ทั้งหมดในระบบ

| Actor | ประเภท | คำอธิบาย |
|---|---|---|
| **Guest** | Primary (Human) | ผู้เยี่ยมชมที่ยังไม่ได้ล็อกอิน เข้าถึงข้อมูลสาธารณะและเครื่องมือพื้นฐานได้ รวมถึง**อ่าน**กระทู้ในฟอรัม (UC-05) และเปิดลิงก์เปรียบเทียบที่ถูกแชร์มา (UC-10) **ยกเว้น AI Chatbot, เครื่องคำนวณค่าใช้จ่าย และการเขียน/กดถูกใจ/รายงานในฟอรัม ซึ่งต้องล็อกอินเสมอ** |
| **Parent / User** | Primary (Human) | ผู้ปกครองที่สมัครสมาชิกแล้ว มีโปรไฟล์บุตรหลาน ใช้ฟีเจอร์ AI แบบเต็มรูปแบบ |
| **Admin** | Primary (Human) | ผู้ดูแลระบบ มีสิทธิ์สูงสุดและรับผิดชอบความถูกต้องของข้อมูล**ทุกโรงเรียน**แต่เพียงผู้เดียว ระบบมีบทบาท Admin แบบเดียว ไม่แบ่งระดับสิทธิ์ย่อย |
| **AI/LLM Recommendation Engine** | Supporting (System) | ระบบภายในที่ถูกเรียกใช้โดย Parent/User เท่านั้น (Guest เข้าถึงไม่ได้) ครอบคลุมทั้งการตอบคำถามและการแนะนำโรงเรียนแบบจัดอันดับ — implement เป็น **AI Service** (schema `ai` + Edge Function `chatbot-api`/`re-embed-handler`) ในสถาปัตยกรรม v6 |
| **Scraper/Crawler Service** | Supporting (System) | ระบบเก็บข้อมูลอัตโนมัติจากเว็บไซต์/เพจโรงเรียน เป็นกลไกหลักที่ทำให้ข้อมูลเป็นปัจจุบันโดยไม่ต้องมีใครติดต่อเข้ามา — เป็นส่วนหนึ่งของ **School Data Service** (schema `school_data`) ไม่ใช่ Service แยกต่างหาก เพราะเป็นเจ้าของข้อมูลชุดเดียวกัน |
| **Google Places API** | Supporting (External System) | แหล่งรีวิวและคะแนนของโรงเรียนตั้งแต่ v6.5 — ระบบเรียกตอนแสดงผลหน้ารายละเอียด (UC-02 แท็บรีวิว) แล้ว cache ไว้ชั่วคราวในตาราง `school_google_reviews` (7.6) **ระบบไม่เป็นเจ้าของเนื้อหารีวิว** จึงแก้ไข คัดกรอง หรือลบไม่ได้ และต้องแสดง attribution กลับไปยัง Google เสมอ — คนละตัวกับ Google Maps API ที่ใช้เติมพิกัดตอน Enrichment ใน UC-12 |
| **Notification Service** | Supporting (System) | ส่งอีเมลเป็นผลลัพธ์ข้างเคียงของ Use Case อื่น (เช่น ยืนยันอีเมล, สถานะ Ticket, PDF พร้อมดาวน์โหลด) — เฟสนี้ implement ผ่าน Resend เฉพาะช่องทางอีเมลเท่านั้น ยังไม่มี push notification จริง (เผื่อ scope ในอนาคต) — เป็นส่วนหนึ่งของ **Ops Service** |

**ความสัมพันธ์ระหว่าง Actor:** Parent/User เป็น generalization ของ Guest — ทำทุกอย่างที่ Guest ทำได้ **บวก** ความสามารถที่ต้องล็อกอิน (UC-06 ถึง UC-10) ส่วน **AI Chatbot (UC-08) และเครื่องคำนวณค่าใช้จ่าย (UC-07) ไม่เคยเป็นสิทธิ์ของ Guest มาก่อน** จึงไม่ใช่การ "ไม่สืบทอด" แต่เป็นสิทธิ์ที่มีเฉพาะหลังสมัครสมาชิกเท่านั้น

**Use Case ที่ Actor สองกลุ่มใช้ร่วมกัน:** UC-03 (เปรียบเทียบ), UC-05 (ฟอรัม) และ UC-10 (ลิงก์แชร์) เป็น Use Case เดียวที่ทั้ง Guest และ Parent/User เข้าถึงได้ โดยความต่างของสิทธิ์เขียนไว้เป็น **Business Rule ภายใน Use Case นั้น** ไม่ได้แยกเป็น Use Case คนละตัว (ดูเหตุผลการรวบในหัวข้อ 2.4)

ส่วน Admin คือผู้รับผิดชอบข้อมูลทั้งหมด โดยมี Scraper Service เป็นผู้ช่วยอัตโนมัติที่ทำงานภายใต้การกำกับของ Admin เสมอ

## 3. รายละเอียด Use Case แบบเต็มรูปแบบ

> โครงสร้าง: Actor / คำอธิบาย / Precondition / Main Flow / **Exception Flow** / Postcondition / Business Rule
> **กติกาการตั้งชื่อบล็อก:** `Main Flow` คือเส้นทางหลักที่เกิดขึ้นเสมอ ส่วน `Alternate Flow` คือเส้นทางทางเลือกที่เกิดเฉพาะบางเงื่อนไข (เช่น ผู้ใช้ล็อกอินแล้ว หรือเลือกใช้ช่องทางอื่น) — ทั้งสองบล็อกใช้เลขขั้นตอน**ชุดเดียวกันเรียงต่อเนื่อง** เพื่อให้อ้างอิงข้ามได้แบบไม่กำกวม เช่น "UC-10 ข้อ 7" ชี้ไปที่ขั้นตอนเดียวเสมอ
> **การนับเลขของ Use Case ที่เกิดจากการรวบ:** เลข Exception Flow เรียงต่อกันจาก Use Case เดิมตัวแรกไปยังตัวถัดไป เพื่อให้การอ้างอิงเดิมอย่าง "UC-G02 E5" ยังชี้ตำแหน่งเดิมได้ในชื่อใหม่ "UC-02 E5" (ตาราง mapping เต็มอยู่ในหัวข้อ 2.4)

## 3.1 กลุ่มสาธารณะ

### UC-01: ค้นหา/กรองรายชื่อโรงเรียน (รวมมุมมองแผนที่)

**Actor หลัก:** Guest, Parent/User
**คำอธิบาย:** ค้นหาโรงเรียนโดยกรองตามหลักสูตร (British/American/IB/Singapore ฯลฯ), ระดับชั้น, ช่วงค่าเทอม, พื้นที่/ระยะทาง, ภาษาที่สอน — ดูผลลัพธ์ได้ทั้งแบบรายการและแบบแผนที่จากชุดผลลัพธ์เดียวกัน
**Precondition:** ไม่มี

**Main Flow**
1. ผู้ใช้เข้าหน้า "ค้นหาโรงเรียน" ระบบแสดงรายชื่อเริ่มต้นเรียงตามความนิยม/ระยะทางโดยประมาณ พร้อม pagination
2. ผู้ใช้เลือกตัวกรองและ/หรือพิมพ์คำค้น
3. Frontend เรียก Auto-API ของ **School Data Service** ตรง (schema `school_data`, RLS ทำหน้าที่แทน API Gateway — client เรียก public API ของ service เองได้ ไม่ผิด Golden Rule ดู System Architecture หัวข้อ 4.2) ค้นด้วย Postgres full-text search บนตาราง `schools`/`school_versions` ตัวเดียวกับข้อมูลจริง ไม่มี Search Index แยกที่ต้อง sync
4. ระบบ query ตามเงื่อนไข พร้อม sort/pagination แล้วแสดงผลลัพธ์แบบย่อ (ชื่อ, รูปปก, ค่าเทอมเริ่มต้น, คะแนนรีวิวจาก Google, ระยะทาง)
**Alternate Flow (มุมมองแผนที่)**
5. ผู้ใช้สลับเป็น "มุมมองแผนที่" ได้จากผลลัพธ์ชุดเดียวกันโดยไม่ต้อง query ใหม่ ระบบวาดแผนที่ด้วย Leaflet + tile provider (Mapbox/OSM) จากพิกัดที่เก็บใน PostGIS ของเราเอง แสดงหมุดตำแหน่งพร้อมข้อมูลย่อ และระยะทางจากตำแหน่งผู้ใช้ (ถ้าอนุญาต location) — คนละตัวกับ Google Maps API ที่ใช้เติมพิกัดตอน Enrichment ใน UC-12 (ดู System Architecture หัวข้อ 2, 9)

**Exception Flow**
- **E1 — School Data Service (Supabase/Postgres) ตอบช้าหรือ timeout:** ฝั่ง Frontend ใช้ SWR/TanStack Query แบบ stale-while-revalidate เสิร์ฟผลลัพธ์จาก Cache ล่าสุดพร้อม badge "ผลลัพธ์อาจไม่เป็นปัจจุบัน" แทนการแสดง error 500 (Circuit Breaker ในระบบนี้ครอบคลุมทั้ง External API อย่าง Maps/Serper/LLM และการเรียกข้าม Service ภายใน เช่น Chatbot → School Data Service — ดู System Architecture หัวข้อ 4.5)
- **E2 — ไม่พบผลลัพธ์:** แสดงข้อความแจ้งพร้อมข้อเสนอแนะให้ลดเงื่อนไข หรือแสดงโรงเรียนใกล้เคียงเงื่อนไขที่สุด
- **E3 — พารามิเตอร์ไม่ถูกต้อง:** validate ทั้ง Frontend และ Backend ก่อนยิง query จริง
- **E4 — (ไม่เกิดขึ้นในสถาปัตยกรรมนี้) ไม่มี Search Index แยกให้ไม่ sync:** full-text search อ่านจากตารางเดียวกับข้อมูลโรงเรียนโดยตรง (ดู System Architecture หัวข้อ 4) ความเสี่ยงที่เหลืออยู่จริงมีแค่ Client เห็น Cache เก่าจาก SWR ก่อน revalidate ซึ่งครอบคลุมแล้วใน E1
- **E5 — แผนที่/tile provider ไม่ตอบสนอง/timeout:** fallback กลับเป็นมุมมองรายการ (list view) แสดงที่อยู่เป็นข้อความแทน
- **E6 — ผู้ใช้ไม่อนุญาต location permission:** แสดงแผนที่โดยไม่คำนวณระยะทาง แทนการฟ้อง error
- **E7 — พิกัดโรงเรียนไม่ถูกต้อง/ไม่มี** (Scraper หาที่อยู่ไม่เจอ): ไม่แสดงหมุดสำหรับโรงเรียนนั้น แต่ยังแสดงในมุมมองรายการได้ปกติ
- **E8 — tile provider ของแผนที่มี quota จำกัด:** ตั้ง rate limit ต่อ session (debounce ตอน pan/zoom)

**Extension Point:** ปุ่ม "บันทึกเป็นโรงเรียนโปรด" บนการ์ดผลลัพธ์แต่ละใบ — เฉพาะผู้ใช้ที่ล็อกอินแล้ว ทำงานตาม UC-06
**Postcondition:** ผู้ใช้เห็นรายชื่อโรงเรียนตรงเงื่อนไข ในมุมมองรายการหรือแผนที่ก็ได้ — ไม่มีการเปลี่ยนแปลงข้อมูลในระบบ (read-only)
**Business Rule:** แสดงเฉพาะโรงเรียนที่เผยแพร่แล้วเท่านั้น — ในระดับ Database คือ `schools.status = active` **และ** `schools.current_published_version_id IS NOT NULL` (โรงเรียนที่เพิ่ง import จาก Phase 1 จะเป็น `active` แต่ยังไม่มีเวอร์ชัน published จึงยังไม่ขึ้นแสดง ดูหัวข้อ 5 และ System Architecture หัวข้อ 3) — และต้องมี fallback แบบ list view เสมอ ห้ามให้ทั้งหน้าใช้งานไม่ได้เพราะแผนที่โหลดไม่ขึ้น

### UC-02: ดูรายละเอียดโรงเรียน (รวมแท็บแผนที่และรีวิวจาก Google)

**Actor หลัก:** Guest, Parent/User
**คำอธิบาย:** แสดงข้อมูลเต็มของโรงเรียน 1 แห่ง แบ่งเป็นแท็บ: ภาพรวม, หลักสูตร, สิ่งอำนวยความสะดวก, **ความปลอดภัย** (มาตรการ รปภ./CCTV/ห้องพยาบาล/ระบบกรอง PM2.5/การควบคุมบุคคลภายนอก และนโยบายคุ้มครองเด็ก — สกัดโดย Scraper ตาม UC-13 เก็บในตาราง 7.10), **รีวิว** (ดึงจาก Google Places API ตั้งแต่ v6.5 — ระบบไม่รับรีวิวที่ผู้ใช้เขียนเองอีกต่อไป) และ **แผนที่** (เดิมคือ UC-G03) — ส่วนแท็บ "คำนวณค่าใช้จ่าย" จะแสดงให้เห็นว่ามีอยู่ แต่ต้องล็อกอินก่อนถึงจะใช้งานได้จริง (ดู UC-07)
**Precondition:** ไม่มี — แต่โรงเรียนที่เปิดดูต้องมีเวอร์ชัน published อยู่ (`schools.current_published_version_id` ไม่เป็น null) มิฉะนั้นเข้าเงื่อนไข E1

**Main Flow**
1. ผู้ใช้กดเข้าจากผลค้นหา หรือเข้าตรงผ่าน URL/slug
2. Frontend ยิง request ไปยัง Auto-API ของ **School Data Service** (schema `school_data`) ด้วย school_id
3. ระบบดึงข้อมูลของเวอร์ชันที่ `schools.current_published_version_id` ชี้อยู่ แล้ว render หน้ารายละเอียด (cache อยู่ฝั่ง Client ด้วย SWR — ระบบนี้ไม่มี Read Replica แยก ทุก read ยิงที่ Postgres instance เดียวกัน ดู System Architecture หัวข้อ 4.6)
4. **(แท็บรีวิว)** เมื่อผู้ใช้กดแท็บ "รีวิว" ระบบเรียก **Google Places API** ด้วย `schools.google_place_id` ของโรงเรียนนั้น ณ เวลาที่แสดงผล แล้วแสดงคะแนนเฉลี่ย จำนวนรีวิวรวม และรีวิวล่าสุดที่ Google คืนมา พร้อม**ระบุที่มาว่า "รีวิวจาก Google" และลิงก์กลับไปยังหน้า Google ของโรงเรียนเสมอ** ตามข้อกำหนดการใช้งานของ Google — ผลลัพธ์ถูก cache ไว้ชั่วคราวในตาราง `school_google_reviews` (7.6) เพื่อลดจำนวนครั้งที่เรียก API
5. **(แท็บแผนที่)** เมื่อผู้ใช้กดแท็บ "แผนที่" ระบบวาดแผนที่ด้วย Leaflet + tile provider จากพิกัด PostGIS แสดงหมุดตำแหน่งของโรงเรียนนี้ และระยะทางจากตำแหน่งผู้ใช้ (ถ้าอนุญาต location) — กติกาและ Exception เดียวกับมุมมองแผนที่ใน UC-01

**Exception Flow**
- **E1 — school_id ไม่ถูกต้องหรือไม่เคยมีอยู่ในระบบ:** แสดงหน้า 404 ที่เป็นมิตร พร้อมแนะนำโรงเรียนใกล้เคียง
- **E1b — โรงเรียนมีสถานะ Archived (ปิดกิจการ/เลิกให้บริการ):** ไม่ขึ้น 404 แต่ยังแสดงหน้ารายละเอียดแบบอ่านอย่างเดียว พร้อม banner ชัดเจนว่า "โรงเรียนนี้ปิดกิจการแล้ว/ไม่พร้อมให้บริการ" เพื่อให้ลิงก์จาก UC-06 (รายการโปรด), UC-03 (เปรียบเทียบ) และแท็บรีวิวในหน้านี้ ยังเปิดดูได้โดยไม่กลายเป็น dead link
- **E2 — บางฟิลด์เป็นค่าว่าง** (Scraper ยังหาไม่เจอ): แสดง placeholder แบบ graceful degradation
- **E2b — ไม่พบข้อมูลความปลอดภัยของโรงเรียนนี้เลย** (`version_safety` ไม่มีแถว หรือทุกฟิลด์เป็น null): **ซ่อนแท็บ "ความปลอดภัย" ไปเลย** ห้ามแสดงเป็น "ไม่มี" หรือ "ไม่ผ่าน" เด็ดขาด เพราะ "ระบบหาไม่เจอ" กับ "โรงเรียนไม่มีมาตรการ" เป็นคนละเรื่องกัน และการสื่อผิดตรงนี้กระทบชื่อเสียงโรงเรียนโดยตรง
- **E3 — School Data Service (Supabase) ล่ม/ช้าผิดปกติ:** เสิร์ฟจาก cache (SWR) พร้อม timestamp อัปเดตล่าสุด หากไม่มี cache แสดงหน้า maintenance พร้อมปุ่ม retry
- **E4 — Admin แก้ไขข้อมูลระหว่างที่ผู้ใช้กำลังดูอยู่ (race condition):** ไม่ error ผู้ใช้เห็นข้อมูลชุดที่โหลดไว้จนกว่าจะ refresh เอง
- **E5 — Guest กดแท็บ "คำนวณค่าใช้จ่าย":** แสดง prompt ให้สมัครสมาชิก/ล็อกอินก่อน แทนการซ่อนแท็บไปเลย (โชว์ว่ามีฟีเจอร์นี้อยู่เพื่อจูงใจให้สมัครสมาชิก)
- **E6 — โรงเรียนยังไม่มี `google_place_id` หรือจับคู่กับสถานที่บน Google ไม่ได้:** **ซ่อนแท็บรีวิวไปเลย** ห้ามแสดงเป็น "0 รีวิว" หรือ "คะแนน 0" เพราะสื่อผิดว่าโรงเรียนถูกรีวิวแย่ ทั้งที่ความจริงคือระบบจับคู่ข้อมูลไม่ได้ (หลักการเดียวกับ E2b)
- **E7 — Google คืนผลว่าโรงเรียนนี้ยังไม่มีรีวิว:** แสดง "ยังไม่มีรีวิวบน Google สำหรับโรงเรียนนี้" **ไม่ชวนให้ผู้ใช้เขียนรีวิว** เพราะระบบไม่รับรีวิวจากผู้ใช้เองแล้ว — ถ้าต้องการชวนให้มีส่วนร่วม ให้ลิงก์ไปที่ฟอรัม (UC-05) แทน
- **E8 — Google Places API ช้า/ล่ม/เกินโควตารายวัน:** เสิร์ฟจาก cache ล่าสุดในตาราง `school_google_reviews` (7.6) พร้อม timestamp กำกับว่า "ข้อมูลรีวิว ณ [วันที่]" ถ้าไม่มี cache ให้ซ่อนเฉพาะแท็บรีวิวพร้อมข้อความ "โหลดรีวิวไม่สำเร็จ ลองใหม่อีกครั้ง" **ไม่กระทบแท็บอื่นของหน้ารายละเอียด** เพราะแท็บอื่นดึงจาก School Data Service คนละแหล่งกัน — โควตารายวันของ Google เป็นต้นทุนที่ต้องเฝ้าระวังใน UC-19 เช่นเดียวกับ Serper/LLM
- **E9 — แผนที่/tile provider ไม่ตอบสนอง/timeout:** ซ่อนแท็บแผนที่หรือแสดงที่อยู่เป็นข้อความแทน ไม่ทำให้ทั้งหน้าแสดงผลผิดพลาด
- **E10 — ผู้ใช้ไม่อนุญาต location permission:** แสดงหมุดโรงเรียนโดยไม่คำนวณระยะทาง
- **E11 — พิกัดโรงเรียนไม่ถูกต้อง/ไม่มี:** ซ่อนแท็บแผนที่ไปเลย แสดงเฉพาะที่อยู่เป็นข้อความในแท็บภาพรวม

**Extension Point:** ปุ่ม "บันทึกเป็นโรงเรียนโปรด" (UC-06), ปุ่ม "แจ้งข้อมูลผิดพลาด" (UC-09), ปุ่ม "เพิ่มเข้าเปรียบเทียบ" (UC-03) — ทุกปุ่มเป็นทางเข้าไปยัง Use Case อื่น ไม่ใช่ส่วนหนึ่งของ Main Flow นี้
**Postcondition:** ผู้ใช้เห็นข้อมูลเต็มของโรงเรียนที่เลือก พร้อมวันที่กำกับครบตามหัวข้อ 7.3 และเห็นรีวิวจาก Google พร้อมแหล่งที่มากำกับ — ไม่มีการเปลี่ยนแปลงข้อมูลใด ๆ ในระบบ นอกจากการอัปเดต cache รีวิวตามตาราง 7.6
**Business Rule:** (1) ทุกหน้าต้องแยกวันที่ตามมิติเวลาในหัวข้อ 7.3 เสมอ ห้ามรวมเป็นประโยคเดียว: "ข้อมูลเปลี่ยนแปลงล่าสุดเมื่อ [วันที่]" (จาก school_versions ปัจจุบัน), "ระบบตรวจสอบล่าสุดเมื่อ [วันที่]" (จาก schools.last_verified_at ซึ่งอาจใหม่กว่าถ้าตรวจแล้วไม่พบการเปลี่ยนแปลง) และเฉพาะฟิลด์กลุ่มค่าใช้จ่ายที่มี `source_published_at` ไม่เป็น null ให้แสดง "ต้นฉบับอัปเดตล่าสุดเมื่อ [วันที่]" เพิ่มอีกบรรทัด (ซ่อนไปเลยถ้าเป็น null) — รวมสูงสุด 3 บรรทัดตามหัวข้อ 7.3 (2) **แท็บรีวิวเป็นข้อมูลจากภายนอกล้วน** ระบบไม่แก้ไข ไม่คัดกรอง และไม่ลบรีวิวใด ๆ ของ Google — ต้องแสดง attribution "รีวิวจาก Google" พร้อมลิงก์กลับต้นทางเสมอ และห้ามเก็บ cache ไว้นานเกินระยะเวลาที่ข้อกำหนดการใช้งานของ Google อนุญาต (ดูตาราง 7.6) (3) เนื่องจากระบบไม่เป็นเจ้าของเนื้อหารีวิว **ผู้ใช้ที่ไม่เห็นด้วยกับรีวิวต้องไปโต้แย้งที่ Google เอง** ระบบไม่มีช่องทางอุทธรณ์รีวิวเหมือนที่ฟอรัมมี (UC-16 E3)

### UC-03: เปรียบเทียบโรงเรียน

**Actor หลัก:** Guest, Parent/User
**คำอธิบาย:** เลือกโรงเรียนมาเทียบข้อมูลเคียงข้างกัน — **Guest ใช้ได้แบบจำกัดและไม่บันทึกผล ส่วนสมาชิกใช้ได้ไม่จำกัด เทียบฟิลด์ละเอียดกว่า และบันทึกชุดไว้ดูย้อนหลัง/แชร์ต่อได้** (เดิมแยกเป็น UC-G05 กับ UC-U03 รวบเป็นตัวเดียวเพราะเป็น Main Flow เดียวกัน ต่างกันที่โควตาและสิทธิ์บันทึกซึ่งเป็น Business Rule)
**Precondition:** ไม่มีสำหรับการเปรียบเทียบ — ขั้น "บันทึกชุด" (ข้อ 4) ต้องล็อกอินก่อน

**Main Flow**
1. ผู้ใช้เลือกโรงเรียนจากผลค้นหา (UC-01) หรือหน้ารายละเอียด (UC-02) กด "เพิ่มเข้าเปรียบเทียบ" — สมาชิกเลือกจากรายการโปรด (UC-06) ได้อีกทางหนึ่ง
2. ระบบเก็บรายการที่เลือกไว้ — Guest เก็บชั่วคราวใน session/local state (ไม่บันทึกลง DB) ส่วนสมาชิกผูกรายการกับบัญชีของตนเอง
3. ผู้ใช้กด "เปรียบเทียบ" ระบบแสดงตารางเทียบเคียงข้างกัน โดยชุดฟิลด์ที่แสดงขึ้นกับสิทธิ์: **Guest** เห็นฟิลด์หลัก (ค่าเทอม, หลักสูตร, ระยะทาง, คะแนนรีวิวจาก Google) ส่วน **สมาชิก** เห็นเพิ่มอีกชั้นคือ Hidden Cost breakdown เต็มรูปแบบ, สิ่งอำนวยความสะดวก และ**มาตรการความปลอดภัย** แสดงเป็นเครื่องหมาย ✓/— ต่อรายการตามตาราง 7.10

**Alternate Flow (เฉพาะสมาชิกที่ล็อกอินแล้ว)**
4. สมาชิกบันทึกชุดเปรียบเทียบนี้ไว้ดูภายหลังได้ (ตั้งชื่อชุด) — ชุดที่บันทึกแล้วนำไป Export เป็น PDF หรือสร้างลิงก์แชร์ต่อได้ทันทีผ่าน UC-10

**Exception Flow**
- **E1 — Guest เลือกเกินจำนวนที่กำหนด:** ปุ่ม "เพิ่ม" ถูก disable พร้อมข้อความแจ้ง limit
- **E2 — Guest เกิน rate limit การเปรียบเทียบต่อ session:** แจ้งให้ล็อกอินเพื่อใช้งานแบบไม่จำกัดและบันทึกชุดได้ตามข้อ 4
- **E3 — โรงเรียนที่เลือกไว้ถูกลบ/archive ระหว่างเปรียบเทียบ:** ตัดออกจากตารางพร้อมแจ้งเตือน ไม่ทำให้ตารางทั้งชุดแสดงผลผิดพลาด
- **E4 — โรงเรียนในชุดเปรียบเทียบที่บันทึกไว้ถูก Archive ภายหลัง:** แสดง badge แจ้ง ไม่ลบออกจากชุดเงียบ ๆ
- **E5 — ข้อมูลบางฟิลด์ไม่ครบในบางโรงเรียน:** แสดง "ไม่ระบุ" ในช่องนั้น ไม่ทำให้แถวทั้งแถวหายไป
- **E6 — จำนวนโรงเรียนที่เทียบมากจนแสดงผลยาก:** แนะนำให้แบ่งเป็นหลายชุดแทนการเลื่อนตารางแนวนอนเป็นระยะยาว

**Postcondition:** ตารางเปรียบเทียบแสดงผล — ถ้าเป็น Guest ตารางหายเมื่อปิดหน้า/session หมดอายุ ถ้าเป็นสมาชิกที่กดบันทึก จะมีแถวใหม่ใน `user_data.comparison_sets` (มี `comparison_id`) ที่พร้อมใช้กับ UC-10 ต่อได้ทันที
**Business Rule:** **Guest:** เลือกได้สูงสุด N โรงเรียนต่อครั้ง และมี rate limit ต่อ session (ค่า N และ rate limit เก็บเป็น config ของระบบ ไม่ hard-code ไว้ในโค้ด เพื่อปรับได้โดยไม่ต้อง deploy ใหม่) และข้อมูลไม่ถูกบันทึกถาวร — **สมาชิก:** ไม่จำกัดจำนวนครั้ง บันทึกและดูย้อนหลังได้ นี่คือความต่างเดียวระหว่างสองกรณี ไม่มีความต่างในขั้นตอนการทำงาน

### UC-04: สมัครสมาชิก / เข้าสู่ระบบ

**Actor หลัก:** Guest
**คำอธิบาย:** สร้างบัญชีใหม่หรือเข้าสู่ระบบด้วยบัญชีที่มีอยู่ เพื่อปลดล็อกความสามารถของ Parent/User (UC-06 ถึง UC-10) — เป็น Use Case เดียวที่ทำหน้าที่เป็นประตูจาก Guest ไปเป็นสมาชิก
**Precondition:** ไม่มี

**Main Flow**
1. ผู้ใช้กด "สมัครสมาชิก" กรอกอีเมล+รหัสผ่าน หรือเลือก Social Login
2. ระบบส่งอีเมลยืนยัน ผู้ใช้กดลิงก์ยืนยันเพื่อเปิดใช้งานบัญชี
3. เข้าสู่ระบบด้วยอีเมล/รหัสผ่าน หรือ Social Login ที่ยืนยันแล้ว

**Exception Flow**
- **E1 — อีเมลซ้ำกับบัญชีที่มีอยู่แล้ว:** แจ้งให้ไปหน้า Login หรือ "ลืมรหัสผ่าน" แทนการสร้างซ้ำ
- **E2 — ลิงก์ยืนยันอีเมลหมดอายุ:** ขอส่งลิงก์ใหม่ได้ ไม่ต้องกรอกฟอร์มสมัครใหม่ทั้งหมด
- **E3 — กรอกรหัสผ่านผิดหลายครั้งติดกัน:** Rate limit ป้องกัน brute-force (lock ชั่วคราวหลังผิดครบจำนวนที่กำหนด)
- **E4 — Social Login provider ล่ม/timeout:** fallback ให้เลือกวิธีอื่น (อีเมล/รหัสผ่าน) แทน ไม่ค้างหน้าโหลด

**Postcondition:** มีบัญชีที่ยืนยันแล้ว และ session ล็อกอินที่ใช้งานฟีเจอร์ของ Parent/User ได้
**Business Rule:** ต้องยืนยันอีเมลก่อนใช้ฟีเจอร์ที่ต้องพึ่ง identity เช่น ตั้งกระทู้/แสดงความคิดเห็นในฟอรัม/บันทึกโปรไฟล์บุตรหลาน/ใช้ AI Chatbot/เครื่องคำนวณค่าใช้จ่าย

### UC-05: ใช้งานฟอรัมผู้ปกครอง

**Actor หลัก:** Guest (อ่านอย่างเดียว), Parent/User (อ่านและมีส่วนร่วม)
**คำอธิบาย:** พื้นที่พูดคุยแบบเปิดที่ต่างจากรีวิว (UC-02 แท็บรีวิว) ตรงที่รีวิวเป็นข้อมูล**จากภายนอก (Google)** ที่อ่านได้อย่างเดียว ผูกกับโรงเรียน 1 แห่งและมีคะแนนดาว ส่วนฟอรัมเป็นเนื้อหาที่ผู้ใช้เขียนเองในระบบ เป็นการสนทนาแบบมีคำถาม/คำตอบ ตั้งหัวข้อเองได้ และแท็กโรงเรียนหรือไม่แท็กก็ได้ — **ตั้งแต่ v6.5 ฟอรัมเป็นเนื้อหาจากผู้ใช้ชนิดเดียวที่ระบบเป็นเจ้าของ** — **Guest อ่านได้อย่างเดียว ส่วนการตั้งกระทู้/แสดงความคิดเห็น/กดถูกใจ/รายงานเนื้อหา ต้องล็อกอินและยืนยันอีเมลแล้วเท่านั้น** (เดิมแยกเป็น UC-G08 กับ UC-U09 รวบเป็นตัวเดียวเพราะเป็นหน้าจอและ Main Flow เดียวกัน ต่างกันที่สิทธิ์ซึ่งเป็น Business Rule)
**Precondition:** ไม่มีสำหรับการอ่าน — ต้องล็อกอินและยืนยันอีเมลแล้ว (ตาม Business Rule ของ UC-04) สำหรับ Main Flow ข้อ 4-8

**Main Flow (อ่าน — ทุกคน)**
1. ผู้ใช้เข้าหน้า "ฟอรัม" ระบบแสดงรายการกระทู้เรียงตามล่าสุด/ได้รับความสนใจมากที่สุด พร้อม pagination
2. กรองตามหมวดหมู่ (Review / Question / Update / Tips) หรือกรองเฉพาะกระทู้ที่แท็กโรงเรียนที่สนใจได้
3. กดเข้ากระทู้ เห็นเนื้อหาเต็ม + ความคิดเห็นทั้งหมดเรียงตามเวลา

**Alternate Flow (มีส่วนร่วม — เฉพาะสมาชิก)**
4. สมาชิกกด "ตั้งกระทู้" เลือกหมวดหมู่ (Review / Question / Update / Tips) กรอกหัวข้อ + เนื้อหา และแท็กโรงเรียนได้ 1 แห่ง (ไม่บังคับ)
5. ระบบผ่าน content filter อัตโนมัติ (คำหยาบ/สแปม/ข้อมูลส่วนบุคคลของผู้อื่น) แล้ว **เผยแพร่ทันที** ตามแนวทาง Post-Moderation ใน Business Rule ข้อ (2)
6. สมาชิกคนอื่นแสดงความคิดเห็นต่อท้ายกระทู้ หรือกดถูกใจได้
7. สมาชิกคนใดก็ได้กด "รายงาน" เนื้อหาที่ไม่เหมาะสม ระบุเหตุผล → เข้าคิวให้ Admin ตรวจผ่าน UC-16
8. เจ้าของกระทู้/ความคิดเห็นแก้ไขหรือลบของตัวเองได้ตลอด (ลบแล้วขึ้น "เนื้อหานี้ถูกลบโดยผู้เขียน" เพื่อไม่ให้บริบทของคนที่ตอบต่อหายไปทั้งเธรด)

**Exception Flow**
- **E1 — ยังไม่มีกระทู้ในหมวดที่เลือก:** แสดงข้อความชวนให้ล็อกอินเพื่อเป็นคนตั้งกระทู้แรก ไม่ใช่หน้าว่างเปล่า
- **E2 — กระทู้ถูกซ่อน/ลบโดย Admin ระหว่างที่ผู้ใช้เปิดค้างไว้:** กดเข้าไปแล้วขึ้น "เนื้อหานี้ถูกนำออกแล้ว" แทน error 404 หรือหน้าที่แสดงผลผิดพลาด
- **E3 — Guest กดปุ่ม "ตั้งกระทู้"/"แสดงความคิดเห็น"/"ถูกใจ"/"รายงาน":** แสดง prompt ให้ล็อกอินก่อน แทนการซ่อนปุ่ม (แนวเดียวกับ UC-02 E5)
- **E4 — Community Service ช้า/ล่ม:** เสิร์ฟจาก cache (SWR) พร้อม badge "อาจไม่เป็นปัจจุบัน" ไม่กระทบหน้าอื่นของเว็บ เพราะเป็นคนละ schema กับ School Data Service
- **E5 — content filter ตรวจพบคำต้องห้าม:** เตือนก่อน submit ให้แก้ไขเอง ถ้ายังยืนยันส่ง ให้ตั้งสถานะเป็น `pending` รอ Admin ตรวจก่อนเผยแพร่แทนการเผยแพร่ทันที
- **E6 — ผู้ใช้โพสต์ถี่ผิดปกติ (spam/bot):** rate limit ต่อบัญชีต่อวัน ทั้งกระทู้และความคิดเห็น
- **E7 — กระทู้ถูกลบระหว่างที่ผู้ใช้กำลังพิมพ์ความคิดเห็น:** แจ้ง "กระทู้นี้ถูกนำออกแล้ว" พร้อมคืนข้อความที่พิมพ์ไว้ให้ copy ไม่ทิ้งโดยไม่แจ้งผู้ใช้
- **E8 — รายงานเนื้อหาเดิมซ้ำ:** 1 บัญชีรายงานได้ 1 ครั้งต่อ 1 เนื้อหา (บังคับที่ระดับ DB) ครั้งถัดไปนับรวมเป็นจำนวนผู้รายงานแทนสร้าง ticket ใหม่ (แนวเดียวกับ UC-09 E1)
- **E9 — Community Service ล่มตอน submit:** Frontend เก็บ draft ที่ผู้ใช้พิมพ์ไว้ฝั่ง client แล้ว retry ให้อัตโนมัติเมื่อ service กลับมา ไม่ทิ้งเนื้อหาที่พิมพ์ไว้ (ไม่มีคิว retry ฝั่ง server เพราะ Community Service ไม่มี Edge Function ของตัวเอง ดู System Architecture หัวข้อ 4.1)
- **E10 — เนื้อหาอ้างข้อมูลค่าเทอมที่ผิด/ล้าสมัย:** ไม่ block การโพสต์ (เป็นความเห็นส่วนบุคคล) แต่ระบบขึ้นหมายเหตุใต้กระทู้ที่แท็กโรงเรียนว่า "ตัวเลขทางการดูได้ที่หน้าโรงเรียน" พร้อมลิงก์ไป UC-02 เพื่อไม่ให้ผู้อ่านเข้าใจผิดว่าเป็นข้อมูลที่ระบบรับรอง

**Postcondition:** ผู้ใช้เห็นเฉพาะกระทู้/ความคิดเห็นที่ยังไม่ถูกนำออก — สำหรับสมาชิก กระทู้/ความคิดเห็นถูกเผยแพร่ (หรืออยู่สถานะ `pending` ตาม E5) และรายการรายงานเข้าคิว UC-16 ถ้ามีการกดรายงาน
**Business Rule:** (1) แสดงเฉพาะเนื้อหาสถานะ `approved` เท่านั้น เนื้อหาที่ถูก Admin นำออก (`rejected`) ไม่แสดงต่อสาธารณะทุกกรณี และแสดงผู้เขียนเป็น display name เท่านั้น ไม่แสดงอีเมลหรือชื่อจริงต่อสาธารณะ (2) ฟอรัมใช้ **Post-Moderation** (เผยแพร่ก่อน ตรวจเมื่อถูกรายงานหรือเมื่อติด content filter) โดยตั้งใจ — เพราะบทสนทนาต้องการความทันทีถึงจะมีชีวิต ทีมมี Admin จำนวนน้อย และเนื้อหาในฟอรัม**ไม่กระทบตัวเลขใด ๆ ที่ระบบแสดงเป็นข้อมูลทางการ** (คะแนนรีวิวที่แสดงในผลค้นหามาจาก Google ไม่ได้มาจากฟอรัม) ความเสียหายถ้าปล่อยผ่านชั่วคราวจึงจำกัดอยู่ที่ตัวกระทู้นั้นเอง (3) เนื้อหาในฟอรัม**ไม่ถูกใช้เป็นแหล่งข้อมูลของ Chatbot (UC-08) หรือของฐานความรู้ AI (หัวข้อ 3.4) เด็ดขาด** เพราะไม่ผ่านการตรวจสอบแบบเดียวกับข้อมูลโรงเรียน

## 3.2 กลุ่ม Parent / User

### UC-06: จัดการโปรไฟล์ บัญชี ข้อมูลบุตรหลาน และรายการโปรด

**Actor หลัก:** Parent/User
**คำอธิบาย:** จัดการข้อมูลบัญชีของตนเอง (อีเมล/รหัสผ่าน), ข้อมูลบุตรหลาน (อายุ, ระดับชั้นที่สนใจ, งบประมาณ, หลักสูตรที่สนใจ, พื้นที่ที่สะดวก) และ**รายการโรงเรียนโปรด** รวมอยู่ในพื้นที่ "บัญชีของฉัน" เดียวกัน ข้อมูลบุตรหลานใช้เป็น input ให้ UC-07 (คำนวณค่าใช้จ่าย) และการแนะนำโรงเรียนในแชท (UC-08)
**Precondition:** ล็อกอินแล้ว (ผ่าน UC-04)

**Main Flow**
1. ผู้ใช้เข้าหน้า "บัญชีของฉัน" แบ่งเป็น 3 ส่วน: ข้อมูลบัญชี (อีเมล/รหัสผ่าน), โปรไฟล์บุตรหลาน (เพิ่มได้มากกว่า 1 คน) และรายการโรงเรียนโปรด
2. แก้ไขข้อมูลส่วนไหนก็ได้อิสระจากกัน ระบบ validate แล้วบันทึกทีละส่วน
3. **(รายการโปรด)** ผู้ใช้กดไอคอน "บันทึก" ได้จากหน้ารายละเอียด (UC-02) หรือผลค้นหา (UC-01) ระบบเพิ่มโรงเรียนเข้า `user_data.favorites` ของบัญชีนั้น แล้วแสดงรวมกันในส่วนรายการโปรดของหน้านี้ พร้อม pagination — กดซ้ำเป็นการเอาออก (toggle)
4. ผู้ใช้ขอลบบัญชีทั้งหมด (รวมข้อมูลบัญชี ข้อมูลบุตรหลาน และรายการโปรด) ได้จากหน้าเดียวกัน (สิทธิ์ตาม PDPA)

**Exception Flow**
- **E1 — ข้อมูลบุตรหลานไม่ครบ** (อย่างน้อยต้องมีงบประมาณ+ระดับชั้นสำหรับ AI แนะนำ): ไม่ block การบันทึก แต่แจ้งเตือนว่า UC-07/UC-08 จะทำงานได้ไม่เต็มที่จนกว่าจะกรอกเพิ่ม
- **E2 — กรอกข้อมูลบุตรหลานผิดรูปแบบ** (ค่าติดลบ, วันเกิดอนาคต): validate ก่อนบันทึก
- **E3 — มีบุตรหลานหลายคน:** รองรับหลายโปรไฟล์ต่อบัญชี เลือกใช้ตอนขอคำแนะนำ/คำนวณได้ว่าจะดูเผื่อคนไหน
- **E4 — เปลี่ยนอีเมลเป็นอีเมลที่มีบัญชีอื่นใช้อยู่แล้ว:** ปฏิเสธพร้อมแจ้งเหตุผล
- **E5 — ขอลบบัญชีขณะมีข้อมูลผูกอยู่** (กระทู้/ความคิดเห็นในฟอรัม ใน Community Service, ประวัติเปรียบเทียบ/โปรไฟล์บุตรหลาน/รายการโปรด ใน User Service, ประวัติสนทนา AI ใน AI Service): ใช้ **Soft Delete + Grace Period** (เช่น 30 วัน) ก่อนลบถาวรจริง ยกเลิกคำขอได้ระหว่างนี้ — เมื่อพ้น Grace Period `account-deletion-cron` (pg_cron) จะแก้ข้อมูลทั้ง 3 schema ในธุรกรรมเดียว: กระทู้/ความคิดเห็นที่เขียนไว้ถูกทำให้เป็น anonymous แทนการลบทิ้ง (เพื่อไม่ให้บริบทของเธรดที่คนอื่นตอบไว้ขาดหาย), favorites/comparison_sets/children_profiles ถูกลบถาวร, ส่วนประวัติสนทนา AI ลบถาวรไปพร้อมบัญชีเพราะเป็นข้อมูลส่วนตัวล้วนไม่มีประโยชน์ต่อผู้ใช้อื่น (รายละเอียดกลไกข้าม Service ดู System Architecture หัวข้อ 4.2)
- **E6 — ข้อมูลบางส่วนต้องเก็บตามกฎหมายแม้ผู้ใช้ขอลบ:** แยกเก็บส่วนที่กฎหมายบังคับออกจากข้อมูลส่วนตัวที่ลบได้ทันที
- **E7 — กดบันทึกโรงเรียนโปรดซ้ำโรงเรียนเดียวกัน:** Idempotent ไม่สร้างข้อมูลซ้ำ (toggle เป็นเอาออกแทน)
- **E8 — โรงเรียนที่บันทึกไว้ถูก Archive ภายหลัง:** ยังแสดงในรายการโปรดแต่มี badge "ไม่พร้อมให้บริการแล้ว" ไม่ลบออกโดยไม่แจ้งผู้ใช้
- **E9 — จำนวนโรงเรียนที่บันทึกมากเกินไป:** มี pagination ในส่วนรายการโปรด ไม่โหลดทั้งหมดพร้อมกัน

**Postcondition:** ข้อมูลบัญชี/บุตรหลานถูกบันทึก หรือบัญชีเข้าสู่กระบวนการลบ — และโรงเรียนอยู่ใน (หรือถูกเอาออกจาก) `user_data.favorites` ของบัญชีนั้น โดยสถานะปุ่มบันทึกใน UC-01/UC-02 ตรงกับความจริงเสมอ
**Business Rule:** ข้อมูลบุตรหลานเป็นข้อมูลอ่อนไหวตาม **PDPA** เข้าถึงได้เฉพาะเจ้าของบัญชี คำขอลบบัญชีต้องดำเนินการให้เสร็จภายในระยะเวลาที่ PDPA กำหนด นับจากวันที่ Grace Period สิ้นสุด — รายการโปรดผูกกับบัญชี ไม่ใช่ device

### UC-07: ใช้เครื่องคำนวณค่าใช้จ่าย (แบบส่วนตัว)

**Actor หลัก:** Parent/User
**คำอธิบาย:** คำนวณค่าใช้จ่ายรวมต่อปี/หลายปีแบบเจาะจงต่อครอบครัว โดยดึงจำนวน/ข้อมูลบุตรหลานจากโปรไฟล์ (UC-06) มาใช้อัตโนมัติ รวมส่วนลดพี่น้อง (ถ้าโรงเรียนมี)
**Precondition:** ต้องล็อกอินเป็น Parent/User เท่านั้น (Guest ไม่มีสิทธิ์เข้าถึงเมนูนี้เลย — ดู UC-02 Exception E5)

**Main Flow**
1. ผู้ใช้ (ล็อกอินแล้ว) เข้าแท็บ "คำนวณค่าใช้จ่าย" จากหน้ารายละเอียดโรงเรียน (UC-02) หรือจากหน้าเปรียบเทียบ (UC-03)
2. ระบบดึงโปรไฟล์บุตรหลานของบัญชีนั้นจาก `user_data.children_profiles` มาเติมเป็นค่าตั้งต้น (จำนวนบุตร, ระดับชั้น, จำนวนปีที่ต้องการคำนวณ) — ผู้ใช้แก้ค่าเองได้ทุกช่อง
3. ระบบดึงรายการค่าใช้จ่ายของโรงเรียนจากเวอร์ชัน published ปัจจุบัน (ค่าเทอม + hidden cost แต่ละรายการ พร้อม `academic_year`/`source_published_at` ที่กำกับมาในระดับฟิลด์ตามหัวข้อ 7.3)
4. คำนวณยอดรวมต่อปีและหลายปีด้วย decimal-safe arithmetic ฝั่ง Backend รวมส่วนลดพี่น้องถ้าโรงเรียนระบุไว้
5. แสดงผลแบบแยกรายรายการ พร้อมวันที่กำกับตามกติกา 3 บรรทัดในหัวข้อ 7.3 และ disclaimer ว่าเป็นตัวเลขประมาณการจากข้อมูลที่ระบบเก็บมา ไม่ใช่ใบเสนอราคาจากโรงเรียน
6. ผู้ใช้บันทึกผลลัพธ์ไว้ดูย้อนหลัง/เทียบกับโรงเรียนอื่นผ่านชุดเปรียบเทียบใน UC-03 ได้

**Exception Flow**
- **E1 — บางรายการค่าใช้จ่ายยังไม่มีข้อมูล:** แสดง "ไม่ระบุ" ไม่รวมยอดอัตโนมัติ พร้อม disclaimer
- **E2 — `academic_year` ของค่าเทอม (ดูหัวข้อ 7.3) เป็นปีการศึกษาเก่ากว่าปีปัจจุบัน:** แสดง badge "ค่าเทอมปีการศึกษา [academic_year]" แยกจาก "ตรวจสอบล่าสุดเมื่อ [system timestamp]" อย่างชัดเจน ไม่รวมเป็นข้อความเดียวกัน — และถ้าฟิลด์นั้นมี `source_published_at` ต้องแสดงบรรทัดที่ 3 "ต้นฉบับอัปเดตล่าสุดเมื่อ [source_published_at]" ด้วย พร้อม badge เตือนสีเหลืองถ้าต้นฉบับเก่ากว่า 1 ปี (กติกาเดียวกับ UC-02 ตามหัวข้อ 7.3)
- **E3 — Input ไม่ถูกต้อง** (จำนวนบุตรติดลบ/เกินขอบเขต): validate range ก่อนคำนวณ
- **E4 — ข้อผิดพลาดจากการปัดเศษ/คำนวณทางการเงิน:** ใช้ decimal-safe arithmetic ฝั่ง backend
- **E5 — โปรไฟล์บุตรหลานยังไม่ได้กรอก (UC-06):** ใช้ค่า default (1 คน ไม่มีส่วนลด) ในการคำนวณเบื้องต้นไปก่อน พร้อมชวนกรอกโปรไฟล์เพื่อผลลัพธ์แม่นยำขึ้น

**Postcondition:** ผู้ใช้เห็นยอดค่าใช้จ่ายประมาณการพร้อมวันที่กำกับครบทุกบรรทัดตามหัวข้อ 7.3 — การคำนวณไม่เขียนทับข้อมูลโรงเรียนใด ๆ เก็บได้แค่ผลลัพธ์ที่ผูกกับชุดเปรียบเทียบของผู้ใช้เอง
**Business Rule:** ต้องระบุแหล่งที่มาและวันที่อัปเดตของทุกตัวเลขเสมอ เพราะไม่มีโรงเรียนมายืนยันตัวเลขเอง ผลลัพธ์บันทึกไว้เทียบย้อนหลังได้ผ่าน UC-03

### UC-08: ขอคำแนะนำผ่าน AI Chatbot แบบคำถามนำทาง (Guided Prompts)

**Actor หลัก:** Parent/User | **Actor รอง:** AI/LLM Recommendation Engine
**คำอธิบาย:** ผู้ช่วย AI ที่ออกแบบให้ **"กดเลือกหัวข้อ" เป็นเส้นทางหลัก ไม่ใช่ห้องแชทแบบพิมพ์อิสระ** — ผู้ใช้เลือกคำถามนำทาง (Guided Prompts) ที่ระบบเตรียมไว้ แล้วเดินต่อด้วยชุดคำถามต่อยอด (Quick Replies) ที่แนบท้ายทุกคำตอบ ครอบคลุมทั้งการถามข้อมูลทั่วไปและ**การขอคำแนะนำโรงเรียนแบบจัดอันดับส่วนบุคคล**ในหน้าต่างเดียวกัน (เดิมแยกเป็น Use Case "รับคำแนะนำ" ต่างหาก ถูกรวมมาไว้ที่นี่ตั้งแต่ v6) โดยทุกคำตอบอ้างอิงเฉพาะข้อมูลที่มีอยู่จริงในฐานข้อมูลของระบบ — **ช่องพิมพ์คำถามเองยังมีอยู่เป็นทางเลือกรอง** สำหรับผู้ใช้ที่ต้องการถามนอกเหนือจากหัวข้อที่เตรียมไว้
**Precondition:** ล็อกอินแล้วเท่านั้น (Guest เข้าถึงไม่ได้)

**Main Flow (คำถามนำทาง — เส้นทางหลัก)**
1. ผู้ใช้เข้าหน้าแชท ระบบแสดง **Guided Prompts** เป็นปุ่มหัวข้อจัดกลุ่มตามเรื่องที่ผู้ปกครองถามบ่อย เช่น "แนะนำโรงเรียนให้หน่อย", "ค่าเทอมโดยประมาณเท่าไหร่", "มีค่าใช้จ่ายแฝงอะไรบ้าง", "เปรียบเทียบหลักสูตรอังกฤษ vs อเมริกัน", "โรงเรียนนี้มีมาตรการความปลอดภัยอะไรบ้าง" — ชุดปุ่มนี้แสดงตั้งแต่เปิดหน้าแชทและแสดงซ้ำได้ตลอดบทสนทนา ไม่ใช่แค่ครั้งแรกครั้งเดียว
2. ผู้ใช้กดเลือกหัวข้อ — **แต่ละปุ่มผูกกับ intent ที่นิยามไว้ล่วงหน้า** พร้อมชุด parameter ที่ intent นั้นต้องใช้ (เช่น งบประมาณ ระดับชั้น พื้นที่ โรงเรียนที่กำลังดูอยู่) ระบบจึงรู้ตั้งแต่ต้นว่าต้อง query อะไรจากฐานข้อมูล ไม่ต้องให้ LLM เดาเจตนาจากข้อความอิสระ ซึ่งเป็นเหตุผลหลักที่เลือกแนวทางนี้: **ลดพื้นที่ที่คำตอบจะคลาดเคลื่อนจากข้อมูลจริง และทำให้ต้นทุน/ความเร็วคาดเดาได้**
3. หากเป็นคำขอแนะนำโรงเรียน **AI Service** (`chatbot-api`) เรียก tool ที่ยิงไปหา `school-data-api` ของ **School Data Service** (`search_schools`, `get_school_details`, `compare_schools`) และ `user-data-api` ของ **User Service** (ดึงโปรไฟล์บุตรหลานจาก UC-06 มาเสริม context) — ทั้งสองเป็นการเรียกข้าม Service จริงผ่าน internal service secret + forward JWT ของผู้ใช้ (ดู System Architecture หัวข้อ 4.3-4.4) ใช้เงื่อนไข hard filter ตามงบประมาณ/พื้นที่/หลักสูตร ด้วย function calling แทน vector search เป็นหลัก เพราะคำถามส่วนใหญ่เป็น structured query (ตัวเลข/หมวดหมู่) และข้อมูลที่เก็บตอนนี้เป็น structured ล้วน ไม่มี free-text ให้ vector search จริง ๆ (ดู System Architecture หัวข้อ 8)
4. ประกอบ prompt โดย inject เฉพาะข้อมูลโรงเรียนที่ `school-data-api` คืนมาจริง + โปรไฟล์ผู้ใช้จาก `user-data-api` + ประวัติสนทนา ส่งเข้า LLM
5. หากเป็นคำแนะนำโรงเรียน ระบบตรวจสอบว่าโรงเรียนที่ถูกแนะนำมีอยู่จริง (grounding check) ก่อนแสดงผล
6. แสดงคำตอบพร้อมเหตุผล/แหล่งอ้างอิง **พร้อมชุดคำถามต่อยอด (Quick Replies) 2-3 ข้อที่เกี่ยวกับคำตอบล่าสุดแนบมาด้วยเสมอ — เป็นเส้นทางเดินต่อหลักของบทสนทนา** (เช่น หลังตอบเรื่องค่าเทอมแล้ว เสนอปุ่ม "แล้วค่าใช้จ่ายแฝงล่ะ" / "เทียบกับโรงเรียนนี้กับอีกที่ไหม") — LLM ต้องคืนค่าเป็น structured output แยก field `answer` กับ `suggested_replies` ชัดเจน ไม่ปนกันเป็น free text เดียว เพื่อให้ Frontend render เป็นปุ่มกดได้จริง
7. ผู้ใช้ให้ feedback ต่อคำตอบได้อย่างรวดเร็ว (ถูกใจ/ไม่ถูกใจ) ซึ่งเป็น signal ที่ UC-18 ใช้จัดลำดับความสำคัญตอนตรวจ Log

**Alternate Flow (พิมพ์คำถามเอง — ทางเลือกรอง)**
8. ผู้ใช้พิมพ์คำถามเองในช่องข้อความได้ตลอดเวลา ระบบพยายามจับคู่ข้อความนั้นเข้ากับ intent ที่รองรับอยู่ก่อนเป็นอันดับแรก — จับคู่ได้ให้เดินตามข้อ 3-7 เหมือนกับการกดปุ่ม จับคู่ไม่ได้ให้ไปตาม E1

**Exception Flow**
- **E1 — ข้อความที่ผู้ใช้พิมพ์เองจับคู่กับ intent ที่รองรับไม่ได้ หรืออยู่นอกขอบเขตระบบ:** ตอบอย่างสุภาพว่ายังไม่รองรับคำถามลักษณะนี้ **พร้อมเสนอ Guided Prompts ที่ใกล้เคียงที่สุด 2-3 ปุ่มให้กดแทน** ไม่ปล่อยให้ผู้ใช้ค้างอยู่กับช่องพิมพ์เปล่า และไม่พยายามตอบเดา
- **E2 — ประวัติสนทนายาวเกิน context window:** สรุปบทสนทนาเก่าอัตโนมัติ เก็บเฉพาะประเด็นสำคัญ
- **E3 — LLM timeout:** retry อัตโนมัติ 1 ครั้งก่อนแจ้ง error ให้ลองใหม่ หากเป็นคำขอแนะนำโรงเรียนและล้มเหลวซ้ำ → fallback เป็นระบบแนะนำแบบ rule-based (filter + scoring ไม่ใช้ LLM) พร้อมแจ้งผู้ใช้ว่าเป็นคำแนะนำแบบพื้นฐานชั่วคราว
- **E4 — Prompt Injection ผ่านข้อความแชท:** output filter ตรวจสอบก่อนส่งกลับ, system prompt แยกชั้นจาก user input ตลอดเวลา
- **E5 — เนื้อหาไม่เหมาะสม/สแปมจากผู้ใช้:** content moderation filter ก่อนส่งเข้า LLM และก่อนบันทึกลง log
- **E6 — LLM แนะนำโรงเรียนที่ไม่มีอยู่จริง (Hallucination):** กรองรายการที่ไม่ผ่าน grounding check ออกก่อนแสดงผลเสมอ log ไว้ให้ Admin ตรวจสอบผ่าน UC-18
- **E7 — โปรไฟล์ผู้ใช้ไม่ครบสำหรับการแนะนำ:** ระบบถามข้อมูลเพิ่มเติมกลับในแชทแบบสนทนา (เช่น "งบประมาณต่อปีประมาณเท่าไหร่คะ") แทนการ block การใช้งานทั้งหมด
- **E8 — Rate limit เกิน** (ป้องกันต้นทุน LLM API โดยเฉพาะตอนขอคำแนะนำที่ใช้ retrieval หนักกว่าการถามข้อมูลทั่วไป): แจ้ง "กรุณาลองใหม่ในอีก X นาที"
- **E9 — Indirect Prompt Injection ผ่านเนื้อหาที่ Scrape มาจากเว็บโรงเรียน** (ดูหัวข้อ 8.3): ข้อมูลที่ Retrieve มาต้องแยกชั้นจาก System Instruction เสมอเช่นเดียวกับ User Input ใน E4 ไม่เชื่อว่าเนื้อหาจากเว็บภายนอกปลอดภัยเสมอไป
- **E10 — LLM ไม่คืน Quick Replies กลับมา หรือคืนมาผิด format:** ไม่ block การแสดงคำตอบหลัก แค่ไม่แสดงปุ่มเสริมของรอบนั้น (Graceful Degradation) — ผู้ใช้ยังกดปุ่มจากชุด Guided Prompts หลัก หรือพิมพ์คำถามต่อเองได้ตามปกติ
- **E11 — ชุด Guided Prompts โหลดไม่ขึ้น:** แสดงชุดหัวข้อพื้นฐานที่ฝัง (hardcode) ไว้ฝั่ง Frontend แทน **ห้ามเหลือหน้าแชทที่มีแต่ช่องพิมพ์เปล่า** เพราะจะขัดกับแนวทางที่ให้การกดปุ่มเป็นเส้นทางหลัก และผู้ใช้กลุ่มเป้าหมายส่วนใหญ่ไม่รู้ว่าจะเริ่มถามอะไร
- **E12 — หัวข้อที่ผู้ใช้กดไม่มีข้อมูลรองรับในฐานข้อมูล** (เช่น กดถามมาตรการความปลอดภัยของโรงเรียนที่ยังไม่มีแถวในตาราง 7.10): ตอบตรงไปตรงมาว่ายังไม่มีข้อมูลส่วนนี้ของโรงเรียนนั้น **ห้ามให้ LLM แต่งคำตอบขึ้นเอง** และเสนอหัวข้ออื่นที่มีข้อมูลรองรับแทน — กรณีนี้ต่างจาก E6 (Hallucination) ตรงที่ระบบรู้ล่วงหน้าว่าไม่มีข้อมูล จึงต้องกันไว้ก่อนส่งเข้า LLM ไม่ใช่ไปกรองทีหลัง

**Postcondition:** ผู้ใช้ได้คำตอบที่ grounded บนข้อมูลจริง พร้อม Quick Replies (ถ้า LLM คืนมาถูก format) และบทสนทนาถูกบันทึกลง `ai.conversations`/`ai.messages` สำหรับ UC-18 โดยบันทึกด้วยว่าแต่ละข้อความมาจากการกดปุ่มหรือการพิมพ์เอง (`entry_mode` ในตาราง 7.18)
**Business Rule:** (1) ทุกคำตอบที่อ้างอิงข้อมูลจำเพาะของโรงเรียนต้องระบุแหล่งอ้างอิงและวันที่เก็บข้อมูลล่าสุด คำแนะนำโรงเรียนต้อง grounded บนข้อมูลจริงในระบบเท่านั้น ห้าม LLM สร้างตัวเลขค่าเทอม/หลักสูตรขึ้นเองโดยเด็ดขาด (2) **ทุกปุ่มใน Guided Prompts ต้องผูกกับ intent ที่มี query รองรับจริง** ห้ามมีปุ่มที่กดแล้วไม่มีข้อมูลตอบ — ปุ่มใดที่ข้อมูลยังไม่พร้อมให้ซ่อนออกจากชุด ไม่ใช่แสดงไว้แล้วตอบว่าไม่รู้ (3) ช่องพิมพ์คำถามเองเป็นทางเลือกรองเสมอ ห้ามออกแบบหน้าจอที่บังคับให้ผู้ใช้ต้องพิมพ์ก่อนถึงจะเห็นปุ่ม (4) สัดส่วนการใช้งาน "กดปุ่ม" เทียบกับ "พิมพ์เอง" เป็นตัวชี้วัดที่ต้องติดตามใน UC-18/UC-19 เพราะถ้าผู้ใช้ยังต้องพิมพ์เองเป็นส่วนใหญ่ แปลว่าชุดหัวข้อที่เตรียมไว้ยังไม่ครอบคลุม

### UC-09: แจ้งข้อมูลผิดพลาด/ไม่เป็นปัจจุบัน

**Actor หลัก:** Parent/User
**คำอธิบาย:** ช่องทางให้ผู้ใช้แจ้งว่าข้อมูลของโรงเรียนผิดหรือไม่เป็นปัจจุบัน โดยระบุฟิลด์ที่ผิด อธิบายเหตุผล และแนบหลักฐานได้ เพื่อส่งเข้ากระบวนการตรวจสอบของ Admin ใน UC-17
**Precondition:** ล็อกอินแล้ว และอยู่ในหน้ารายละเอียดของโรงเรียนที่ต้องการแจ้ง (UC-02)

**Main Flow**
1. ผู้ใช้กด "แจ้งข้อมูลผิดพลาด" ในหน้ารายละเอียดโรงเรียน (UC-02) เลือกฟิลด์ที่ผิด + อธิบาย + แนบหลักฐานได้
2. ระบบสร้าง Ticket ผูกกับโรงเรียนและฟิลด์นั้น ส่งเข้าคิว Admin ผ่าน UC-17

**Exception Flow**
- **E1 — มีคนแจ้งฟิลด์เดียวกันของโรงเรียนเดียวกันซ้ำ:** รวมเป็น ticket เดียว นับจำนวนครั้งที่แจ้งแทนสร้างซ้ำ ช่วย Admin จัดลำดับความสำคัญ
- **E2 — แนบไฟล์หลักฐานล้มเหลว:** ยังส่ง ticket ได้โดยไม่มีไฟล์แนบ ไม่ block การแจ้ง
- **E3 — ผู้ใช้แจ้งข้อมูลเดิมซ้ำหลายรอบโดยไม่มีเหตุผลใหม่:** จำกัดจำนวนครั้งต่อวันต่อบัญชี

**Postcondition:** Ticket เข้าคิว Admin ผู้แจ้งได้รับแจ้งเตือนเมื่อสถานะเปลี่ยน (Database Webhook บน `community.data_correction_reports.status` ยิงไปหา Ops Service `notification-sender` ตรง — ไม่ใช่ Community Service เรียกออกเองเพราะไม่มี Edge Function ของตัวเอง ดู System Architecture หัวข้อ 4.3.1)
**Business Rule:** การแจ้งไม่ทำให้ข้อมูลเปลี่ยนทันที ต้องผ่านการตรวจสอบของ Admin ก่อนเสมอ — Use Case นี้แยกจากการ "รายงานเนื้อหาไม่เหมาะสม" ใน UC-05 โดยตั้งใจ เพราะปลายทางเป็นคนละคิว คนละการตัดสิน และคนละตาราง (`data_correction_reports` กับ `forum_reports` — ดูหัวข้อ 2.6)

### UC-10: ส่งออก/แชร์ผลการเปรียบเทียบ และเปิดลิงก์ที่ถูกแชร์

**Actor หลัก:** Parent/User (ฝั่งสร้าง/แชร์), Guest (ฝั่งเปิดลิงก์ — ไม่ต้องมีบัญชี)
**คำอธิบาย:** จากหน้าเปรียบเทียบที่บันทึกไว้แล้ว (UC-03 ข้อ 4) ผู้ใช้เลือกได้ว่าจะ Export เป็น PDF (snapshot ตายตัว ณ ตอนสร้าง) หรือสร้างลิงก์แชร์ (ข้อมูลอัปเดตตามจริงเสมอ) หรือทำทั้งคู่ — และรวมถึง**ฝั่งของคนที่เปิดลิงก์นั้น** ซึ่งเดิมแยกเป็น UC-G07 (รวบเข้ามาเพราะเป็นสองด้านของสิ่งเดียวกันคือ `comparison_sets.share_token` ตัวเดียว ถ้าแยกเป็นคนละ Use Case กติกาเรื่อง token/การปิดแชร์จะกระจายอยู่สองที่)
**Precondition:** สำหรับฝั่งสร้าง — ต้องมีชุดเปรียบเทียบที่บันทึกแล้ว (มี `comparison_id`) จาก UC-03 ข้อ 4 | สำหรับฝั่งเปิดดู — ไม่มี

**Main Flow (Export PDF)**
1. ผู้ใช้อยู่ในหน้าเปรียบเทียบที่**บันทึกไว้แล้ว** (UC-03) กด "Export เป็น PDF" — ต้องเป็นชุดที่บันทึกแล้วเช่นเดียวกับลิงก์แชร์ เพราะ `pdf-export` (Ops Service) ดึงชุดเปรียบเทียบผ่าน `user-data-api` ด้วย `comparison_id` ไม่ได้รับ `school_ids` มาจากหน้าเว็บโดยตรง (ดู System Architecture หัวข้อ 6)
2. ระบบสร้างงาน generate PDF แบบ async
3. เมื่อเสร็จ แจ้งเตือนผู้ใช้พร้อมลิงก์ดาวน์โหลด

**Alternate Flow (สร้างลิงก์แชร์)**
4. ผู้ใช้อยู่ในหน้าเปรียบเทียบที่**บันทึกไว้แล้ว**เท่านั้น (ชุดที่ยังไม่บันทึกไม่มี `comparison_id` ให้ผูก token) กด "สร้างลิงก์แชร์"
5. ระบบสุ่ม `share_token` แบบคาดเดาไม่ได้ (ถ้ายังไม่เคยมี) ตั้ง `share_enabled = true` แสดงลิงก์ให้ copy/แชร์ต่อได้ทันที
6. ผู้ใช้ปิดแชร์ภายหลังได้ตลอดเวลาโดยไม่ต้องลบชุดเปรียบเทียบ (toggle `share_enabled`) — เปิดใหม่ได้โดยลิงก์เดิมใช้ได้เหมือนเดิม ไม่สุ่ม token ใหม่ทุกครั้งที่เปิด/ปิด

**Alternate Flow (เปิดลิงก์ที่ถูกแชร์)**
7. ผู้เปิดลิงก์ (Guest หรือสมาชิกก็ได้) เปิด URL ที่มี `share_token` ต่อท้าย — เป็นทางเข้าที่มาจากนอกระบบ (แชร์ต่อใน LINE/โซเชียลมีเดีย) ไม่ใช่จากการเรียกดูภายในเว็บ
8. Frontend เรียก `get-shared-comparison` (Edge Function ของ **User Service**) ด้วย token — ตรวจสอบว่า token ยังใช้งานได้ (`share_enabled = true` และชุดเปรียบเทียบยังไม่ถูกลบ)
9. `get-shared-comparison` เรียกข้ามไปยัง `school-data-api` ของ **School Data Service** เพื่อดึงรายละเอียด**ล่าสุด**ของโรงเรียนทุกแห่งใน `school_ids` (ไม่ใช่ snapshot ตอนแชร์ — ต่างจาก PDF Export โดยตั้งใจ เพราะลิงก์ควรมีประโยชน์ระยะยาว ให้ผู้รับเห็นข้อมูลล่าสุดเสมอแม้เปิดลิงก์ทีหลังผ่านไปหลายเดือน) ประกอบเป็น response เดียวส่งกลับ
10. แสดงตารางเปรียบเทียบแบบ read-only — ไม่มีปุ่มแก้ไข/บันทึกเพิ่ม เพราะผู้เปิดลิงก์ไม่ใช่เจ้าของ

**Exception Flow**
- **E1 — Generate PDF ใช้เวลานาน/ล้มเหลว:** ทำแบบ async เสมอ ไม่ให้หน้าค้าง retry อัตโนมัติ 1 ครั้งก่อนแจ้งว่าล้มเหลวจริง
- **E2 — ข้อมูลในชุดเปรียบเทียบเปลี่ยนระหว่างรอ generate PDF:** PDF ใช้ snapshot ข้อมูล ณ ตอนกดสร้าง ไม่ใช่ real-time ล่าสุด (ต่างจากลิงก์แชร์ที่ตั้งใจให้เป็น live เสมอ)
- **E3 — ไฟล์ PDF ใหญ่เกินขนาดที่ระบบอนุญาต:** บีบอัดหรือแจ้งให้ดาวน์โหลดผ่านลิงก์แทนการแนบไฟล์
- **E4 — พยายาม Export PDF หรือสร้างลิงก์แชร์จากชุดเปรียบเทียบที่ยังไม่บันทึก:** ปุ่มทั้งสองถูก disable พร้อมข้อความ "บันทึกชุดก่อนถึงจะ Export/แชร์ได้"
- **E5 — เจ้าของลบชุดเปรียบเทียบทั้งที่มีลิงก์แชร์เปิดอยู่:** ลิงก์เดิมใช้ไม่ได้ทันที (ดู E6)
- **E6 — Token ไม่ถูกต้อง/ไม่มีอยู่จริง/ถูกปิดแชร์ (`share_enabled = false`)/ชุดเปรียบเทียบถูกลบไปแล้ว:** แสดงหน้า "ลิงก์นี้ใช้ไม่ได้แล้ว" แบบเดียวกันทุกกรณี ไม่บอกรายละเอียดว่าเคยมีอยู่จริงหรือถูกปิดแชร์ (กัน enumeration — ไม่ leak ว่า token ที่ถูกเดาสุ่มขึ้นมานั้น "เคยมีอยู่จริง" หรือ "ไม่เคยมี") ไม่ error 500 ทุกกรณี
- **E7 — โรงเรียนบางแห่งในชุดถูก Archive หลังแชร์:** แสดง badge เหมือน UC-03 E4 ไม่ทำให้ตารางทั้งชุดแสดงผลผิดพลาด
- **E8 — คนเปิดลิงก์เยอะผิดปกติ** (เผยแพร่ในโซเชียลมีเดียแล้วมีคนเข้าเยอะ หรือถูกใช้ scrape ข้อมูลจำนวนมาก): เป็น public endpoint ไม่มี auth ต้องมี rate limit ต่อ IP ที่ `get-shared-comparison`
- **E9 — School Data Service (`school-data-api`) ตอบช้า/ล่มตอนดึงรายละเอียดโรงเรียน:** แสดง cache ล่าสุดถ้ามี (SWR) พร้อม badge "ผลลัพธ์อาจไม่เป็นปัจจุบัน" เหมือน UC-01 E1 — แต่ผู้เปิดลิงก์ส่วนใหญ่มาจากนอกระบบและยังไม่เคยมี cache เลย จึงต้องมีหน้า "โหลดข้อมูลไม่สำเร็จ ลองใหม่อีกครั้ง" พร้อมปุ่ม retry เป็น fallback หลัก ไม่ใช่ error 500 เต็มหน้า

**Postcondition:** ได้ไฟล์ PDF ดาวน์โหลด และ/หรือ ลิงก์แชร์ที่เปิดใช้งานอยู่ (แล้วแต่ทางที่ผู้ใช้เลือก) — ฝั่งผู้เปิดลิงก์เห็นตารางเปรียบเทียบล่าสุดแบบ read-only ไม่มีสิทธิ์แก้ไข/บันทึกเพิ่มเอง (ต้องสมัครสมาชิกก่อนถ้าอยากบันทึกชุดของตัวเอง ผ่าน UC-04 → UC-03)
**Business Rule:** PDF ต้องระบุวันที่สร้างรายงานกำกับไว้เสมอ เพราะเป็น snapshot — ลิงก์แชร์เป็น**คนละอย่าง**กับ PDF โดยตั้งใจ: ข้อมูลอัปเดตตามจริงเสมอ (ไม่ใช่ snapshot) เพื่อให้ลิงก์มีประโยชน์ระยะยาวแม้เปิดทีหลังผ่านไปหลายเดือน — หน้าที่แชร์เป็น read-only เสมอ และไม่แสดงตัวตนเจ้าของชุดเปรียบเทียบต่อสาธารณะ (ไม่มี user_id/ชื่อ/อีเมลของเจ้าของปรากฏในหน้านี้หรือใน response ของ `get-shared-comparison` เลย)

## 3.3 กลุ่ม Admin

### UC-11: จัดการข้อมูลโรงเรียนโดยตรง

**Actor หลัก:** Admin
**คำอธิบาย:** ช่องทางที่ Admin แก้ไขข้อมูลโรงเรียนด้วยตนเอง (เช่น หลังโทรสอบถามโรงเรียนโดยตรง หรือแก้จากการตรวจพบข้อผิดพลาด) ผ่าน validation แล้ว **เผยแพร่ทันที** ไม่ต้องขออนุมัติซ้อนเพราะ Admin คือผู้อนุมัติอยู่แล้วในตัว
**Precondition:** ล็อกอินด้วยบัญชี Admin และโรงเรียนนั้นมีอยู่ในระบบแล้ว (นำเข้าผ่าน UC-12)

**Main Flow**
1. Admin เปิดหน้าแก้ไขโรงเรียน เห็น **ประวัติเวอร์ชันทั้งหมด** ของโรงเรียนนี้ (วันที่, แหล่งที่มา admin/scraper/bulk_import, ใครทำ, สรุปว่าแก้อะไรบ้างจาก diff_summary) ดึงจาก `school_versions` เรียงจากล่าสุด
2. Admin แก้ไขฟิลด์ที่ต้องการ ระบบ validate แล้วบันทึกเป็นเวอร์ชันใหม่ status=published ทันที
3. Admin เลือก "Restore" เวอร์ชันเก่าจากประวัติในข้อ 1 ได้ทุกเมื่อ ซึ่งจะสร้างเวอร์ชันใหม่ที่มีค่าเท่าเวอร์ชันเก่าที่เลือก (ไม่ใช่การลบเวอร์ชันหลังจากนั้นทิ้ง เพื่อรักษาความต่อเนื่องของ Audit Trail)

**Exception Flow**
- **E1 — Admin สองคนแก้ไขโรงเรียนเดียวกันพร้อมกัน:** ใช้ **Optimistic Locking ด้วย version number** — คนที่บันทึกทีหลังได้รับ conflict error ต้อง reload ก่อน
- **E2 — แก้ไขผิดพลาดโดยไม่ตั้งใจ:** ใช้ฟีเจอร์ "Restore เวอร์ชันก่อนหน้า" จากข้อ 3 ของ Main Flow ได้ทันที ไม่ต้องแก้ไขฟิลด์ทีละอันย้อนกลับเอง
- **E3 — Validation error:** แสดง error รายฟิลด์ก่อนบันทึก
- **E4 — ลบ/ปิดโรงเรียนที่มีข้อมูลผู้ใช้ผูกอยู่:** ใช้ **Soft Delete** เท่านั้น (สถานะ Archived) ห้าม hard delete

**Postcondition:** โรงเรียนมีเวอร์ชันใหม่สถานะ published ที่ `schools.current_published_version_id` ชี้อยู่ (อยู่ใน transaction เดียวกันตามหัวข้อ 8.5) และมีแถวใหม่ใน `audit_log`
**Business Rule:** ห้าม hard delete ข้อมูลโรงเรียนเด็ดขาด ใช้ Archived status แทนเสมอ

### UC-12: นำเข้าข้อมูลเริ่มต้น (OPEC Scrape, Serper URL)

**Actor หลัก:** Admin
**คำอธิบาย:** Seed ข้อมูลเริ่มต้นของทุกโรงเรียนในระบบ โดยใช้ 2 แหล่งประกอบกัน: (1) ดึงรายชื่อโรงเรียนนานาชาติที่ได้รับอนุญาตถูกต้องตามกฎหมายจากฐานข้อมูลของ **สช. (สำนักงานคณะกรรมการส่งเสริมการศึกษาเอกชน / OPEC)** และ (2) ใช้ **Serper API** (Google Search API) ค้นหา URL เว็บไซต์/เพจทางการของแต่ละโรงเรียนจากชื่อ+ที่อยู่ที่ได้จาก OPEC เพื่อเตรียมเป้าหมายให้ UC-13 ใช้ต่อ
**Precondition:** ล็อกอินด้วยบัญชี Admin และมีชุดข้อมูล OPEC พร้อมนำเข้า
**หมายเหตุ:** Use Case นี้**ไม่ได้รวบกับ UC-13** ทั้งที่ดูเหมือนเป็น "การเก็บข้อมูลจากภายนอก" เหมือนกัน เพราะผลลัพธ์ปลายทางต่างกันในเชิงกติกา — ที่นี่บันทึกเป็นเวอร์ชัน **Published ทันที** ส่วน UC-13 บันทึกเป็น **Pending Review** รออนุมัติ (ดูเหตุผลเต็มในหัวข้อ 2.6)

**Main Flow**
1. Admin สั่งรัน Import Job ระบุแหล่งข้อมูล (OPEC dataset)
2. ระบบ parse รายชื่อโรงเรียนจาก OPEC ตรวจสอบความซ้ำกับข้อมูลที่มีอยู่
3. สำหรับโรงเรียนใหม่แต่ละแห่ง เรียก Serper API ค้นหาด้วย query "ชื่อโรงเรียน + ที่อยู่/จังหวัด" เพื่อหา URL เว็บไซต์ทางการที่น่าจะใช่ที่สุด
4. Admin ตรวจสอบ preview รายการก่อน confirm import จริง (โดยเฉพาะ URL ที่ Serper หาให้)
5. Confirm → บันทึกเป็นเวอร์ชัน Published เริ่มต้นของแต่ละโรงเรียน พร้อม official_website_url

**Exception Flow**
- **E1 — บางแถวข้อมูลจาก OPEC ผิดรูปแบบ/ไม่ครบ:** ประมวลผลแบบ per-row ไม่ใช่ all-or-nothing แถวที่ผิดถูกรวบรวมเป็นรายงาน error ให้ Admin แก้ไขทีหลัง
- **E2 — Serper API หา URL ไม่เจอ หรือเจอ URL ที่ไม่ใช่เว็บโรงเรียนจริง** (เช่น หน้าข่าว/Wikipedia): ไม่ auto-confirm URL ที่ความมั่นใจต่ำ ต้องให้ Admin ยืนยัน/แก้เองในขั้นตอน Preview เสมอ
- **E3 — Serper API rate limit/ค่าใช้จ่ายเกิน quota:** ทำแบบ throttled/batch พร้อม retry ภายหลัง ไม่ยิง request ถี่เกินงบประมาณที่ตั้งไว้
- **E4 — ไฟล์/ข้อมูล OPEC ขนาดใหญ่/ใช้เวลานาน:** ประมวลผลแบบ async job พร้อม progress bar แจ้งผลเมื่อเสร็จ
- **E5 — ข้อมูลซ้ำกับโรงเรียนที่มีอยู่แล้ว:** flag ให้ Admin เลือก merge/skip/สร้างใหม่

**Postcondition:** โรงเรียนใหม่ถูกเพิ่มเข้าระบบพร้อม official_website_url ที่พร้อมให้ UC-13 ใช้ต่อ
**Business Rule:** URL ที่ได้จาก Serper ต้องผ่านการยืนยันจาก Admin อย่างน้อย 1 ครั้งก่อนถูกใช้เป็นเป้าหมาย Scraper จริง เพื่อป้องกัน Scraper ไปเก็บข้อมูลจากเว็บผิด

### UC-13: เก็บข้อมูลผ่าน Web Scraping อัตโนมัติ

**Actor หลัก:** Admin | **Actor รอง:** Scraper/Crawler Service
**คำอธิบาย:** แหล่งข้อมูลหลักที่แท้จริงของระบบ รักษาความเป็นปัจจุบันของข้อมูลทุกโรงเรียนโดยไม่ต้องพึ่งพาใครติดต่อเข้ามา
**Precondition:** โรงเรียนมี official_website_url แล้ว (จาก UC-12)

**Main Flow**
1. ระบบรัน Scraper ตามตารางเวลาที่ตั้งไว้ หรือ Admin สั่ง trigger เองเป็นรายโรงเรียน (ต้อง acquire lock เฉพาะโรงเรียนนั้นก่อนเริ่มเสมอ — ดูหัวข้อ 8.2 เรื่อง Concurrency)
2. Scraper ดึงเนื้อหาหน้าเว็บ/เพจตาม URL ที่บันทึกไว้ โดยเคารพ robots.txt และหน่วงเวลาระหว่าง request
3. แยกโครงสร้างข้อมูล (parsing) ด้วย selector แบบ rule-based หรือ LLM ช่วยอ่าน raw content พร้อมคำนวณ confidence score ต่อฟิลด์ — นอกจากค่าเทอม/ค่าใช้จ่ายแฝง/หลักสูตรแล้ว ยังนำทางไปหน้า Safety/Safeguarding Policy เพื่อสกัด**ข้อมูลความปลอดภัย**เพิ่มด้วย (ตาราง 7.10) โดยฟิลด์ที่หาไม่เจอให้เป็น `null` ห้ามเดาเป็น `false` — สำหรับฟิลด์กลุ่มค่าใช้จ่าย พยายามสกัด `source_published_at` เพิ่มด้วยแบบ best-effort (เช่น footer "Last updated", วันที่บนเอกสาร PDF) ไม่ error ถ้าหาไม่เจอในหน้านั้น เพราะเป็น optional field ตามหัวข้อ 7.3
4. เปรียบเทียบผลลัพธ์กับข้อมูล Published ปัจจุบัน หากต่างอย่างมีนัยสำคัญ (กำหนด threshold ต่อประเภทฟิลด์ เช่น ตัวเลขค่าเทอมเปลี่ยนเกิน 1% หรือ academic_year เปลี่ยน) จึงสร้างเวอร์ชันใหม่สถานะ **Pending Review** ส่งต่อ UC-14 — หากไม่ต่างเลยหรือต่างเล็กน้อยไม่มีนัยสำคัญ (เช่น หน้าเว็บจัดใหม่แต่เนื้อหาเดิม) จะไม่สร้าง Pending Review เพื่อลด noise
5. ไม่ว่าจะพบความเปลี่ยนแปลงหรือไม่ ให้อัปเดต `schools.last_verified_at` เป็นเวลาปัจจุบันเสมอเมื่อ Scrape สำเร็จ เพื่อเป็นสัญญาณ "ตรวจสอบล่าสุดเมื่อไหร่" แยกจาก "เปลี่ยนแปลงล่าสุดเมื่อไหร่" (ดูหัวข้อ 7.3)

**Exception Flow**
- **E1 — โครงสร้างเว็บไซต์เปลี่ยนจน Selector เดิมใช้งานไม่ได้:** Job fail แบบ graceful ไม่ commit ข้อมูลผิดเข้า Pending Review แจ้งเตือนทีมพัฒนาให้ปรับปรุง (และไม่อัปเดต last_verified_at เพราะยังไม่ได้ตรวจสอบสำเร็จจริง)
- **E2 — เว็บไซต์เป้าหมาย Block/Rate-limit:** ใช้ User-Agent ระบุตัวตนชัดเจน หน่วงเวลาและ retry แบบ backoff หยุด Scrape ชั่วคราวหากถูก Block ต่อเนื่อง
- **E3 — Scraper ตรวจพบความเปลี่ยนแปลงขณะ Admin กำลังแก้ไขโรงเรียนเดียวกันอยู่พอดี (UC-11):** ใช้ parent_version_id เช็คเช่นเดียวกับ Optimistic Locking — ถ้า Admin บันทึกไปก่อนแล้ว Pending Review จาก Scraper ที่ base เวอร์ชันเก่ากว่าจะถูก flag ให้ re-diff ก่อน
- **E4 — เว็บไซต์โรงเรียนใช้งานไม่ได้แล้ว/โดเมนหมดอายุ:** Flag เป็น "ต้องตรวจสอบด้วยตนเอง" ให้ Admin ตามหาช่องทางใหม่
- **E5 — ผลลัพธ์จากการ Extract ผิดปกติ:** Sanity-check ทาง Backend (range validation) กรองออกก่อนเข้า Pending Review
- **E6 — เนื้อหาที่ Scrape มาอาจมีสคริปต์/โค้ดแฝง** (เว็บโรงเรียนถูกแฮ็ก หรือ URL ที่ Serper ให้มาไม่ใช่เว็บโรงเรียนจริงตาม UC-12 E2): Sanitize/escape เนื้อหาทุกฟิลด์ (strip HTML/script tags) ก่อนบันทึกเข้า Pending Review เสมอ ไม่พึ่งพาการตรวจสอบด้วยสายตาของ Admin ใน Diff View เป็นด่านเดียว
- **E7 — โรงเรียนไม่ถูก verify สำเร็จมานานเกิน threshold ที่กำหนด** (เช่น เกิน 6 เดือน จาก E1-E4 ที่ล้มเหลวซ้ำ): flag ขึ้น Dashboard ของ UC-19 ให้ Admin ตรวจสอบด้วยตนเอง (ถ้า UC-19 ถูกตัดออกจาก scope ต้องย้าย flag นี้ไปแสดงที่ UC-18 แทน ห้ามปล่อยให้ไม่มีที่แสดง)ว่า Scraper ยังทำงานปกติกับโรงเรียนนี้อยู่หรือไม่ ป้องกัน Silent Failure ที่ไม่มีใครสังเกตเห็น

**Postcondition:** ทุกโรงเรียนมีข้อมูลที่ค่อนข้างเป็นปัจจุบัน โดยไม่ต้องมีใครติดต่อเข้ามาเลย
**Business Rule:** ข้อมูลจาก Scraper ต้องผ่าน Admin อนุมัติเสมอ ไม่มีข้อยกเว้น

### UC-14: ตรวจสอบและอนุมัติ/ปฏิเสธข้อมูลที่ Scraper ตรวจพบ

**Actor หลัก:** Admin
**คำอธิบาย:** ด่านอนุมัติสุดท้ายก่อนข้อมูลที่ Scraper เก็บมาจะขึ้นให้ผู้ใช้เห็นจริง โดย Admin อ่าน Diff ทีละฟิลด์แล้วตัดสิน Approve/Reject — เป็นจุดที่ Business Rule ของ UC-13 ("ข้อมูลจาก Scraper ต้องผ่าน Admin อนุมัติเสมอ") ถูกบังคับใช้จริง
**Precondition:** ล็อกอินด้วยบัญชี Admin และมีเวอร์ชันสถานะ Pending Review อย่างน้อย 1 รายการในคิว (สร้างโดย UC-13 ข้อ 4)

**Main Flow**
1. Admin เปิดคิวคำขอที่รออนุมัติ
2. ระบบแสดง **Diff View** เทียบข้อมูลเดิมกับข้อมูลที่ Scrape มาได้ทีละฟิลด์ พร้อม confidence score
3. Admin เลือก Approve ทั้งหมด/บางฟิลด์ หรือ Reject
4. Approve → publish เวอร์ชันใหม่ (อัปเดต `schools.current_published_version_id` ใน transaction เดียวกับการเปลี่ยน status ของ `school_versions` เป็น published — ดูหัวข้อ 8.5), และ invalidate cache ฝั่ง Client
5. Reject → เวอร์ชันนี้ถูกทิ้ง ไม่กระทบข้อมูล Published เดิม

**Exception Flow**
- **E1 — ข้อมูล Live ถูกแก้โดย Admin ระหว่างกำลัง Review:** ตรวจสอบ base version ที่ Scraper ใช้ตอนสร้าง Pending ว่ายังตรงปัจจุบันหรือไม่ก่อน approve ถ้าไม่ตรงต้อง re-diff ใหม่
- **E2 — Admin ปฏิเสธข้อมูลจาก Scraper ของโรงเรียนเดียวกันซ้ำหลายรอบติดกัน:** flag เป็น "ต้องตรวจสอบ Scraper Config ด้วยตนเอง" แทนวนเข้าคิวซ้ำเดิม

**Postcondition:** เวอร์ชันที่ถูก Approve กลายเป็น published — หรือเวอร์ชันที่ถูก Reject ถูกทิ้งโดยข้อมูล published เดิมไม่ถูกแตะ ทั้งสองกรณีมี Audit Trail ครบ
**Business Rule:** ทุก action ต้องมี Audit Trail ครบถ้วน

### UC-15: จัดการบัญชีผู้ใช้ (ระงับ/ลบ)

**Actor หลัก:** Admin
**คำอธิบาย:** ระงับหรือลบบัญชีผู้ใช้ที่ละเมิดกติกา โดยทุกครั้งต้องระบุเหตุผลและถูกบันทึกลง Audit Log — มักถูกเรียกต่อจาก UC-16 ข้อ 4 ในกรณีที่เนื้อหาผิดกติการ้ายแรงหรือทำซ้ำ
**Precondition:** ล็อกอินด้วยบัญชี Admin

**Main Flow**
1. Admin ค้นหา/เปิดดูบัญชีผู้ใช้ที่ต้องการจัดการ
2. เลือกระงับ (suspend) ชั่วคราวหรือลบ พร้อมระบุเหตุผล

**Exception Flow**
- **E1 — ระงับบัญชีที่กำลังใช้งานอยู่ (active session):** session ปัจจุบันถูก invalidate ทันที ไม่รอ token หมดอายุเอง
- **E2 — ลบบัญชีที่มีข้อมูลผูกอยู่มาก:** ใช้ Soft Delete เท่านั้น (เช่นเดียวกับ UC-06 E5 — `account-deletion-cron` แก้ข้อมูลข้าม 3 schema ในธุรกรรมเดียวตอน Grace Period หมด ดู System Architecture หัวข้อ 4.2)
- **E3 — Admin ระงับบัญชีผิดคน:** มีปุ่ม "ยกเลิกการระงับ" คืนสิทธิ์ได้ทันที พร้อม log ไว้ audit

**Postcondition:** บัญชีอยู่ในสถานะ `suspended` หรือ `pending_deletion` ตามที่ Admin เลือก พร้อมเหตุผลที่บันทึกไว้ใน `audit_log` (การลบจริงเกิดตอน Grace Period หมดตาม UC-06 E5)
**Business Rule:** ทุกการระงับ/ลบต้องระบุเหตุผลและถูกบันทึกใน Audit Log เสมอ

### UC-16: ดูแลเนื้อหาในฟอรัม

**Actor หลัก:** Admin
**คำอธิบาย:** คิวตรวจเนื้อหาที่ผู้ใช้เขียนขึ้นในฟอรัม (กระทู้และความคิดเห็น) เฉพาะรายการที่ถูกรายงานหรือติด content filter ตามแนวทาง **Post-Moderation** ของ UC-05 — ตั้งแต่ v6.5 ฟอรัมเป็นเนื้อหาจากผู้ใช้ชนิดเดียวที่ระบบเป็นเจ้าของ เพราะรีวิวเปลี่ยนไปใช้ข้อมูลจาก Google ซึ่งระบบไม่มีสิทธิ์แก้ไขหรือคัดกรอง (ดู UC-02 Business Rule ข้อ 2) จึงไม่มีคิวตรวจรีวิวอีกต่อไป
**Precondition:** ล็อกอินด้วยบัญชี Admin และมีเนื้อหาฟอรัมรอตรวจอย่างน้อย 1 รายการในคิว (จาก UC-05)

**Main Flow**
1. Admin เปิดคิว "เนื้อหารอตรวจ" ซึ่งรวมเนื้อหาฟอรัมที่ถูกรายงานจาก UC-05 ข้อ 7 เรียงตามจำนวนผู้รายงาน และเนื้อหาสถานะ `pending` ที่ติด content filter (UC-05 E5)
2. อ่านทบทวนเนื้อหาพร้อมบริบทของทั้งเธรด ไม่ใช่แค่ข้อความเดี่ยว เพราะข้อความเดียวกันอาจเหมาะสมหรือไม่เหมาะสมขึ้นกับบริบทที่ตอบ
3. เลือก "คงไว้" (ปิดรายงานโดยไม่แก้อะไร) หรือ "นำออก" (`rejected`) พร้อมระบุเหตุผลเสมอ
4. กรณีร้ายแรงหรือทำซ้ำ สั่งระงับบัญชีผู้เขียนต่อได้ทันทีผ่าน UC-15

**Exception Flow**
- **E1 — เนื้อหาถูกรายงานเยอะผิดปกติเพราะความเห็นต่าง ไม่ใช่เพราะผิดกฎ:** จำนวนผู้รายงานเป็นแค่ลำดับความสำคัญ ไม่ใช่เกณฑ์ตัดสิน — ระบบห้ามซ่อนเนื้อหาอัตโนมัติตามจำนวนรายงานเด็ดขาด ต้องมี Admin ตัดสินเสมอ
- **E2 — เจ้าของเนื้อหาลบเองก่อน Admin ตรวจ:** ปิดรายงานอัตโนมัติพร้อมบันทึกว่า "ผู้เขียนลบเอง" ไม่ค้างอยู่ในคิว
- **E3 — ผู้เขียนโต้แย้งว่าการนำเนื้อหาออกไม่เป็นธรรม:** มีช่องทางยื่นอุทธรณ์ เข้าคิวให้ Admin คนอื่นพิจารณาซ้ำ หากช่วงนั้นมี Admin ปฏิบัติงานอยู่คนเดียว ให้ทบทวนใหม่อีกรอบพร้อมบันทึกเหตุผลเพิ่มเติมลง Audit Log แทน เพื่อให้มีร่องรอยการพิจารณาสองรอบเสมอ
- **E4 — Volume เนื้อหาเยอะเกินตรวจด้วยตา:** ตรวจเฉพาะที่ถูกรายงานหรือติด filter เท่านั้น ไม่ไล่อ่านทั้งฟอรัม (นี่คือเหตุผลที่เลือก Post-Moderation ตั้งแต่แรก)
- **E5 — ต้องนำเนื้อหาที่เคยตัดสินว่า "คงไว้" ออกในภายหลัง:** ทำได้ แต่ต้องบันทึกเหตุผลใหม่ทับไว้ใน Audit Log เผื่อมีข้อโต้แย้งว่าทำไมมาตรฐานเปลี่ยน

**Postcondition:** เนื้อหาอยู่สถานะ `approved` (คงอยู่ใน UC-05) หรือ `rejected` (ไม่แสดงต่อสาธารณะแต่ยังเก็บไว้ในฐานข้อมูล) พร้อมผู้ตัดสินและเหตุผลที่บันทึกไว้ และรายงานที่เกี่ยวข้องถูกปิดทั้งหมด
**Business Rule:** (1) ทุกการนำเนื้อหาออกต้องระบุเหตุผลและถูกบันทึกใน Audit Log เสมอ (2) เนื้อหาที่ถูกนำออกไม่ถูกลบจริงจากฐานข้อมูล (เก็บไว้เผื่อมีข้อโต้แย้ง) แต่ไม่แสดงต่อสาธารณะทุกกรณี (3) **ขอบเขตของ Use Case นี้จำกัดอยู่ที่เนื้อหาในฟอรัมเท่านั้น** — รีวิวที่แสดงใน UC-02 เป็นข้อมูลของ Google ที่ระบบไม่มีสิทธิ์แก้ไขหรือนำออก ผู้ที่ต้องการโต้แย้งรีวิวต้องดำเนินการที่ Google เอง

### UC-17: จัดการคำแจ้งข้อมูลผิดพลาดจากผู้ใช้

**Actor หลัก:** Admin
**คำอธิบาย:** งาน**สืบข้อเท็จจริง**จาก Ticket ที่ผู้ใช้แจ้งเข้ามาตาม UC-09 แล้วจบด้วยการสั่งงานต่อไปยัง Use Case อื่น — ต่างจาก UC-14 ที่เป็นการอ่าน Diff แล้วกด Approve/Reject ตรง ๆ (เหตุผลที่ไม่รวบสอง Use Case นี้อยู่ในหัวข้อ 2.5)
**Precondition:** ล็อกอินด้วยบัญชี Admin และมี Ticket อย่างน้อย 1 รายการในคิวจาก UC-09

**Main Flow**
1. Admin เปิดคิว Ticket จาก UC-09 เรียงตามจำนวนคนแจ้งซ้ำ/ความสำคัญ
2. ตรวจสอบข้อเท็จจริง (เข้าเว็บโรงเรียนเอง หรือสั่ง UC-13 Scrape เฉพาะจุดซ้ำ) แล้วตัดสินใจ

**Exception Flow**
- **E1 — ตรวจสอบแล้วพบว่าผู้แจ้งเข้าใจผิด:** ปิด Ticket พร้อมเหตุผล แจ้งกลับผู้ใช้ ไม่ต้องแก้ข้อมูล
- **E2 — ตรวจสอบแล้วพบว่าผู้แจ้งถูกต้อง:** แก้ไขโดยตรงผ่าน UC-11 หรือสั่ง UC-13 เฉพาะโรงเรียนนั้นแล้วรอผลผ่าน UC-14
- **E3 — มี Ticket ค้างเกินเวลาที่กำหนด (SLA):** ระบบแจ้งเตือน Admin อัตโนมัติเมื่อ Ticket ค้างเกิน threshold

**Postcondition:** Ticket ถูกปิดพร้อมผลลัพธ์ ผู้แจ้งได้รับแจ้งเตือนสถานะ
**Business Rule:** ทุก Ticket ต้องมีผลสรุปและถูกบันทึกไว้ ไม่ปล่อยค้างสถานะ "รอตรวจสอบ" ไม่มีกำหนด

### UC-18: ตรวจสอบบันทึกระบบ (Audit Log + Log สนทนา AI)

**Actor หลัก:** Admin | **Actor รอง:** AI/LLM Recommendation Engine (เฉพาะส่วน Log สนทนา)
**คำอธิบาย:** หน้าเดียวสำหรับค้นหาและอ่านบันทึกย้อนหลังของระบบ แยกเป็น 2 ชุดข้อมูลที่ใช้ Main Flow เดียวกัน (เปิดหน้า → กรอง → อ่านรายละเอียด) แต่มีกติกาความเป็นส่วนตัวและ retention คนละแบบตาม Business Rule ด้านล่าง — เดิมแยกเป็น UC-A10 กับ UC-A08
**Precondition:** ล็อกอินด้วยบัญชี Admin

**Main Flow (Audit Log)**
1. Admin เปิดหน้า Audit Log ค้นหา/กรองตาม actor, action, ช่วงเวลา, entity
2. ดูรายละเอียด before/after snapshot ของแต่ละ action

**Alternate Flow (Log การสนทนา AI)**
3. Admin เปิดแท็บ Log การสนทนา กรองตามช่วงเวลา/สถานะ (ผู้ใช้ report, ระบบตรวจพบ hallucination จาก UC-08 E6)
4. อ่าน transcript เพื่อประเมินคุณภาพคำตอบ/หา pattern ที่ต้องปรับปรุง prompt

**Exception Flow**
- **E1 — พยายามแก้ไข/ลบ audit log ย้อนหลัง:** ระบบปฏิเสธเสมอ (Append-only โดยสถาปัตยกรรม ไม่มี endpoint ให้แก้ไขได้แม้เป็น Admin)
- **E2 — Log มีปริมาณมากจนค้นหาช้า:** ทำ indexing ตามฟิลด์ที่ค้นบ่อย (actor_id, entity_id, created_at) พร้อม pagination
- **E3 — ต้องการ export log ไปตรวจสอบภายนอก:** รองรับ export เป็น CSV แบบ async job เหมือน UC-10
- **E4 — บทสนทนามีข้อมูลส่วนบุคคลของผู้ใช้:** mask ข้อมูลอ่อนไหวก่อนแสดงให้ Admin เห็น (PDPA compliance แม้เป็น internal use)
- **E5 — Log สนทนามีปริมาณมากเกินไล่ดูทั้งหมด:** เรียงลำดับด้วย signal อัตโนมัติ (thumbs-down จาก UC-08 ข้อ 7, hallucination flag จาก UC-08 E6) ให้ Admin ดูเคสสำคัญก่อน
- **E6 — Log สนทนากระทบ storage/performance:** ตั้ง retention policy (เก็บ raw transcript ไม่เกิน 90 วัน สรุปสถิติไว้ระยะยาวแทน) — ต่างจาก Audit Log ที่เก็บถาวร

**Postcondition:** Admin เห็น/ส่งออกรายการบันทึกตามเงื่อนไขที่กรอง โดยตัวบันทึกไม่ถูกแก้ไขหรือลบ — และกรณีเปิดดูบทสนทนา AI การเข้าดูนั้นถูกบันทึกไว้ใน `audit_log` แยกจาก action ทั่วไปตาม PDPA
**Business Rule:** (1) Audit Log เป็นแหล่งความจริงสุดท้าย (Source of Truth) เมื่อเกิดข้อพิพาทว่าใครทำอะไรไปเมื่อไหร่ เป็น append-only เก็บถาวร (2) การเข้าถึง Log การสนทนาต้องมี audit ว่าใครเปิดดูบทสนทนาของใครเมื่อไหร่ เพราะเป็นข้อมูลส่วนบุคคล และมี retention 90 วันต่างจาก Audit Log — **สองกติกานี้ห้ามปนกัน** แม้อยู่ใน Use Case เดียวกัน

### UC-19: ดู Dashboard สถิติการใช้งาน

**Actor หลัก:** Admin
**คำอธิบาย:** หน้าสรุปภาพรวมการใช้งานและสุขภาพของระบบสำหรับ Admin เป็นแบบอ่านอย่างเดียว ใช้เฝ้าระวังคิวงานค้างและ Silent Failure ของ Scraper เป็นหลัก
**Precondition:** ล็อกอินด้วยบัญชี Admin

**Main Flow**
1. Admin เปิดหน้า Dashboard เห็นภาพรวม (ผู้ใช้ใหม่, โรงเรียนที่ถูกค้นหา/ดูมากที่สุด, อัตราการใช้ AI, คิว Pending Review ค้าง, โรงเรียนที่ verify ไม่สำเร็จนานเกิน threshold ตาม UC-13 E7, งาน re-embed ที่ตกใน `failed_jobs` ตามหัวข้อ 3.4, ค่าใช้จ่าย LLM/Serper API สะสมรายวัน)
2. กรองช่วงเวลา/export ดูรายละเอียดเพิ่มได้

**Exception Flow**
- **E1 — Query สถิติหนักกระทบ production DB:** ไม่คำนวณสดทุกครั้ง — ใช้ **Materialized View** ที่ refresh ตามรอบด้วย `pg_cron` แล้วให้ Dashboard อ่านจาก view นั้นแทน (ระบบนี้ไม่มี Read Replica/Data Warehouse แยก เพราะทุก Service ยังอยู่ Postgres instance เดียวกัน ดู System Architecture หัวข้อ 4.6) ใช้ร่วมกับ cache ใน E3
- **E2 — ข้อมูลสถิติมี lag:** แสดง timestamp "ข้อมูลล่าสุดเมื่อ..." กำกับเสมอ
- **E3 — Dashboard โหลดช้า:** cache ผลลัพธ์ที่คำนวณแล้วไว้ระยะสั้น (5-15 นาที) แทนคำนวณใหม่ทุกครั้ง

**Postcondition:** Admin เห็นภาพรวมสถิติพร้อม timestamp กำกับว่าข้อมูลเป็นปัจจุบันถึงเมื่อใด — เป็น read-only ไม่เปลี่ยนแปลงข้อมูลในระบบ
**Business Rule:** Dashboard เป็น read-only ไม่มีการแก้ไขข้อมูลจากหน้านี้โดยตรง — เป็น Use Case เดียวที่ทำเครื่องหมาย Could ในกลุ่ม Admin จึงเป็นตัวแรกที่ตัดออกได้ถ้าเวลาไม่พอ โดยไม่กระทบ Use Case อื่น (ข้อมูลที่ Dashboard แสดงยังเข้าถึงได้ผ่าน UC-18 และ query ตรงที่ฐานข้อมูล)

## 3.4 ส่วนขยายที่ออกแบบไว้แล้วแต่ยังไม่เปิดใช้ในเฟสนี้

> ส่วนนี้**ไม่ใช่ Use Case** เพราะไม่มี Actor เป็นผู้ริเริ่ม และ**ไม่ได้ทำงานอยู่ในเฟสนี้** —
> เก็บการออกแบบไว้ครบเพื่อให้ขยายต่อได้โดยไม่ต้องรื้อของเดิม แต่ละหัวข้อระบุ
> **เงื่อนไขที่ต้องเกิดก่อนถึงจะเปิดใช้** ไว้ชัดเจน ตารางในฐานข้อมูลที่รองรับถูกสร้างไว้แล้ว
> แต่ยังไม่มีข้อมูลไหลเข้า และ**ไม่มี Use Case ใดพึ่งพาส่วนนี้ในการทำงานปกติ**

### 3.4.1 การอัปเดตฐานความรู้ของ AI อัตโนมัติ (RAG Re-embedding) — เดิมคือ UC-A07

> **สถานะ: ออกแบบไว้แล้ว ยังไม่เปิดใช้** — ระบบเวอร์ชันปัจจุบัน**ไม่มี RAG ทำงานอยู่จริง**
> AI Chatbot (UC-08) ตอบคำถามด้วย **function calling บนข้อมูล structured ในฐานข้อมูล**
> ไม่ได้ใช้ vector search เลย และ v6.5 ที่เปลี่ยนมาใช้ Guided Prompts ยิ่งทำให้ทุกคำถาม
> map เข้า query ที่นิยามไว้ล่วงหน้า ซึ่งเป็นเส้นทางที่แม่นกว่าและถูกกว่าสำหรับคำถาม
> เชิงตัวเลข/หมวดหมู่ที่ผู้ปกครองถามจริง
>
> **เงื่อนไขที่ต้องเกิดก่อนถึงจะเปิดใช้:** Phase 3 ของ Data Pipeline ต้องขยายไปเก็บ
> **เนื้อหาข้อความอิสระ** ของโรงเรียน (ปรัชญาการสอน บรรยากาศ นโยบาย กิจกรรม) เพิ่มจาก
> ข้อมูล structured ที่เก็บอยู่ตอนนี้ — ตราบใดที่ยังไม่มีข้อความพวกนี้ การ embed
> จะได้เวกเตอร์ของข้อมูลที่ query ตรง ๆ ได้อยู่แล้ว ซึ่งไม่เพิ่มความสามารถอะไรเลย
>
> **สิ่งที่มีอยู่แล้วและพร้อมใช้ทันทีเมื่อเปิด:** ตาราง `ai.school_embeddings` (หัวข้อ 7.19),
> extension `pgvector` ใน `db/schema.sql` และการออกแบบ flow ทั้งหมดด้านล่าง

**ผู้รับผิดชอบเมื่อเปิดใช้:** AI Service (`re-embed-handler`) | **Trigger:** Database Webhook บน `school_data.school_versions`
**เหตุผลที่ลดรูปจาก Use Case:** Main Flow เดิมทั้ง 3 ขั้นเป็นงานอัตโนมัติล้วน ไม่มี Actor มนุษย์ทำอะไรเลย ส่วนขั้นที่ 4 ที่ Admin ตรวจงานล้มเหลว ก็ทำผ่าน UC-18/UC-19 อยู่แล้ว — การคงไว้เป็น Use Case แยกทำให้แผนภาพ Use Case มีวงรีที่ไม่มีเส้นเชื่อมกับ Actor ใดเลย ซึ่งผิดหลักการของ Use Case Diagram

**ลำดับการทำงานที่ออกแบบไว้ (เมื่อเปิดใช้)**
1. เวอร์ชันใหม่ถูก publish (จาก UC-11 หรือ UC-14) → **Database Webhook** บน `school_data.school_versions` ยิง HTTP ไปหา `re-embed-handler` ของ **AI Service** อัตโนมัติ พร้อม Correlation ID เดียวกับ flow ต้นทาง (ดูหัวข้อ 8.6)
2. `re-embed-handler` เรียกข้าม Service ไปที่ `school-data-api` ของ **School Data Service** เพื่อดึงข้อความของเวอร์ชันที่เพิ่ง publish (ไม่ query schema `school_data` ตรงตาม Golden Rule)
3. คำนวณ embedding แล้ว **upsert** ลง `ai.school_embeddings` โดยใช้ `version_id` เป็น key (ต้อง idempotent เพราะ webhook เป็น at-least-once delivery — ดูหัวข้อ 8.4)
4. Admin ตรวจสอบงาน re-embed ที่ล้มเหลวได้จากตาราง `ops.failed_jobs` ผ่าน UC-18 (Log) หรือ UC-19 (Dashboard)

**Exception Flow**
- **E1 — Embedding job ล้มเหลว:** retry แบบ exponential backoff ถ้ายัง fail ซ้ำให้ตกเข้าตาราง `failed_jobs` (แทน Dead Letter Queue) พร้อมแจ้งเตือนทีมพัฒนา
- **E2 — pgvector (`ai.school_embeddings`) ยังไม่ถูก re-embed ตามข้อมูลล่าสุดทันที:** เพราะ **AI Service** ต้องเรียกข้าม Service ไปหา `school-data-api` ของ **School Data Service** แบบ async ผ่าน Database Webhook → `re-embed-handler` (ดู System Architecture หัวข้อ 4.3) ยอมรับ eventual consistency ในช่วงเวลาสั้น (ไม่เกิน 5-10 นาที) — เป็นธรรมชาติของการแยก Service กันจริงตาม Golden Rule ไม่ใช่ bug

**Postcondition:** `ai.school_embeddings` มี embedding ที่ตรงกับเวอร์ชัน published ล่าสุดของโรงเรียนนั้น (ภายในกรอบ eventual consistency ตาม E2) หรือมีร่องรอยความล้มเหลวอยู่ใน `failed_jobs` เสมอ ไม่สูญหายโดยไม่มีร่องรอย
**Business Rule (มีผลเมื่อเปิดใช้):** ห้าม embed ข้อมูลที่ยังไม่ผ่านสถานะ published เด็ดขาด — ฐานความรู้ของ AI ต้องสะท้อนเฉพาะข้อมูลที่ Admin อนุมัติแล้วเท่านั้น สอดคล้องกับ Business Rule ของ UC-13/UC-14

**สรุปผลกระทบต่อเฟสนี้:** เนื่องจากยังไม่เปิดใช้ **UC-11 และ UC-14 จึงไม่มีขั้นตอน re-embed
ใน Main Flow** และไม่มี Exception เรื่อง `re-embed-handler` ล้มเหลว — การ publish จบที่การอัปเดต
`current_published_version_id` และเขียน `audit_log` เท่านั้น ถ้าเปิดใช้ในอนาคตให้เพิ่มกลับเป็น
`«include»` ของทั้งสอง Use Case ตามที่ออกแบบไว้ข้างบน โดยไม่ต้องแก้โครงสร้างอื่น

## 4. รูปแบบการจัดการข้อผิดพลาดฝั่ง Backend (Cross-cutting Patterns)

| Pattern | ใช้แก้ปัญหาอะไร | ใช้ใน Use Case ตัวอย่าง |
|---|---|---|
| **Retry + Exponential Backoff + Jitter** | เรียก service/API ที่ล้มเหลวชั่วคราว | LLM API, Serper API, Media Storage, Edge Function-to-Edge Function call (ดูหัวข้อ 4 ของ System Architecture — ระบบนี้ไม่มี Message Queue) |
| **Circuit Breaker** | ป้องกัน cascading failure เมื่อ service ปลายทางล่ม | External API (Maps, Serper, LLM, **Google Places**) **และ** internal call ข้าม Service ผ่าน Edge Function (เช่น Chatbot → `school-data-api`/`user-data-api`, Re-embed handler → `school-data-api`) — ตอนนี้มี Service แยกจริงตาม schema แล้ว (ดู System Architecture หัวข้อ 4) |
| **Cache + Stale-While-Revalidate** | ลด latency และให้บริการต่อได้แม้ backend ช้า/ล่มชั่วคราว | UC-01, UC-02 (ทำที่ฝั่ง Frontend ด้วย SWR/TanStack Query ไม่ต้องสร้าง caching layer เอง) — ส่วนรีวิวจาก Google cache ไว้ฝั่ง server ด้วยตาราง 7.6 เพราะมีโควตาต่อวันและมีข้อกำหนดเรื่องอายุ cache |
| **Optimistic Locking (version field)** | ป้องกัน conflict เมื่อแก้ไขข้อมูลพร้อมกันหลาย session | UC-11, UC-13, UC-14 |
| **Database Webhook → Edge Function** (แทน Event-Driven Sync ผ่าน Message Queue) | trigger งาน async ข้าม Service (เช่น School Data Service publish → AI Service re-embed) โดยไม่ต้องมี Message Queue จริง | Re-embed handler (หัวข้อ 3.4) |
| **(ตัดออก) Reconciliation Job** | ยังไม่จำเป็น เพราะทุก schema อยู่ Postgres instance เดียวกัน ไม่มีความเสี่ยง network partition ระหว่าง service แบบที่ database แยก instance กันจะเจอ (ถ้าในอนาคตแยก instance จริงตาม service ค่อยพิจารณาใหม่) | — |
| **Idempotency Key** | ป้องกันข้อมูลซ้ำจากการ retry ของ client | UC-04, UC-05 (กดถูกใจ/รายงาน), UC-06 (บันทึกโรงเรียนโปรด — บังคับด้วย composite PK และ unique constraint ที่ระดับ DB ดูหัวข้อ 7.13/7.21) |
| **`failed_jobs` table** (แทน Dead Letter Queue) | เก็บ job ที่ fail ซ้ำหลายครั้งไว้ตรวจสอบภายหลังโดยไม่บล็อกระบบหลัก — ไม่ต้องมี Message Queue จริง | UC-13, หัวข้อ 3.4 |
| **Correlation ID** | เชื่อม Log ข้าม Edge Function ตอนเรียกข้าม Service | UC-08 (Chatbot → School Data/User Service), หัวข้อ 3.4, UC-10 (`get-shared-comparison` → School Data Service, ดูหัวข้อ 8.6) |
| **Graceful Degradation** | fallback แทน error 500 เมื่อ service ล่ม | UC-08, UC-01 E5 |
| **Field-level Validation (Defense in Depth)** | ป้องกันข้อมูลผิดรูปแบบตั้งแต่ต้นทาง | ทุก Use Case ที่มีการกรอกฟอร์ม |
| **Soft Delete + Versioning + Audit Log** | ป้องกันข้อมูลหายถาวรจากความผิดพลาด รองรับการ undo | UC-11, UC-15, UC-06 |

## 5. วงจรสถานะของข้อมูลโรงเรียน (Data Lifecycle)

```
[Admin แก้ไขข้อมูลโดยตรง] --(ผ่าน validation)--> Published ทันที

[Scraper อัตโนมัติ] --(ตรวจพบความต่างที่มีนัยสำคัญ)--> Pending Review --(Admin อนุมัติ)--> Published
                                                              |
                                                              +--(Admin ปฏิเสธ)--> ทิ้งเวอร์ชันนี้ (ไม่กระทบ Published เดิม)

[ระดับโรงเรียน — schools.status]
active --(โรงเรียนปิดกิจการ/Admin สั่ง Archive)--> archived
archived --(Admin สั่ง Reactivate)--> active
```

**หมายเหตุเรื่องระดับของสถานะ:** `Pending Review`/`Approved`/`Rejected`/`Published`/`Superseded` เป็นสถานะของ **`school_versions`** (หัวข้อ 7.2) ส่วน `active`/`archived` เป็นสถานะของ **`schools`** (หัวข้อ 7.1) คนละระดับกัน — การ Archive ไม่ได้ลบเวอร์ชัน published ทิ้ง แต่ทำให้โรงเรียนไม่ขึ้นในผลค้นหา (UC-01) และหน้ารายละเอียดขึ้น banner แทน (UC-02 E1b) ส่วนการ Reactivate คืนค่า `schools.status` เป็น `active` โดยยังชี้เวอร์ชันเดิมที่ `current_published_version_id`

**หลักการสำคัญ:** ข้อมูลที่ Guest/Parent มองเห็นต้องมาจากสถานะ **Published** เท่านั้นเสมอ Admin เป็นผู้เดียวที่ทำให้ข้อมูลเป็น Published ได้ ไม่ว่าจะแก้เองหรืออนุมัติจาก Scraper

## 6. ข้อเสนอแนะสำหรับขอบเขตโปรเจกต์ (Scoping Notes)

- สถาปัตยกรรมนี้เรียบง่ายและตรงกับ Plan จริงของทีม: **ไม่มี School Representative, ไม่มี Role/Permission หลายระดับ** — Admin มีบทบาทเดียว ทำให้ Timeline พัฒนาสั้นลงชัดเจน
- **การสร้าง/จัดการบัญชี Admin เอง ไม่ได้ทำเป็น Use Case ในระบบ** (ต่างจาก UC-15 ที่จัดการบัญชี Parent/User) เพราะสมมติฐานคือทีมงานมีจำนวนน้อย จึงตั้งค่าบัญชี Admin ผ่านระดับ Infrastructure/Database โดยตรงแทนการทำ UI จัดการเอง — Exception ที่พูดถึง "Admin สองคน" (เช่น UC-11 E1, UC-16 E3) จึงหมายถึง Admin ที่ถูกสร้างไว้ล่วงหน้าแล้ว ไม่ใช่ระบบเปิดให้สมัครเอง ถ้าโปรเจกต์ขยายทีมในอนาคตค่อยเพิ่มเป็น Use Case ใหม่ทีหลังได้
- **ฟอรัมยังไม่มีการแจ้งเตือนเมื่อมีคนตอบกระทู้ — เป็นการตัดสินใจ ไม่ใช่การมองข้าม** เพราะฟีเจอร์แจ้งเตือนทั้งหมดถูกตัดออกจากเฟสนี้แล้ว (ดู bullet ถัดไปเรื่อง Notification/Saved Search) ผู้ใช้ต้องกลับเข้ามาดูกระทู้เอง ถ้าจะเพิ่มในอนาคตให้ต่อกับ `notification-sender` ของ Ops Service ที่มีอยู่แล้วผ่าน Database Webhook เหมือน UC-09 ไม่ต้องรื้อของเดิม
- **ฟอรัม (UC-05 ฝั่งผู้ใช้ และ UC-16 ฝั่ง Admin) ใช้ Post-Moderation ไม่ใช่ Pre-Moderation** — เลือกแบบนี้เพราะทีมมี Admin จำนวนน้อยมาก ถ้าบังคับให้ทุกกระทู้รอตรวจก่อน ฟอรัมจะไม่มีความเคลื่อนไหวตั้งแต่วันแรกและกลายเป็นภาระ Admin ที่ไม่จำเป็น
- **ตั้งแต่ v6.5 ระบบไม่รับรีวิวที่ผู้ใช้เขียนเอง** แต่ดึงรีวิวจาก **Google Places API** มาแสดงแทน (UC-02 แท็บรีวิว) — แลกกันตรงที่ระบบไม่ต้องแบกภาระ Moderation รีวิวและได้ปริมาณรีวิวตั้งต้นทันทีโดยไม่ต้องรอผู้ใช้สะสม แต่ก็**ควบคุมเนื้อหาไม่ได้เลย ขึ้นกับโควตาและข้อกำหนดการใช้งานของ Google** และมีต้นทุนต่อการเรียก API ที่ต้องเฝ้าระวังใน UC-19 เช่นเดียวกับ Serper/LLM
- **AI Chatbot (UC-08) ถูก gate ไว้หลัง Login เสมอ** และตอนนี้ครอบคลุมทั้งการตอบคำถามและการแนะนำโรงเรียนแบบจัดอันดับในที่เดียว ลดจำนวนหน้า/endpoint ที่ต้องสร้างลงจากเดิม
- **ทุก UI ในเอกสารนี้ต้องเป็น Responsive** (ตอบข้อ 5.1/8.2 ของแบบฟอร์ม คง.101) โดยเฉพาะ UC-01 (ค้นหา/กรอง + มุมมองแผนที่), UC-02 (หน้ารายละเอียดแบบหลายแท็บ), UC-03 (ตารางเปรียบเทียบ) ที่มี layout ซับซ้อนบนจอเล็ก — รายละเอียดแนวทาง Tailwind CSS + breakpoint ดู System Architecture หัวข้อ 9
- **ตัดฟีเจอร์ Notification/Saved Search ออกจากเฟสนี้** *(เดิมเคยใช้เลข UC-U09 ในเอกสารก่อน v6.2 ซึ่งต่อมาถูกใช้กับ Use Case ฟอรัมแทน และกลายเป็น UC-05 ใน v6.4 — ดูตาราง mapping หัวข้อ 2.4 ไม่ใช่ Use Case เดิมที่ถูกตัด)* — ถ้าอยากทำในอนาคต ตาราง `audit_log`/schema ที่มีอยู่ไม่กระทบ เพิ่มเป็นโมดูลใหม่ทีหลังได้โดยไม่ต้องรื้อของเดิม
- **หลังรวบใน v6.4 และตัดรีวิวออกใน v6.5 เหลือ 19 Use Case** (จาก 29 เดิม) โดย Must 14 / Should 3 / Could 2 — ตัวที่ตัดออกได้ก่อนถ้าเวลาไม่พอคือ UC-10 (Export/แชร์) และ UC-19 (Dashboard) ซึ่งเป็น Could ทั้งคู่ — ตัด UC-10 แล้ว UC-03 ข้อ 4 เหลือแค่ "บันทึกชุดเปรียบเทียบ" โดยไม่มีปุ่ม Export/แชร์ต่อ ซึ่งยังใช้งานได้ครบในตัว ส่วนตัด UC-19 ต้องย้ายการแจ้งเตือน Silent Failure ตาม UC-13 E7 ไปไว้ที่ UC-18 แทน มิฉะนั้นจะไม่มีใครเห็นว่า Scraper เงียบไป ส่วนเกณฑ์และคู่ที่พิจารณาแล้วตัดสินใจไม่รวบอยู่ในหัวข้อ 2.6
- Use Case ที่ทำเครื่องหมาย **Must** คือกลุ่มที่ควรทำให้เสร็จสมบูรณ์ก่อนสำหรับ demo/defend ส่วน **Should/Could** เป็นส่วนเสริมหากเวลาเหลือ
- แนะนำให้แต่ละ Exception Flow ในเอกสารนี้ถูกแปลงเป็น Test Case ของ QA โดยตรง (1 Exception Flow ≈ 1 Integration Test ขั้นต่ำ) — ทั้งเอกสารมี **120 Exception Flow** — 118 รายการอยู่ใน 19 Use Case (มากที่สุดที่ UC-02 จำนวน 13 รายการ) และอีก 2 รายการอยู่ในหัวข้อ 3.4 จึงเป็นฐานของชุด Integration Test อย่างน้อย 120 เคส — เป็นส่วนหนึ่งของแผนทดสอบเต็มที่ System Architecture หัวข้อ 13 (DevOps & QA Plan) ซึ่งครอบคลุม API/RLS/Security/Load Testing และ UAT เพิ่มเติมจากที่นี่ รวมถึง CI/CD Pipeline และ Centralized Logging/Error Tracking ที่ผูกกับ Correlation ID ในหัวข้อ 8.6 ด้านล่าง

### 7.3 การเก็บวันที่ 3 มิติแยกจากกัน: System Fetch, Source Published, Effective Period

ข้อมูลบางประเภท โดยเฉพาะค่าเทอม/ค่าใช้จ่าย มีมิติเวลาอยู่ **3 ชั้นที่ต้องแยกจากกันชัดเจน** (แก้ไข
จากเดิมที่เคยมี 2 มิติ เพิ่มมิติที่ 2 ด้านล่างเข้ามาใหม่ เพื่อตอบคำถาม "ต้นฉบับข้อมูลนี้เก่าแค่ไหน
กันแน่" ซึ่งมิติเดิม 2 อย่างตอบไม่ได้):

1. **System fetch timestamp** (เมื่อไหร่ที่**ระบบ**ไปดึง/ตรวจสอบข้อมูลนี้มา) — คือ
   `school_versions.created_at` (เปลี่ยนแปลงล่าสุด) และ `schools.last_verified_at` (ตรวจสอบ
   ล่าสุด แม้ไม่เปลี่ยน) — ตอบคำถาม "เราไปเช็คมาเมื่อไหร่"
2. **Source published/updated date** (เมื่อไหร่ที่**ต้นฉบับ** — เว็บไซต์/เอกสารของโรงเรียนเอง —
   ถูกเผยแพร่หรือแก้ไขล่าสุดตามที่ระบุไว้ในหน้านั้น เช่น footer "Last updated: March 2025" หรือ
   PDF metadata) — ตอบคำถาม **"ต้นฉบับเองเก่าแค่ไหน"** ซึ่งเป็นคนละเรื่องกับข้อ 1 โดยสิ้นเชิง:
   ระบบอาจ "เพิ่งไปเช็คเมื่อวานนี้" (system fetch = เมื่อวาน) แต่ตรวจเจอว่าหน้าเว็บของโรงเรียนเอง
   "ไม่เคยถูกแก้ไขมา 2 ปีแล้ว" (source published = 2 ปีก่อน) — สองตัวเลขนี้ต่างกันได้มาก และ
   เป็นสัญญาณคุณภาพข้อมูลที่ผู้ปกครองควรเห็น ไม่ใช่แค่ "ระบบเช็คล่าสุดเมื่อไหร่" อย่างเดียว
   **Nullable เสมอ** เพราะไม่ใช่ทุกหน้าเว็บ/เอกสารจะระบุวันที่แก้ไขไว้ — AI Scraper (UC-13)
   พยายามสกัดฟิลด์นี้เป็น best-effort เท่านั้น ไม่ error ถ้าหาไม่เจอ
3. **Effective date/period** (ข้อมูลนี้ใช้กับช่วงเวลาไหนในความเป็นจริง) — เช่น ค่าเทอมที่ Scrape
   มาในเดือนสิงหาคม 2568 อาจเป็นอัตราของ**ปีการศึกษา 2567** ที่โรงเรียนยังไม่อัปเดตเว็บ หรือเป็น
   อัตรา**ปีการศึกษา 2568** ที่เพิ่งประกาศใหม่ก็ได้ — ตอบคำถาม "ตัวเลขนี้ใช้กับปีไหน" คนละคำถาม
   กับข้อ 1-2 ทั้งคู่

**แนวทาง:** ฟิลด์ในกลุ่มค่าใช้จ่าย/ค่าเทอมภายใน `data_snapshot` เก็บทั้ง `source_published_at`
(มิติที่ 2) และ `academic_year` (มิติที่ 3) กำกับตัวเองในระดับฟิลด์ ไม่ใช่ระดับเวอร์ชัน เพราะแต่ละ
รายการค่าใช้จ่ายอาจอ้างอิงคนละต้นฉบับ/คนละปีกันได้ในเวอร์ชันเดียว (เช่น ค่าเทอมมาจากหน้าที่เพิ่ง
อัปเดตสัปดาห์นี้ แต่ค่ากิจกรรมมาจากหน้า PDF เก่าที่ไม่ได้แตะมา 1 ปีแล้ว) ตัวอย่างโครงสร้างภายใน
`data_snapshot.tuition`:

```json
{
  "tuition": {
    "amount": 250000,
    "currency": "THB",
    "academic_year": "2568",
    "source_published_at": "2025-03-15",
    "source_type": "scraper",
    "confidence_score": 0.82
  }
}
```

> **Source of truth ระหว่าง JSONB กับตาราง normalize (สำคัญ — เคลียร์ใน v6.3):** ตัวอย่าง JSON
> ข้างบนคือหน้าตาของ `data_snapshot` ซึ่งเป็น **provenance ดิบ** ที่เก็บ payload ตามที่ AI คืนมา
> ทั้งก้อนไว้ตรวจย้อนหลัง/rollback **ห้ามให้ระบบอ่านไปคำนวณหรือกรองโดยตรง** — ค่าที่ระบบใช้จริง
> (แสดงผล, กรองใน UC-01, คำนวณใน UC-07) ต้องอ่านจากตาราง **`version_fees`** (หัวข้อ 7.14) และ
> **`version_extra_fees`** (หัวข้อ 7.15) ซึ่ง normalize ออกมาแล้วเป็นคอลัมน์ `numeric` พร้อม
> `academic_year`/`source_published_at` กำกับรายแถว เหตุผลที่ต้องแยก 2 ชั้นแบบนี้: (1) ตัวเลขใน
> JSON เป็น float ปัดเศษพลาดได้ ผิดข้อกำหนด decimal-safe ของ UC-07 E4 (2) การกรองช่วงค่าเทอม
> ใน JSONB ช้าและเขียน query ยากกว่าคอลัมน์ปกติมาก — ทั้งสองชั้นถูกเขียนพร้อมกันใน transaction
> เดียวตอนบันทึกเวอร์ชัน จึงไม่มีความเสี่ยงว่าจะไม่ตรงกัน

ฝั่ง UI (UC-02, UC-07) ต้องแสดง **สูงสุด 3 บรรทัดแยกกัน** ไม่รวมเป็นประโยคเดียวเพราะสื่อความหมายคนละอย่าง: (1) "ค่าเทอมนี้เป็นของปีการศึกษา 2568" (effective period, มิติที่ 3) (2) "ตรวจสอบล่าสุดโดยระบบเมื่อ [system timestamp]" (system fetch, มิติที่ 1) (3) "ต้นฉบับอัปเดตล่าสุดเมื่อ [source_published_at]" (source published, มิติที่ 2) — **บรรทัดที่ 3 แสดงเฉพาะเมื่อ `source_published_at` ไม่ null เท่านั้น** (ซ่อนไปเลยถ้าไม่มี ไม่แสดง "ไม่ทราบ" ให้รก) และเมื่อบรรทัดที่ 3 ปรากฏพร้อมกับวันที่เก่ากว่าบรรทัดที่ 2 มาก (เช่น ต้นฉบับไม่ถูกแตะมา 1 ปีขึ้นไป) ให้ขึ้น badge เตือนสีเหลือง "ต้นฉบับอาจไม่อัปเดต" เพิ่มด้วย เพื่อเตือนผู้ปกครองว่าตัวเลขนี้แม้ระบบเพิ่งเช็คมา แต่ตัวโรงเรียนเองอาจยังไม่ได้แก้ไขมานานแล้ว

### 7.6 ตาราง `school_google_reviews` (schema `school_data`, **School Data Service**)

**ตารางนี้แทนที่ตาราง `reviews` เดิมใน v6.5:** เดิมชื่อ `reviews` อยู่ใน schema `community`
เก็บรีวิวที่ผู้ใช้เขียนเองพร้อมสถานะ Moderation — ตอนนี้เป็น **cache ชั่วคราวของรีวิวที่ดึงมาจาก
Google Places API** เพื่อลดจำนวนครั้งที่เรียก API และให้ยังแสดงผลได้ตอน Google ล่มหรือเกินโควตา (UC-02 E8)
**ไม่ใช่ source of truth** และไม่มีคอลัมน์ Moderation อีกต่อไปเพราะระบบไม่มีสิทธิ์คัดกรองเนื้อหาของ Google

**เหตุผลที่ย้ายมาอยู่ schema `school_data` ไม่ใช่ `community`:** `community` เป็นเจ้าของ*เนื้อหาที่ผู้ใช้ของเราสร้าง*
แต่ cache ชุดนี้เป็น*ข้อมูลเกี่ยวกับโรงเรียนที่ดึงมาจากภายนอก* ซึ่งเป็นความรับผิดชอบของ School Data Service
เช่นเดียวกับข้อมูลที่ Scraper เก็บมา การวางไว้ schema เดียวกับ `schools` ยังทำให้ sync `rating_avg`
กลับไปที่ `schools` เป็นการเขียนภายใน Service เดียว ไม่ต้องข้าม Service ให้ผิด Golden Rule

| Column | Type | หมายเหตุ |
|---|---|---|
| review_cache_id | UUID (PK) | |
| school_id | UUID | โรงเรียนที่ cache นี้เป็นของ |
| google_place_id | text | คัดลอกมาจาก `schools.google_place_id` ตอน fetch เพื่อให้ตรวจย้อนได้ว่า cache นี้มาจากสถานที่ใด |
| rating_avg, review_count | numeric(2,1), int | ค่าที่ Google คืนมา ณ เวลา fetch — sync กลับไปที่ `schools` เพื่อใช้เรียง/กรองใน UC-01 |
| payload | JSONB | รายการรีวิวที่ Google คืนมาทั้งชุด (ผู้เขียน, คะแนน, ข้อความ, เวลา, ลิงก์ต้นทาง) เก็บเป็นก้อนเพราะระบบไม่ query รายรีวิว แค่แสดงต่อ |
| attribution_url | text | ลิงก์กลับไปหน้าของโรงเรียนบน Google — **บังคับแสดงคู่กับรีวิวเสมอ** ตาม UC-02 Business Rule ข้อ 2 |

| expires_at | timestamp | เวลาหมดอายุของ cache — **ต้องไม่เกินระยะเวลาที่ข้อกำหนดการใช้งานของ Google อนุญาตให้เก็บ** เมื่อพ้นกำหนดต้องลบทิ้งแล้วดึงใหม่ ห้ามแสดงต่อ |

ทำให้ขั้นตอนลบบัญชีใน UC-06 E5 ไม่ต้องยุ่งกับตารางนี้เลย — และ schema `community`
เหลือเฉพาะเนื้อหาที่ผู้ใช้เขียนเองจริง ๆ คือฟอรัมและคำแจ้งข้อมูลผิดพลาด

### 7.16 ตาราง Lookup: หลักสูตรและระดับชั้น (schema `school_data`)

**เหตุผลที่ต้องมี:** ข้อมูลจริงจาก OPEC เก็บหลักสูตรเป็น **free-text array ภาษาไทยที่ไม่ normalize**
(เช่น `"หลักสูตรราชอาณาจักร"`, `"หลักสูตรประเทศสหรัฐอเมริกา"`, `"IB"`,
`"หลักสูตรจากระบบอังกฤษ (IGCSE and A-Level)"`, `"United State (Californian) Common Core"`)
และระดับชั้นเป็น array ไทย (`"อนุบาล"`, `"ประถมศึกษา"`, ...) — ถ้าไม่ map เป็นรหัสมาตรฐานก่อน
**ตัวกรอง "หลักสูตร" และ "ระดับชั้น" ของ UC-01 จะกรองไม่เจอโรงเรียนจำนวนมาก**

| ตาราง | Column หลัก | หน้าที่ |
|---|---|---|
| `curriculums` | `code` (PK), `name_th`, `name_en`, `sort_order`, `aliases text[]` | รหัสหลักสูตรมาตรฐาน `BRITISH` / `AMERICAN` / `IB` / … พร้อมข้อความดิบที่ต้อง map มาที่รหัสนี้ |
| `grade_levels` | `code` (PK), `name_th`, `name_en`, `sort_order`, `aliases text[]` | `PRE_K` / `KINDERGARTEN` / `PRIMARY` / `LOWER_SEC` / `UPPER_SEC` พร้อม alias แบบเดียวกัน |

**เหลือ 2 ตารางแทน 6 ตารางในแบบเดิม (v6.5):** แบบเดิมแยก `*_aliases` และ `school_*` ออกเป็นตารางต่างหาก
รวมเป็น 6 ตาราง ซึ่งไม่คุ้มกับสิ่งที่ได้ เพราะ (1) alias เป็นความสัมพันธ์ many-to-one ที่ไม่มี attribute อื่นเลย
เก็บเป็น `text[]` ในตาราง lookup เองได้โดยยังค้นด้วย GIN index ได้เหมือนกัน (2) ความสัมพันธ์
โรงเรียน↔หลักสูตร และ โรงเรียน↔ระดับชั้น เก็บเป็น `schools.curriculums text[]` และ
`schools.levels_offered text[]` พร้อม GIN index อยู่แล้ว การแตกเป็นตารางเชื่อมเพิ่มแค่ join
โดยไม่ได้ความสามารถใหม่ — ตัวกรองของ UC-01 ใช้ `curriculums && ARRAY[...]` ได้ตรง ๆ

**Business Rule:** ข้อความดิบที่ map ไม่ลงต้องไม่ถูกทิ้งเงียบ — ให้ตกลงรหัส `OTHER` และขึ้นรายงานใน

## 8. ข้อพิจารณาเชิงลึกสำหรับ Dev จริง (Concurrency & Security)

### 8.1 Authentication & Authorization

**Public-facing:** UC-01 ถึง UC-05 ไม่ต้อง auth เลย (ยกเว้นส่วนที่ต้องล็อกอินภายใน UC-03 และ UC-05) ส่วน UC-06 ถึง UC-10 ทุกตัวตรวจ JWT ผ่าน **Supabase Auth** โดยตรง — **Row Level Security (RLS)** ที่ระดับ table/schema ทำหน้าที่ authorization แทน API Gateway แบบเต็มรูป (ดู System Architecture หัวข้อ 1, 4)

**Anti-IDOR (สำคัญมากเพราะมีข้อมูลบุตรหลานที่เป็น PDPA):** ทุก resource ที่ผูกกับ user_id (children_profiles, favorites, saved comparisons, chat history) **ต้องมี RLS policy บังคับว่า resource นั้นเป็นของ user ที่ login อยู่จริงเสมอ** ไม่พึ่งพาการซ่อน ID ไว้ในหน้า UI — เช่น query `children_profiles` (schema `user_data`) ต้องมี policy ที่ filter ด้วย `user_id = auth.uid()` เสมอที่ระดับ database ไม่ใช่แค่ logic ฝั่ง Frontend มิฉะนั้นคนอื่นที่เดา/เปลี่ยน ID จะเห็นข้อมูลบุตรหลานของคนอื่นได้ผ่าน Auto-API โดยตรง

**ข้อยกเว้นเดียวที่ตั้งใจ — ลิงก์แชร์ผลเปรียบเทียบ (UC-10):** `comparison_sets` เข้าถึงได้แบบ anonymous ผ่าน `get-shared-comparison` เมื่อมี `share_token` ที่ถูกต้องเท่านั้น — นี่**ไม่ใช่** IDOR เพราะ (1) เป็นการเปิดให้เข้าถึงโดยเจตนาของเจ้าของเอง ไม่ใช่ช่องโหว่ที่เจ้าของไม่รู้ตัว (2) `share_token` สุ่มแบบคาดเดาไม่ได้ ต่างจาก sequential ID ที่ไล่เดาได้ (3) resource ที่ expose ผ่าน token ถูกจำกัดเฉพาะ field ที่จำเป็นต่อการแสดงผลเท่านั้น (`name` ของชุด + รายละเอียดโรงเรียนที่ resolve จาก `school_ids` ผ่าน `school-data-api` แล้ว) **ไม่มี `user_id`/`comparison_id`/`share_token` เองปรากฏออกไปในเลย** — ทำผ่าน Edge Function (`get-shared-comparison`) ที่ใช้ Service Role bypass RLS อย่างตั้งใจและควบคุม field ที่คืนเองในโค้ด ไม่ใช่เปิด RLS policy กว้าง ๆ ให้ query ตรงผ่าน Auto-API ซึ่งเสี่ยงหลุด column อื่นออกไปด้วยโดยไม่ตั้งใจ

**Service-to-service (Internal):** ระบบแบ่งเป็น 5 Service ตาม schema จริง (School Data, Community, User, AI, Ops — ดู System Architecture หัวข้อ 4) การเรียกข้าม Service (เช่น Chatbot → `school-data-api`, Re-embed handler → `school-data-api`) ต้องผ่าน **Internal Service Secret** (custom header ที่รู้กันเฉพาะฝั่ง Edge Function) ร่วมกับ **forward JWT ของ user ต้นทาง** เพื่อให้ Service ปลายทางยังตรวจสิทธิ์ตาม user จริง ไม่ใช้ Service Role Key ข้ามสิทธิ์เต็มรูปแบบ (รายละเอียดดู System Architecture หัวข้อ 4.4) — เลือกใช้ shared secret แทน mTLS ของจริงเพราะทีมเล็กไม่มี certificate infra แต่ยังพิสูจน์ตัวตนระหว่าง service ได้

**ฟอรัม (UC-05 ฝั่งผู้ใช้ และ UC-16 ฝั่ง Admin):** `forum_posts`/`forum_comments` อ่านแบบ anonymous ได้เฉพาะแถวที่ `status = 'approved'` ส่วนการเขียน/แก้/ลบ ต้องมี policy บังคับ `user_id = auth.uid()` เสมอ (เจ้าของแก้ได้เฉพาะของตัวเอง) และ `forum_reports` ต้องไม่เปิดให้ผู้ใช้ทั่วไป select เห็นว่าใครรายงานใคร — อ่านได้เฉพาะ Admin เท่านั้น

**Admin routes:** แยกฝั่ง Frontend เป็นแอปคนละตัว (Admin Dashboard) และบังคับด้วย RLS policy ที่เช็ค role admin จาก JWT claim ที่ระดับ table เสมอ ไม่ใช่แค่ซ่อนปุ่มฝั่ง Frontend

### 8.2 Scraper Concurrency: ป้องกัน Job ซ้อนกันต่อโรงเรียนเดียวกัน

**ปัญหา:** ถ้า Scheduled Job รอบใหม่เริ่มก่อนที่ Job รอบเก่าของโรงเรียนเดียวกันรันเสร็จ (เช่น เว็บโรงเรียนโหลดช้ามาก) จะเกิด 2 Job ทำงานพร้อมกันบนโรงเรียนเดียวกัน เสี่ยงสร้าง Pending Review ซ้ำหรือชน Optimistic Locking โดยไม่จำเป็น

**แนวทาง:** ระบบนี้ไม่มี Redis แยก (ทุก Service ยังอยู่ Postgres instance เดียวกัน ไม่ใช่ all-in-one แบบไม่แยก Service — ดู System Architecture หัวข้อ 4-5) จึงใช้ **Postgres Advisory Lock** แทน Redis `SETNX` — ก่อนเริ่ม Job เรียก `pg_try_advisory_lock(hashtext(school_id))` ถ้าล็อกไม่สำเร็จ (มี Job อื่นถืออยู่) ให้ข้าม Job รอบนี้ไปทำรอบถัดไปแทนการรอ/รันซ้อน ข้อดีคือไม่ต้องตั้ง TTL เองเหมือน Redis เพราะ Advisory Lock ผูกกับ session/connection ของ Postgres โดยตรง — ถ้า Worker ที่ถือ Lock crash กลางทาง connection หลุดแล้ว Postgres ปลด Lock ให้อัตโนมัติทันที ไม่ต้องรอหมดอายุเหมือน TTL — Concurrency ระหว่างคนละโรงเรียนไม่มีปัญหา เพราะคนละ Lock key กัน รันขนานได้เต็มที่ตาม Worker Pool ที่มี

### 8.3 Indirect Prompt Injection ผ่านข้อมูลที่ Scrape มา

ต่างจาก Prompt Injection ที่ผู้ใช้พิมพ์เองใน UC-08 (E4) — นี่คือกรณีที่**เนื้อหาบนเว็บไซต์โรงเรียนเอง**มีข้อความพยายามสั่งการ LLM (เว็บถูกแฮ็กแล้วแทรกข้อความสั่งการ) เพราะข้อมูลที่ Scrape มาจะถูก inject เข้า Prompt ของ UC-08 โดยตรงตอนตอบคำถาม/แนะนำโรงเรียน (ผ่านผลลัพธ์ที่ tool call คืนมา) — เป็นช่องโหว่แยกจาก Sanitization กัน XSS ใน UC-13 (E6) เพราะ HTML sanitizer กรองแค่ script tag ไม่ได้กรองข้อความสั่งการที่เป็น plain text

**แนวทาง:** ข้อมูลที่ Retrieve มาจาก `school-data-api` ของ School Data Service ผ่าน tool call (`search_schools`, `get_school_details`, `compare_schools`) ต้องใส่ใน Prompt ในฐานะ "ข้อมูลอ้างอิง" ที่แยกชั้นจาก System Instruction เสมอ (หลักการเดียวกับที่แยกจาก User Input ใน E4) และผ่าน Output Filter เดียวกันก่อนตอบกลับ — apply กับทุกแหล่งข้อมูลภายนอกที่เข้าสู่ Prompt ไม่ใช่แค่ข้อความจากผู้ใช้

### 8.4 Idempotent Consumers สำหรับ Event-Driven Sync ข้าม Service

Pattern "Database Webhook → Edge Function" ในหัวข้อ 4 เป็น At-least-once Delivery (retry แบบ exponential backoff) หมายความว่า **`re-embed-handler` ของ AI Service มีโอกาสถูกเรียกซ้ำมากกว่า 1 ครั้ง** สำหรับ publish event เดียวกัน (เช่น เรียก `school-data-api` ข้าม Service สำเร็จแต่ตัว handler เอง timeout ก่อนบันทึกผล ระบบจึง retry ทั้ง flow ใหม่) จึงต้องออกแบบให้ Apply ซ้ำได้ผลลัพธ์เหมือนเดิม (Idempotent) เช่น ใช้ `version_id` เป็น Key ในการ **Upsert** ค่า embedding ลง `ai.school_embeddings` แทน Insert ตรง ๆ ไม่เช่นนั้นอาจมี embedding ซ้ำหลายแถวสำหรับเวอร์ชันเดียวกัน

### 8.5 Transaction Boundary ตอน Publish

ตอน Approve (UC-14) หรือ CRUD ตรง (UC-11) การอัปเดต `schools.current_published_version_id` กับการเปลี่ยน status ของแถวใน `school_versions` เป็น published **ต้องอยู่ใน Database Transaction เดียวกัน** ถ้าแยกเป็น 2 Query โดยไม่มี Transaction ครอบแล้วระบบ crash ระหว่างกลาง อาจเกิดสถานะไม่ตรงกัน (version บอก published แต่ schools ยังชี้เวอร์ชันเก่า หรือกลับกัน)

### 8.6 Observability: Correlation ID

แม้ระบบนี้ไม่ใช่ true Microservices เต็มรูป (ยังอยู่ Postgres instance เดียว — ดู System Architecture หัวข้อ 4.6) แต่ตอนนี้มีการเรียกข้าม **5 Service จริง** ทาง HTTP (Edge Function เรียก Edge Function) เช่น Scraper (School Data Service) → Pending Review → Approve → Database Webhook → `re-embed-handler` (AI Service) → เรียกกลับ `school-data-api` (School Data Service) หรือ Chatbot (AI Service) → `school-data-api` + `user-data-api` (School Data/User Service) หรือ `get-shared-comparison` (User Service) → `school-data-api` (School Data Service) ตอน Guest เปิดลิงก์แชร์ (UC-10) การ Debug ตอนมีปัญหาจริงจะยากมากถ้าไม่มีทางเชื่อมโยง Log ข้าม Service — ทุก Request/Event ควรพก Correlation ID เดียวกันตั้งแต่ต้นจนจบ Flow ผ่าน header (เช่น `X-Correlation-Id`) ทุกครั้งที่ Edge Function หนึ่งเรียกอีก Edge Function หนึ่ง (รวมถึงตอนถูกเรียกโดย Guest ที่ไม่มี JWT ก็ยังต้องมี Correlation ID เสมอ) แล้วใส่ใน Log ทุก Service (รวม `school_scrape_log`) เพื่อ trace ปัญหาข้าม Service ได้โดยไม่ต้องไล่ Log ทีละ Service แยกกัน
