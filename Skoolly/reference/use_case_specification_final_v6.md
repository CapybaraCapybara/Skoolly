# เอกสารข้อกำหนด Use Case (Use Case Specification) — v6 (ฉบับปรับตาม Wireframe)
## ระบบ AI แนะนำโรงเรียนนานาชาติสำหรับผู้ปกครองในประเทศไทย

**หมายเหตุเรื่องเลขเวอร์ชัน:** เดิมเอกสารนี้ใช้เลข "(v2)" ตาม Wireframe/Scope revision (ดู bullet ด้านล่าง) ซึ่งเป็น
คนละชุดเลขกับ System Architecture doc — ตั้งแต่รอบนี้จึงปรับหัวเอกสารมาใช้เลขเดียวกันคือ **v6** (ปรับให้สอดคล้องกับสถาปัตยกรรม
Microservices แบบ Schema-per-Service ตามแบบฟอร์ม คง.101, เพิ่ม DevOps & QA Plan ตอบข้อ 7.5-7.6
ของฟอร์ม, และเพิ่ม 3 ฟีเจอร์ใหม่: Guided Prompts, source_published_at, ลิงก์แชร์ผลเปรียบเทียบ) —
เอกสารนี้ถูกแก้ไขให้สอดคล้องกับ System Architecture v6 ล่าสุดแล้วทุกจุด และใช้เลขเวอร์ชันตรงกันแล้ว

**เอกสารฉบับนี้ปรับให้ตรงกับรายการความสามารถของแต่ละ Actor ตามภาพที่ให้มา บวกการปรับ scope รอบล่าสุด:**
- **Guest ไม่มีสิทธิ์ใช้ AI Chatbot อีกต่อไป** — ต้องสมัครสมาชิกก่อนเสมอ
- **เครื่องคำนวณค่าใช้จ่าย (เดิม UC-G03) ตัดออกจาก Guest เช่นกัน** — ต้องล็อกอินเป็นสมาชิกเท่านั้นถึงจะใช้ได้
- **ตัด "รับคำแนะนำโรงเรียนแบบ Personalized จาก AI" ออกเป็น Use Case แยก** — รวมความสามารถนี้เข้ากับ AI Chatbot แทน เพราะเป็นความสามารถเดียวกันในมุมมองผู้ใช้ (ขอคำแนะนำผ่านการแชทได้โดยตรง)
- **ตัด "ตั้งค่าการแจ้งเตือน/บันทึกเงื่อนไขค้นหา" ออก** — ยังไม่ทำในเฟสนี้
- **รวม "จัดการบัญชี" เข้ากับ "จัดการโปรไฟล์บุตรหลาน" เป็น Use Case เดียว** เพราะเป็นหน้าตั้งค่าส่วนตัวเหมือนกัน
- **Admin ตัด "จัดการสิทธิ์ผู้ใช้งาน/Role" ออก** — ระบบมีบทบาท Admin แบบเดียว
- **UC-A02 ระบุแหล่งข้อมูลชัดเจน:** ดึงรายชื่อจาก **OPEC** และหา URL เว็บไซต์ทางการด้วย **Serper API**
- ทุก Use Case เขียนเป็นแบบเต็มรูปแบบ (Main Flow / Exception Flow / Postcondition / Business Rule)
- **(v6) UC-U05 เพิ่ม Guided Prompts/Quick Replies** — ปุ่มคำถามนำทางตอนเริ่มแชท + คำถามต่อยอดท้ายทุกคำตอบ
- **(v6) เพิ่ม `source_published_at`** เป็นมิติเวลาที่ 2 (จากทั้งหมด 3 มิติ) ในหัวข้อ 7.3 แทรกระหว่าง system fetch timestamp กับ effective period เดิม

## 1. Actor ทั้งหมดในระบบ

| Actor | ประเภท | คำอธิบาย |
|---|---|---|
| **Guest** | Primary (Human) | ผู้เยี่ยมชมที่ยังไม่ได้ล็อกอิน เข้าถึงข้อมูลสาธารณะและเครื่องมือพื้นฐานได้ รวมถึง**อ่าน**กระทู้ในฟอรัม (UC-G08) **ยกเว้น AI Chatbot, เครื่องคำนวณค่าใช้จ่าย และการเขียน/กดถูกใจ/รายงานในฟอรัม ซึ่งต้องล็อกอินเสมอ** |
| **Parent / User** | Primary (Human) | ผู้ปกครองที่สมัครสมาชิกแล้ว มีโปรไฟล์บุตรหลาน ใช้ฟีเจอร์ AI แบบเต็มรูปแบบ |
| **Admin** | Primary (Human) | ผู้ดูแลระบบ มีสิทธิ์สูงสุดและรับผิดชอบความถูกต้องของข้อมูล**ทุกโรงเรียน**แต่เพียงผู้เดียว ระบบมีบทบาท Admin แบบเดียว ไม่แบ่งระดับสิทธิ์ย่อย |
| **AI/LLM Recommendation Engine** | Supporting (System) | ระบบภายในที่ถูกเรียกใช้โดย Parent/User เท่านั้น (Guest เข้าถึงไม่ได้) ครอบคลุมทั้งการตอบคำถามและการแนะนำโรงเรียนแบบจัดอันดับ — implement เป็น **AI Service** (schema `ai` + Edge Function `chatbot-api`/`re-embed-handler`) ในสถาปัตยกรรม v6 |
| **Scraper/Crawler Service** | Supporting (System) | ระบบเก็บข้อมูลอัตโนมัติจากเว็บไซต์/เพจโรงเรียน เป็นกลไกหลักที่ทำให้ข้อมูลเป็นปัจจุบันโดยไม่ต้องมีใครติดต่อเข้ามา — เป็นส่วนหนึ่งของ **School Data Service** (schema `school_data`) ไม่ใช่ Service แยกต่างหาก เพราะเป็นเจ้าของข้อมูลชุดเดียวกัน |
| **Notification Service** | Supporting (System) | ส่งอีเมลเป็นผลลัพธ์ข้างเคียงของ Use Case อื่น (เช่น ยืนยันอีเมล, สถานะ Ticket, PDF พร้อมดาวน์โหลด) — เฟสนี้ implement ผ่าน Resend เฉพาะช่องทางอีเมลเท่านั้น ยังไม่มี push notification จริง (เผื่อ scope ในอนาคต) — เป็นส่วนหนึ่งของ **Ops Service** |

**ความสัมพันธ์ระหว่าง Actor:** Parent/User เป็น generalization ของ Guest แต่**ไม่ได้สืบทอดสิทธิ์ AI Chatbot และเครื่องคำนวณค่าใช้จ่ายมาด้วย** เพราะทั้งสองเป็นสิทธิ์ที่เพิ่มเข้ามาเฉพาะตอนสมัครสมาชิกเท่านั้น ไม่ใช่สิทธิ์พื้นฐานของ Guest ส่วน Admin คือผู้รับผิดชอบข้อมูลทั้งหมด โดยมี Scraper Service เป็นผู้ช่วยอัตโนมัติที่ทำงานภายใต้การกำกับของ Admin เสมอ

## 3. รายละเอียด Use Case แบบเต็มรูปแบบ

> โครงสร้าง: Actor / คำอธิบาย / Precondition / Main Flow / **Exception Flow** / Postcondition / Business Rule

## 3.1 กลุ่ม Guest

### UC-G01: ค้นหา/กรองรายชื่อโรงเรียน

**Actor หลัก:** Guest, Parent/User
**คำอธิบาย:** ค้นหาโรงเรียนโดยกรองตามหลักสูตร (British/American/IB/Singapore ฯลฯ), ระดับชั้น, ช่วงค่าเทอม, พื้นที่/ระยะทาง, ภาษาที่สอน
**Precondition:** ไม่มี

**Main Flow**
1. ผู้ใช้เข้าหน้า "ค้นหาโรงเรียน" ระบบแสดงรายชื่อเริ่มต้นเรียงตามความนิยม/ระยะทางโดยประมาณ พร้อม pagination
2. ผู้ใช้เลือกตัวกรองและ/หรือพิมพ์คำค้น
3. Frontend เรียก Auto-API ของ **School Data Service** ตรง (schema `school_data`, RLS ทำหน้าที่แทน API Gateway — client เรียก public API ของ service เองได้ ไม่ผิด Golden Rule ดู System Architecture หัวข้อ 4.2) ค้นด้วย Postgres full-text search บนตาราง `schools`/`school_versions` ตัวเดียวกับข้อมูลจริง ไม่มี Search Index แยกที่ต้อง sync
4. ระบบ query ตามเงื่อนไข พร้อม sort/pagination แล้วแสดงผลลัพธ์แบบย่อ (ชื่อ, รูปปก, ค่าเทอมเริ่มต้น, คะแนนรีวิว, ระยะทาง)

**Exception Flow**
- **E1 — School Data Service (Supabase/Postgres) ตอบช้าหรือ timeout:** ฝั่ง Frontend ใช้ SWR/TanStack Query แบบ stale-while-revalidate เสิร์ฟผลลัพธ์จาก Cache ล่าสุดพร้อม badge "ผลลัพธ์อาจไม่เป็นปัจจุบัน" แทนการแสดง error 500 (Circuit Breaker ในระบบนี้ครอบคลุมทั้ง External API อย่าง Maps/Serper/LLM และการเรียกข้าม Service ภายใน เช่น Chatbot → School Data Service — ดู System Architecture หัวข้อ 4.5)
- **E2 — ไม่พบผลลัพธ์:** แสดงข้อความแจ้งพร้อมข้อเสนอแนะให้ลดเงื่อนไข หรือแสดงโรงเรียนใกล้เคียงเงื่อนไขที่สุด
- **E3 — พารามิเตอร์ไม่ถูกต้อง:** validate ทั้ง Frontend และ Backend ก่อนยิง query จริง
- **E4 — (ไม่เกิดขึ้นในสถาปัตยกรรมนี้) ไม่มี Search Index แยกให้ไม่ sync:** full-text search อ่านจากตารางเดียวกับข้อมูลโรงเรียนโดยตรง (ดู System Architecture หัวข้อ 4) ความเสี่ยงที่เหลืออยู่จริงมีแค่ Client เห็น Cache เก่าจาก SWR ก่อน revalidate ซึ่งครอบคลุมแล้วใน E1

**Postcondition:** ผู้ใช้เห็นรายชื่อโรงเรียนตรงเงื่อนไข
**Business Rule:** แสดงเฉพาะโรงเรียนที่เผยแพร่แล้วเท่านั้น — ในระดับ Database คือ `schools.status = active` **และ** `schools.current_published_version_id IS NOT NULL` (โรงเรียนที่เพิ่ง import จาก Phase 1 จะเป็น `active` แต่ยังไม่มีเวอร์ชัน published จึงยังไม่ขึ้นแสดง ดูหัวข้อ 5 และ System Architecture หัวข้อ 3)

### UC-G02: ดูรายละเอียดโรงเรียน

**Actor หลัก:** Guest, Parent/User
**คำอธิบาย:** แสดงข้อมูลเต็มของโรงเรียน 1 แห่ง แบ่งเป็นแท็บ: ภาพรวม, หลักสูตร, สิ่งอำนวยความสะดวก, **ความปลอดภัย** (มาตรการ รปภ./CCTV/ห้องพยาบาล/ระบบกรอง PM2.5/การควบคุมบุคคลภายนอก และนโยบายคุ้มครองเด็ก — สกัดโดย Scraper ตาม UC-A03 เก็บในตาราง 7.10), แผนที่ (UC-G03), รีวิว (UC-G04) — ส่วนแท็บ "คำนวณค่าใช้จ่าย" จะแสดงให้เห็นว่ามีอยู่ แต่ต้องล็อกอินก่อนถึงจะใช้งานได้จริง (ดู UC-U04)

**Main Flow**
1. ผู้ใช้กดเข้าจากผลค้นหา หรือเข้าตรงผ่าน URL/slug
2. Frontend ยิง request ไปยัง Auto-API ของ **School Data Service** (schema `school_data`) ด้วย school_id
3. ระบบดึงข้อมูลของเวอร์ชันที่ `schools.current_published_version_id` ชี้อยู่ แล้ว render หน้ารายละเอียด (cache อยู่ฝั่ง Client ด้วย SWR — ระบบนี้ไม่มี Read Replica แยก ทุก read ยิงที่ Postgres instance เดียวกัน ดู System Architecture หัวข้อ 4.6)

**Exception Flow**
- **E1 — school_id ไม่ถูกต้องหรือไม่เคยมีอยู่ในระบบ:** แสดงหน้า 404 ที่เป็นมิตร พร้อมแนะนำโรงเรียนใกล้เคียง
- **E1b — โรงเรียนมีสถานะ Archived (ปิดกิจการ/เลิกให้บริการ):** ไม่ขึ้น 404 แต่ยังแสดงหน้ารายละเอียดแบบอ่านอย่างเดียว พร้อม banner ชัดเจนว่า "โรงเรียนนี้ปิดกิจการแล้ว/ไม่พร้อมให้บริการ" เพื่อให้ลิงก์จาก UC-U02 (รายการโปรด), UC-U03 (เปรียบเทียบ), UC-G04 (รีวิว) ยังเปิดดูได้โดยไม่พังเป็น dead link
- **E2 — บางฟิลด์เป็นค่าว่าง** (Scraper ยังหาไม่เจอ): แสดง placeholder แบบ graceful degradation
- **E2b — ไม่พบข้อมูลความปลอดภัยของโรงเรียนนี้เลย** (`version_safety` ไม่มีแถว หรือทุกฟิลด์เป็น null): **ซ่อนแท็บ "ความปลอดภัย" ไปเลย** ห้ามแสดงเป็น "ไม่มี" หรือ "ไม่ผ่าน" เด็ดขาด เพราะ "ระบบหาไม่เจอ" กับ "โรงเรียนไม่มีมาตรการ" เป็นคนละเรื่องกัน และการสื่อผิดตรงนี้กระทบชื่อเสียงโรงเรียนโดยตรง
- **E3 — School Data Service (Supabase) ล่ม/ช้าผิดปกติ:** เสิร์ฟจาก cache (SWR) พร้อม timestamp อัปเดตล่าสุด หากไม่มี cache แสดงหน้า maintenance พร้อมปุ่ม retry
- **E4 — Admin แก้ไขข้อมูลระหว่างที่ผู้ใช้กำลังดูอยู่ (race condition):** ไม่ error ผู้ใช้เห็นข้อมูลชุดที่โหลดไว้จนกว่าจะ refresh เอง
- **E5 — Guest กดแท็บ "คำนวณค่าใช้จ่าย":** แสดง prompt ให้สมัครสมาชิก/ล็อกอินก่อน แทนการซ่อนแท็บไปเลย (โชว์ว่ามีฟีเจอร์นี้อยู่เพื่อจูงใจให้สมัครสมาชิก)

**Postcondition:** ผู้ใช้เห็นข้อมูลเต็มของโรงเรียนที่เลือก พร้อมวันที่กำกับครบตามหัวข้อ 7.3 — ไม่มีการเปลี่ยนแปลงข้อมูลใดๆ ในระบบ (read-only)
**Business Rule:** ทุกหน้าต้องแยกวันที่ตามมิติเวลาในหัวข้อ 7.3 เสมอ ห้ามรวมเป็นประโยคเดียว: (1) "ข้อมูลเปลี่ยนแปลงล่าสุดเมื่อ [วันที่]" (จาก school_versions ปัจจุบัน) (2) "ระบบตรวจสอบล่าสุดเมื่อ [วันที่]" (จาก schools.last_verified_at ซึ่งอาจใหม่กว่าถ้าตรวจแล้วไม่พบการเปลี่ยนแปลง) และ (3) เฉพาะฟิลด์กลุ่มค่าใช้จ่ายที่มี `source_published_at` ไม่เป็น null ให้แสดง "ต้นฉบับอัปเดตล่าสุดเมื่อ [วันที่]" เพิ่มอีกบรรทัด (ซ่อนไปเลยถ้าเป็น null) — รวมสูงสุด 3 บรรทัดตามหัวข้อ 7.3

### UC-G03: ดูตำแหน่งโรงเรียนบนแผนที่

**Actor หลัก:** Guest, Parent/User

**Main Flow**
1. ผู้ใช้กดแท็บ "แผนที่" ในหน้ารายละเอียด หรือดูภาพรวมหลายโรงเรียนจากหน้าค้นหา (map view)
2. ระบบวาดแผนที่ด้วย Leaflet + tile provider (Mapbox/OSM) จากพิกัดที่เก็บใน PostGIS ของเราเอง แสดงหมุดตำแหน่งพร้อมข้อมูลย่อ และระยะทางจากตำแหน่งผู้ใช้ (ถ้าอนุญาต location) — คนละตัวกับ Google Maps API ที่ใช้เติมพิกัดตอน Enrichment ใน UC-A02 (ดู System Architecture หัวข้อ 2, 9)

**Exception Flow**
- **E1 — แผนที่/tile provider ไม่ตอบสนอง/timeout:** fallback เป็นมุมมองรายการ (list view) แสดงที่อยู่เป็นข้อความแทน
- **E2 — ผู้ใช้ไม่อนุญาต location permission:** แสดงแผนที่โดยไม่คำนวณระยะทาง แทนการฟ้อง error
- **E3 — พิกัดโรงเรียนไม่ถูกต้อง/ไม่มี** (Scraper หาที่อยู่ไม่เจอ): ไม่แสดงหมุดสำหรับโรงเรียนนั้น แต่ยังแสดงในมุมมองรายการได้ปกติ
- **E4 — tile provider ของแผนที่มี quota จำกัด:** ตั้ง rate limit ต่อ session (debounce ตอน pan/zoom)

**Postcondition:** ผู้ใช้เห็นตำแหน่งโรงเรียนบนแผนที่ หรือเห็น list view แทนถ้าแผนที่ใช้งานไม่ได้ — ไม่มีการเปลี่ยนแปลงข้อมูลในระบบ
**Business Rule:** ต้องมี fallback แบบ list view เสมอ ห้ามให้ทั้งหน้าใช้งานไม่ได้เพราะแผนที่โหลดไม่ขึ้น

### UC-G04: ดูรีวิวโรงเรียน

**Actor หลัก:** Guest, Parent/User
**คำอธิบาย:** อ่านรีวิว/คะแนนจากผู้ปกครองคนอื่นที่ผ่านการตรวจสอบแล้ว (มาจาก UC-U06 → UC-A06)

**Main Flow**
1. ผู้ใช้กดแท็บ "รีวิว" ในหน้ารายละเอียดโรงเรียน
2. ระบบแสดงคะแนนเฉลี่ยรวม + รายการรีวิวที่ Approve แล้ว เรียงตามล่าสุด/เป็นประโยชน์ที่สุด พร้อม pagination

**Exception Flow**
- **E1 — โรงเรียนยังไม่มีรีวิว:** แสดง "ยังไม่มีรีวิวสำหรับโรงเรียนนี้" พร้อมชวนผู้ใช้ที่ล็อกอินให้เป็นคนแรก
- **E2 — รีวิวถูกลบโดย Admin ระหว่างหน้ากำลังแสดงอยู่:** ไม่ error แค่ไม่ปรากฏในการโหลดครั้งถัดไป
- **E3 — Community Service (ตาราง `reviews` schema `community`) ช้า/ล่ม:** เสิร์ฟจาก cache หรือซ่อนเฉพาะแท็บนี้ชั่วคราว ไม่กระทบแท็บอื่นของหน้ารายละเอียด (แท็บอื่นเรียก School Data Service คนละ schema กัน จึงไม่กระทบกัน)

**Postcondition:** ผู้ใช้เห็นเฉพาะรีวิวสถานะ Approved พร้อมคะแนนเฉลี่ย — ไม่มีการเปลี่ยนแปลงข้อมูลในระบบ
**Business Rule:** แสดงเฉพาะรีวิวสถานะ Approved เท่านั้น ตาม UC-A06

### UC-G05: เปรียบเทียบโรงเรียนเบื้องต้น

**Actor หลัก:** Guest, Parent/User (สืบทอด)
**คำอธิบาย:** เลือกโรงเรียนสูงสุด N แห่งมาเทียบข้อมูลหลักแบบเคียงข้างกัน ไม่ต้องล็อกอิน ไม่บันทึกผล จำกัดจำนวนครั้ง/จำนวนโรงเรียนต่อ session

**Main Flow**
1. ผู้ใช้เลือกโรงเรียนจากผลค้นหาหรือหน้ารายละเอียด กด "เพิ่มเข้าเปรียบเทียบ"
2. ระบบเก็บรายการชั่วคราวไว้ใน session/local state (ไม่บันทึกลง DB)
3. เมื่อเลือกครบ ผู้ใช้กด "เปรียบเทียบ" ระบบแสดงตารางเทียบฟิลด์หลัก (ค่าเทอม, หลักสูตร, ระยะทาง, คะแนนรีวิว)

**Exception Flow**
- **E1 — เลือกเกินจำนวนที่กำหนด:** ปุ่ม "เพิ่ม" ถูก disable พร้อมข้อความแจ้ง limit
- **E2 — เกิน rate limit การเปรียบเทียบต่อ session:** แจ้งให้ล็อกอินเพื่อใช้ UC-U03 แทนซึ่งไม่มี limit นี้
- **E3 — โรงเรียนที่เลือกไว้ถูกลบ/archive ระหว่างเปรียบเทียบ:** ตัดออกจากตารางพร้อมแจ้งเตือน ไม่ทำให้ทั้งตารางพัง

**Postcondition:** ตารางเปรียบเทียบแสดงชั่วคราว หายเมื่อปิดหน้า/session หมดอายุ
**Business Rule:** ข้อมูลเปรียบเทียบของ Guest ไม่ถูกบันทึกถาวร ต้องล็อกอินก่อนถึงจะบันทึก/ดูย้อนหลังได้

### UC-G06: สมัครสมาชิก / เข้าสู่ระบบ

**Actor หลัก:** Guest

**Main Flow**
1. ผู้ใช้กด "สมัครสมาชิก" กรอกอีเมล+รหัสผ่าน หรือเลือก Social Login
2. ระบบส่งอีเมลยืนยัน ผู้ใช้กดลิงก์ยืนยันเพื่อเปิดใช้งานบัญชี
3. เข้าสู่ระบบด้วยอีเมล/รหัสผ่าน หรือ Social Login ที่ยืนยันแล้ว

**Exception Flow**
- **E1 — อีเมลซ้ำกับบัญชีที่มีอยู่แล้ว:** แจ้งให้ไปหน้า Login หรือ "ลืมรหัสผ่าน" แทนการสร้างซ้ำ
- **E2 — ลิงก์ยืนยันอีเมลหมดอายุ:** ขอส่งลิงก์ใหม่ได้ ไม่ต้องกรอกฟอร์มสมัครใหม่ทั้งหมด
- **E3 — กรอกรหัสผ่านผิดหลายครั้งติดกัน:** Rate limit ป้องกัน brute-force (lock ชั่วคราวหลังผิดครบจำนวนที่กำหนด)
- **E4 — Social Login provider ล่ม/timeout:** fallback ให้เลือกวิธีอื่น (อีเมล/รหัสผ่าน) แทน ไม่ค้างหน้าโหลด

**Postcondition:** มีบัญชีที่ยืนยันแล้ว และ session ล็อกอินที่ใช้งานฟีเจอร์ของ Parent/User ได้
**Business Rule:** ต้องยืนยันอีเมลก่อนใช้ฟีเจอร์ที่ต้องพึ่ง identity เช่น เขียนรีวิว/บันทึกโปรไฟล์บุตรหลาน/ใช้ AI Chatbot/เครื่องคำนวณค่าใช้จ่าย

### UC-G07: ดูหน้าเปรียบเทียบที่ถูกแชร์ (ผ่านลิงก์)

**Actor หลัก:** Guest (ไม่ต้องมีบัญชี/ไม่ต้องล็อกอิน แม้เป็นสมาชิกที่ล็อกอินอยู่ก็เปิดดูได้เหมือนกัน)
**คำอธิบาย:** เปิดลิงก์ที่ Parent/User คนอื่นแชร์มาจาก UC-U08 เพื่อดูตารางเปรียบเทียบแบบ read-only โดยไม่ต้องสมัครสมาชิก — เป็นทางเข้าใหม่ของ Guest ที่มาจากนอกระบบ (แชร์ต่อใน LINE/โซเชียลมีเดีย) ไม่ใช่จากการเรียกดูภายในเว็บ

**Main Flow**
1. ผู้ใช้เปิดลิงก์ที่มี `share_token` ต่อท้าย URL
2. Frontend เรียก `get-shared-comparison` (Edge Function ของ **User Service**) ด้วย token — ตรวจสอบว่า token ยังใช้งานได้ (`share_enabled = true` และชุดเปรียบเทียบยังไม่ถูกลบ)
3. `get-shared-comparison` เรียกข้ามไปยัง `school-data-api` ของ **School Data Service** เพื่อดึงรายละเอียด**ล่าสุด**ของโรงเรียนทุกแห่งใน `school_ids` (ไม่ใช่ snapshot ตอนแชร์ — ต่างจาก PDF Export ใน UC-U08 โดยตั้งใจ เพราะลิงก์ควรมีประโยชน์ระยะยาว ให้ผู้รับเห็นข้อมูลล่าสุดเสมอแม้เปิดลิงก์ทีหลังผ่านไปหลายเดือน) ประกอบเป็น response เดียวส่งกลับ
4. แสดงตารางเปรียบเทียบแบบ read-only — ไม่มีปุ่มแก้ไข/บันทึกเพิ่ม เพราะผู้เปิดลิงก์ไม่ใช่เจ้าของ

**Exception Flow**
- **E1 — Token ไม่ถูกต้อง/ไม่มีอยู่จริง/ถูกปิดแชร์ (`share_enabled = false`)/ชุดเปรียบเทียบถูกลบไปแล้ว:** แสดงหน้า "ลิงก์นี้ใช้ไม่ได้แล้ว" แบบเดียวกันทุกกรณี ไม่บอกรายละเอียดว่าเคยมีอยู่จริงหรือถูกปิดแชร์ (กัน enumeration — ไม่ leak ว่า token ที่เดามั่วๆ นั้น "เคยมีอยู่จริง" หรือ "ไม่เคยมี") ไม่ error 500 ทุกกรณี
- **E2 — โรงเรียนบางแห่งในชุดถูก Archive หลังแชร์:** แสดง badge เหมือน UC-U03 E1 ไม่ทำให้ทั้งตารางพัง
- **E3 — คนเปิดลิงก์เยอะผิดปกติ** (เผยแพร่ในโซเชียลมีเดียแล้วมีคนเข้าเยอะ หรือถูกใช้ scrape ข้อมูลจำนวนมาก): เป็น public endpoint ไม่มี auth ต้องมี rate limit ต่อ IP ที่ `get-shared-comparison`
- **E4 — School Data Service (`school-data-api`) ตอบช้า/ล่มตอนดึงรายละเอียดโรงเรียน:** แสดง cache ล่าสุดถ้ามี (SWR) พร้อม badge "ผลลัพธ์อาจไม่เป็นปัจจุบัน" เหมือน UC-G01 E1 — แต่ผู้เปิดลิงก์ส่วนใหญ่มาจากนอกระบบและยังไม่เคยมี cache เลย จึงต้องมีหน้า "โหลดข้อมูลไม่สำเร็จ ลองใหม่อีกครั้ง" พร้อมปุ่ม retry เป็น fallback หลัก ไม่ใช่ error 500 เต็มหน้า

**Postcondition:** ผู้เปิดลิงก์เห็นตารางเปรียบเทียบล่าสุด ไม่มีสิทธิ์แก้ไข/บันทึกเพิ่มเอง (ต้องสมัครสมาชิกก่อนถ้าอยากบันทึกชุดของตัวเอง ผ่าน UC-G06 → UC-U03)
**Business Rule:** หน้าที่แชร์เป็น read-only เสมอ ไม่แสดงตัวตนเจ้าของชุดเปรียบเทียบต่อสาธารณะ (ไม่มี user_id/ชื่อ/อีเมลของเจ้าของปรากฏในหน้านี้หรือใน response ของ `get-shared-comparison` เลย)

---

### UC-G08: ดูกระทู้/ความคิดเห็นในฟอรัมผู้ปกครอง

**Actor หลัก:** Guest, Parent/User
**คำอธิบาย:** อ่านกระทู้ที่ผู้ปกครองคนอื่นตั้งไว้ — เป็นพื้นที่พูดคุยแบบเปิดที่ต่างจากรีวิว (UC-G04) ตรงที่รีวิวผูกกับโรงเรียน 1 แห่งและมีคะแนนดาว ส่วนกระทู้เป็นการสนทนาแบบมีคำถาม/คำตอบ ตั้งหัวข้อเองได้ และแท็กโรงเรียนหรือไม่แท็กก็ได้
**Precondition:** ไม่มี

**Main Flow**
1. ผู้ใช้เข้าหน้า "ฟอรัม" ระบบแสดงรายการกระทู้เรียงตามล่าสุด/ได้รับความสนใจมากที่สุด พร้อม pagination
2. กรองตามหมวดหมู่ (Review / Question / Update / Tips) หรือกรองเฉพาะกระทู้ที่แท็กโรงเรียนที่สนใจได้
3. กดเข้ากระทู้ เห็นเนื้อหาเต็ม + ความคิดเห็นทั้งหมดเรียงตามเวลา

**Exception Flow**
- **E1 — ยังไม่มีกระทู้ในหมวดที่เลือก:** แสดงข้อความชวนให้ล็อกอินเพื่อเป็นคนตั้งกระทู้แรก ไม่ใช่หน้าว่างเปล่า
- **E2 — กระทู้ถูกซ่อน/ลบโดย Admin ระหว่างที่ผู้ใช้เปิดค้างไว้:** กดเข้าไปแล้วขึ้น "เนื้อหานี้ถูกนำออกแล้ว" แทน error 404 หรือหน้าพัง
- **E3 — Guest กดปุ่ม "ตั้งกระทู้"/"แสดงความคิดเห็น"/"ถูกใจ":** แสดง prompt ให้ล็อกอินก่อน แทนการซ่อนปุ่ม (แนวเดียวกับ UC-G02 E5)
- **E4 — Community Service ช้า/ล่ม:** เสิร์ฟจาก cache (SWR) พร้อม badge "อาจไม่เป็นปัจจุบัน" ไม่กระทบหน้าอื่นของเว็บ เพราะเป็นคนละ schema กับ School Data Service

**Postcondition:** ผู้ใช้เห็นเฉพาะกระทู้/ความคิดเห็นที่ยังไม่ถูกนำออก — ไม่มีการเปลี่ยนแปลงข้อมูลในระบบ
**Business Rule:** แสดงเฉพาะเนื้อหาสถานะ `approved` เท่านั้น เนื้อหาที่ถูก Admin นำออก (`rejected`) ไม่แสดงต่อสาธารณะทุกกรณี และแสดงผู้เขียนเป็น display name เท่านั้น ไม่แสดงอีเมล/ชื่อจริง (กติกาเดียวกับ UC-U06)

## 3.2 กลุ่ม Parent / User

### UC-U01: จัดการโปรไฟล์ บัญชี และข้อมูลบุตรหลาน

**Actor หลัก:** Parent/User
**คำอธิบาย:** จัดการข้อมูลบัญชีของตนเอง (อีเมล/รหัสผ่าน) และข้อมูลบุตรหลาน (อายุ, ระดับชั้นที่สนใจ, งบประมาณ, หลักสูตรที่สนใจ, พื้นที่ที่สะดวก) รวมอยู่ในหน้าเดียวกัน ข้อมูลบุตรหลานใช้เป็น input ให้ UC-U04 (คำนวณค่าใช้จ่าย) และการแนะนำโรงเรียนในแชท (UC-U05)

**Main Flow**
1. ผู้ใช้เข้าหน้า "บัญชีของฉัน" แบ่งเป็น 2 ส่วน: ข้อมูลบัญชี (อีเมล/รหัสผ่าน) และโปรไฟล์บุตรหลาน (เพิ่มได้มากกว่า 1 คน)
2. แก้ไขข้อมูลส่วนไหนก็ได้อิสระจากกัน ระบบ validate แล้วบันทึกทีละส่วน
3. ผู้ใช้ขอลบบัญชีทั้งหมด (รวมข้อมูลบุตรหลาน) ได้จากหน้าเดียวกัน (สิทธิ์ตาม PDPA)

**Exception Flow**
- **E1 — ข้อมูลบุตรหลานไม่ครบ** (อย่างน้อยต้องมีงบประมาณ+ระดับชั้นสำหรับ AI แนะนำ): ไม่ block การบันทึก แต่แจ้งเตือนว่า UC-U04/UC-U05 จะทำงานได้ไม่เต็มที่จนกว่าจะกรอกเพิ่ม
- **E2 — กรอกข้อมูลบุตรหลานผิดรูปแบบ** (ค่าติดลบ, วันเกิดอนาคต): validate ก่อนบันทึก
- **E3 — มีบุตรหลานหลายคน:** รองรับหลายโปรไฟล์ต่อบัญชี เลือกใช้ตอนขอคำแนะนำ/คำนวณได้ว่าจะดูเผื่อคนไหน
- **E4 — เปลี่ยนอีเมลเป็นอีเมลที่มีบัญชีอื่นใช้อยู่แล้ว:** ปฏิเสธพร้อมแจ้งเหตุผล
- **E5 — ขอลบบัญชีขณะมีข้อมูลผูกอยู่** (รีวิว ใน Community Service, ประวัติเปรียบเทียบ/โปรไฟล์บุตรหลานใน User Service, ประวัติสนทนา AI ใน AI Service): ใช้ **Soft Delete + Grace Period** (เช่น 30 วัน) ก่อนลบถาวรจริง ยกเลิกคำขอได้ระหว่างนี้ — เมื่อพ้น Grace Period `account-deletion-cron` (pg_cron) จะแก้ข้อมูลทั้ง 3 schema ในธุรกรรมเดียว: รีวิวที่เขียนไว้ถูกทำให้เป็น anonymous แทนการลบทิ้ง, favorites/comparison_sets/children_profiles ถูกลบถาวร, ส่วนประวัติสนทนา AI ลบถาวรไปพร้อมบัญชีเพราะเป็นข้อมูลส่วนตัวล้วนไม่มีประโยชน์ต่อผู้ใช้อื่น (รายละเอียดกลไกข้าม Service ดู System Architecture หัวข้อ 4.2)
- **E6 — ข้อมูลบางส่วนต้องเก็บตามกฎหมายแม้ผู้ใช้ขอลบ:** แยกเก็บส่วนที่กฎหมายบังคับออกจากข้อมูลส่วนตัวที่ลบได้ทันที

**Postcondition:** ข้อมูลบัญชี/บุตรหลานถูกบันทึก หรือบัญชีเข้าสู่กระบวนการลบ
**Business Rule:** ข้อมูลบุตรหลานเป็นข้อมูลอ่อนไหวตาม **PDPA** เข้าถึงได้เฉพาะเจ้าของบัญชี คำขอลบบัญชีต้องดำเนินการให้เสร็จภายในระยะเวลาที่ PDPA กำหนด นับจากวันที่ Grace Period สิ้นสุด

### UC-U02: บันทึกโรงเรียนโปรด

**Actor หลัก:** Parent/User

**Main Flow**
1. ผู้ใช้กดไอคอน "บันทึก" ในหน้ารายละเอียดหรือผลค้นหา
2. ระบบเพิ่มโรงเรียนเข้ารายการโปรดของบัญชีนั้น แสดงในหน้า "รายการโปรด"

**Exception Flow**
- **E1 — กดบันทึกซ้ำโรงเรียนเดียวกัน:** Idempotent ไม่สร้างข้อมูลซ้ำ (toggle เป็นเอาออกแทน)
- **E2 — โรงเรียนที่บันทึกไว้ถูก Archive ภายหลัง:** ยังแสดงในรายการโปรดแต่มี badge "ไม่พร้อมให้บริการแล้ว" ไม่ลบออกเงียบๆ
- **E3 — จำนวนโรงเรียนที่บันทึกมากเกินไป:** มี pagination ในหน้ารายการโปรด ไม่โหลดทั้งหมดพร้อมกัน

**Postcondition:** โรงเรียนอยู่ใน (หรือถูกเอาออกจาก) รายการโปรดของบัญชีนั้นใน `user_data.favorites` และสถานะปุ่มบันทึกตรงกับความจริงเสมอ
**Business Rule:** รายการโปรดผูกกับบัญชี ไม่ใช่ device

---

### UC-U03: เปรียบเทียบโรงเรียนขั้นสูง

**Actor หลัก:** Parent/User
**คำอธิบาย:** เทียบโรงเรียนจากรายการที่บันทึกไว้ ไม่จำกัดจำนวนครั้ง เทียบฟิลด์ละเอียดกว่ารวม Hidden Cost breakdown เต็มรูปแบบ และบันทึกผลไว้ดูย้อนหลังได้

**Main Flow**
1. ผู้ใช้เข้าหน้า "เปรียบเทียบ" เลือกโรงเรียนจากรายการโปรดหรือค้นหาเพิ่ม
2. ระบบแสดงตารางเทียบแบบละเอียด (Hidden Cost breakdown, หลักสูตร, สิ่งอำนวยความสะดวก, **มาตรการความปลอดภัย** แสดงเป็นเครื่องหมาย ✓/— ต่อรายการตามตาราง 7.10, คะแนนรีวิว)
3. ผู้ใช้บันทึกชุดเปรียบเทียบนี้ไว้ดูภายหลังได้ (ตั้งชื่อชุด) — ชุดที่บันทึกแล้วนำไป Export เป็น PDF หรือสร้างลิงก์แชร์ต่อได้ทันทีผ่าน UC-U08

**Exception Flow**
- **E1 — โรงเรียนในชุดเปรียบเทียบถูก Archive:** แสดง badge แจ้ง ไม่ลบออกจากชุดเงียบๆ
- **E2 — ข้อมูลบางฟิลด์ไม่ครบในบางโรงเรียน:** แสดง "ไม่ระบุ" ในช่องนั้น ไม่ทำให้แถวทั้งแถวหายไป
- **E3 — จำนวนโรงเรียนที่เทียบมากจนแสดงผลยาก:** แนะนำให้แบ่งเป็นหลายชุดแทนการ scroll แนวนอนไม่จบ

**Postcondition:** ตารางเปรียบเทียบแสดงผล และถ้าผู้ใช้กดบันทึก จะมีแถวใหม่ใน `user_data.comparison_sets` (มี `comparison_id`) ที่พร้อมใช้กับ UC-U08 ต่อได้ทันที
**Business Rule:** ต่างจาก UC-G05 ตรงที่บันทึกและดูย้อนหลังได้ ไม่มี limit จำนวนครั้ง

### UC-U04: ใช้เครื่องคำนวณค่าใช้จ่าย (แบบส่วนตัว)

**Actor หลัก:** Parent/User
**Precondition:** ต้องล็อกอินเป็น Parent/User เท่านั้น (Guest ไม่มีสิทธิ์เข้าถึงเมนูนี้เลย — ดู UC-G02 Exception E5)
**คำอธิบาย:** คำนวณค่าใช้จ่ายรวมต่อปี/หลายปีแบบเจาะจงต่อครอบครัว โดยดึงจำนวน/ข้อมูลบุตรหลานจากโปรไฟล์ (UC-U01) มาใช้อัตโนมัติ รวมส่วนลดพี่น้อง (ถ้าโรงเรียนมี)

**Main Flow**
1. ผู้ใช้ (ล็อกอินแล้ว) เข้าแท็บ "คำนวณค่าใช้จ่าย" จากหน้ารายละเอียดโรงเรียน (UC-G02) หรือจากหน้าเปรียบเทียบ (UC-U03)
2. ระบบดึงโปรไฟล์บุตรหลานของบัญชีนั้นจาก `user_data.children_profiles` มาเติมเป็นค่าตั้งต้น (จำนวนบุตร, ระดับชั้น, จำนวนปีที่ต้องการคำนวณ) — ผู้ใช้แก้ค่าเองได้ทุกช่อง
3. ระบบดึงรายการค่าใช้จ่ายของโรงเรียนจากเวอร์ชัน published ปัจจุบัน (ค่าเทอม + hidden cost แต่ละรายการ พร้อม `academic_year`/`source_published_at` ที่กำกับมาในระดับฟิลด์ตามหัวข้อ 7.3)
4. คำนวณยอดรวมต่อปีและหลายปีด้วย decimal-safe arithmetic ฝั่ง Backend รวมส่วนลดพี่น้องถ้าโรงเรียนระบุไว้
5. แสดงผลแบบแยกรายรายการ พร้อมวันที่กำกับตามกติกา 3 บรรทัดในหัวข้อ 7.3 และ disclaimer ว่าเป็นตัวเลขประมาณการจากข้อมูลที่ระบบเก็บมา ไม่ใช่ใบเสนอราคาจากโรงเรียน
6. ผู้ใช้บันทึกผลลัพธ์ไว้ดูย้อนหลัง/เทียบกับโรงเรียนอื่นผ่านชุดเปรียบเทียบใน UC-U03 ได้

**Exception Flow**
- **E1 — บางรายการค่าใช้จ่ายยังไม่มีข้อมูล:** แสดง "ไม่ระบุ" ไม่รวมยอดอัตโนมัติ พร้อม disclaimer
- **E2 — `academic_year` ของค่าเทอม (ดูหัวข้อ 7.3) เป็นปีการศึกษาเก่ากว่าปีปัจจุบัน:** แสดง badge "ค่าเทอมปีการศึกษา [academic_year]" แยกจาก "ตรวจสอบล่าสุดเมื่อ [system timestamp]" อย่างชัดเจน ไม่รวมเป็นข้อความเดียวกัน — และถ้าฟิลด์นั้นมี `source_published_at` ต้องแสดงบรรทัดที่ 3 "ต้นฉบับอัปเดตล่าสุดเมื่อ [source_published_at]" ด้วย พร้อม badge เตือนสีเหลืองถ้าต้นฉบับเก่ากว่า 1 ปี (กติกาเดียวกับ UC-G02 ตามหัวข้อ 7.3)
- **E3 — Input ไม่ถูกต้อง** (จำนวนบุตรติดลบ/เกินขอบเขต): validate range ก่อนคำนวณ
- **E4 — ข้อผิดพลาดจากการปัดเศษ/คำนวณทางการเงิน:** ใช้ decimal-safe arithmetic ฝั่ง backend
- **E5 — โปรไฟล์บุตรหลานยังไม่ได้กรอก (UC-U01):** ใช้ค่า default (1 คน ไม่มีส่วนลด) ในการคำนวณเบื้องต้นไปก่อน พร้อมชวนกรอกโปรไฟล์เพื่อผลลัพธ์แม่นยำขึ้น

**Postcondition:** ผู้ใช้เห็นยอดค่าใช้จ่ายประมาณการพร้อมวันที่กำกับครบทุกบรรทัดตามหัวข้อ 7.3 — การคำนวณไม่เขียนทับข้อมูลโรงเรียนใดๆ เก็บได้แค่ผลลัพธ์ที่ผูกกับชุดเปรียบเทียบของผู้ใช้เอง
**Business Rule:** ต้องระบุแหล่งที่มาและวันที่อัปเดตของทุกตัวเลขเสมอ เพราะไม่มีโรงเรียนมายืนยันตัวเลขเอง ผลลัพธ์บันทึกไว้เทียบย้อนหลังได้ผ่าน UC-U03

### UC-U05: สนทนากับ AI Chatbot (รวมการแนะนำโรงเรียนส่วนบุคคล)

**Actor หลัก:** Parent/User | **Actor รอง:** AI/LLM Recommendation Engine
**Precondition:** ล็อกอินแล้วเท่านั้น (Guest เข้าถึงไม่ได้)
**คำอธิบาย:** สนทนากับ AI แบบมี Context/History ครอบคลุมทั้งการถามข้อมูลทั่วไปและ**การขอคำแนะนำโรงเรียนแบบจัดอันดับส่วนบุคคล**ในหน้าต่างเดียวกัน (เดิมแยกเป็น Use Case "รับคำแนะนำ" ต่างหาก ถูกรวมมาไว้ที่นี่เพราะเป็นความสามารถเดียวกันในมุมมองผู้ใช้ — ผู้ใช้แค่พิมพ์ขอคำแนะนำในแชทได้เลย)

**Main Flow**
1. ผู้ใช้เข้าหน้าแชทครั้งแรก (ยังไม่เคยพิมพ์อะไรในบทสนทนานี้) — ระบบแสดง **Guided Prompts** เป็นปุ่มหัวข้อคำถามนำทางให้กดเลือกได้ทันที (เช่น "แนะนำโรงเรียนให้หน่อย", "ค่าเทอมโดยประมาณเท่าไหร่", "เปรียบเทียบหลักสูตรอังกฤษ vs อเมริกัน", "มีค่าใช้จ่ายแฝงอะไรบ้าง") ลดภาระการพิมพ์เองสำหรับผู้ใช้ที่ยังไม่รู้จะถามอะไร — ผู้ใช้พิมพ์คำถามเองแทนก็ได้เสมอ ปุ่มเป็นทางลัดไม่ใช่ทางเดียว
2. หากเป็นคำขอแนะนำโรงเรียน **AI Service** (`chatbot-api`) เรียก tool ที่ยิงไปหา `school-data-api` ของ **School Data Service** (`search_schools`, `get_school_details`, `compare_schools`) และ `user-data-api` ของ **User Service** (ดึงโปรไฟล์บุตรหลานจาก UC-U01 มาเสริม context) — ทั้งสองเป็นการเรียกข้าม Service จริงผ่าน internal service secret + forward JWT ของผู้ใช้ (ดู System Architecture หัวข้อ 4.3-4.4) ใช้เงื่อนไข hard filter ตามงบประมาณ/พื้นที่/หลักสูตร ด้วย function calling แทน vector search เป็นหลัก เพราะคำถามส่วนใหญ่เป็น structured query (ตัวเลข/หมวดหมู่) และข้อมูลที่เก็บตอนนี้เป็น structured ล้วน ไม่มี free-text ให้ vector search จริงๆ (ดู System Architecture หัวข้อ 8)
3. ประกอบ prompt โดย inject เฉพาะข้อมูลโรงเรียนที่ `school-data-api` คืนมาจริง + โปรไฟล์ผู้ใช้จาก `user-data-api` + ประวัติสนทนา ส่งเข้า LLM
4. หากเป็นคำแนะนำโรงเรียน ระบบตรวจสอบว่าโรงเรียนที่ถูกแนะนำมีอยู่จริง (grounding check) ก่อนแสดงผล
5. แสดงคำตอบพร้อมเหตุผล/แหล่งอ้างอิง **พร้อมชุดคำถามต่อยอด (Quick Replies) 2-3 ข้อที่เกี่ยวกับคำตอบล่าสุดแนบมาด้วยเสมอ** (เช่น หลังตอบเรื่องค่าเทอมแล้ว เสนอปุ่ม "แล้วค่าใช้จ่ายแฝงล่ะ" / "เทียบกับโรงเรียนนี้กับอีกที่ไหม") — LLM ต้องคืนค่าเป็น structured output แยก field `answer` กับ `suggested_replies` ชัดเจน ไม่ปนกันเป็น free text เดียว เพื่อให้ Frontend render เป็นปุ่มกดได้จริง
6. ผู้ใช้ให้ feedback คำตอบได้แบบเร็วๆ (ถูกใจ/ไม่ถูกใจ) ซึ่งเป็น signal ที่ UC-A08 ใช้จัดลำดับความสำคัญตอนตรวจ Log

**Exception Flow**
- **E1 — คำถามนอกขอบเขตระบบ:** ตอบอย่างสุภาพว่าไม่สามารถช่วยเรื่องนี้ได้ ไม่พยายามตอบเดา
- **E2 — ประวัติสนทนายาวเกิน context window:** สรุปบทสนทนาเก่าอัตโนมัติ เก็บเฉพาะประเด็นสำคัญ
- **E3 — LLM timeout:** retry อัตโนมัติ 1 ครั้งก่อนแจ้ง error ให้ลองใหม่ หากเป็นคำขอแนะนำโรงเรียนและล้มเหลวซ้ำ → fallback เป็นระบบแนะนำแบบ rule-based (filter + scoring ไม่ใช้ LLM) พร้อมแจ้งผู้ใช้ว่าเป็นคำแนะนำแบบพื้นฐานชั่วคราว
- **E4 — Prompt Injection ผ่านข้อความแชท:** output filter ตรวจสอบก่อนส่งกลับ, system prompt แยกชั้นจาก user input ตลอดเวลา
- **E5 — เนื้อหาไม่เหมาะสม/สแปมจากผู้ใช้:** content moderation filter ก่อนส่งเข้า LLM และก่อนบันทึกลง log
- **E6 — LLM แนะนำโรงเรียนที่ไม่มีอยู่จริง (Hallucination):** กรองรายการที่ไม่ผ่าน grounding check ออกก่อนแสดงผลเสมอ log ไว้ให้ Admin ตรวจสอบผ่าน UC-A08
- **E7 — โปรไฟล์ผู้ใช้ไม่ครบสำหรับการแนะนำ:** ระบบถามข้อมูลเพิ่มเติมกลับในแชทแบบสนทนา (เช่น "งบประมาณต่อปีประมาณเท่าไหร่คะ") แทนการ block การใช้งานทั้งหมด
- **E8 — Rate limit เกิน** (ป้องกันต้นทุน LLM API โดยเฉพาะตอนขอคำแนะนำที่ใช้ retrieval หนักกว่าถามเฉยๆ): แจ้ง "กรุณาลองใหม่ในอีก X นาที"
- **E9 — Indirect Prompt Injection ผ่านเนื้อหาที่ Scrape มาจากเว็บโรงเรียน** (ดูหัวข้อ 8.3): ข้อมูลที่ Retrieve มาต้องแยกชั้นจาก System Instruction เสมอเช่นเดียวกับ User Input ใน E4 ไม่เชื่อว่าเนื้อหาจากเว็บภายนอกปลอดภัยเสมอไป
- **E10 — LLM ไม่คืน Quick Replies กลับมา หรือคืนมาผิด format:** ไม่ block การแสดงคำตอบหลัก แค่ไม่แสดงปุ่มเสริมของรอบนั้น (Graceful Degradation) — ผู้ใช้ยังพิมพ์คำถามต่อเองได้ตามปกติ

**Postcondition:** ผู้ใช้ได้คำตอบที่ grounded บนข้อมูลจริง พร้อม Quick Replies (ถ้า LLM คืนมาถูก format) และบทสนทนาถูกบันทึกลง `ai.conversations`/`ai.messages` สำหรับ UC-A08
**Business Rule:** ทุกคำตอบที่อ้างอิงข้อมูลจำเพาะของโรงเรียนต้องระบุแหล่งอ้างอิงและวันที่เก็บข้อมูลล่าสุด คำแนะนำโรงเรียนต้อง grounded บนข้อมูลจริงในระบบเท่านั้น ห้าม LLM สร้างตัวเลขค่าเทอม/หลักสูตรขึ้นเองโดยเด็ดขาด

### UC-U06: เขียนรีวิว/ให้คะแนนโรงเรียน

**Actor หลัก:** Parent/User

**Main Flow**
1. ผู้ใช้เข้าหน้ารายละเอียดโรงเรียน กด "เขียนรีวิว" ให้คะแนน (ดาว) + เขียนความคิดเห็น
2. ระบบตรวจสอบว่าผู้ใช้ยังไม่เคยรีวิวโรงเรียนนี้มาก่อน
3. รีวิวเข้าคิว Moderation (UC-A06) ก่อนเผยแพร่จริง

**Exception Flow**
- **E1 — ผู้ใช้เคยรีวิวโรงเรียนนี้แล้ว:** ไม่สร้างใหม่ซ้ำ แต่เปิดให้แก้ไขรีวิวเดิมแทน (จำกัด 1 รีวิวต่อคนต่อโรงเรียน)
- **E2 — เนื้อหารีวิวมีคำหยาบ/สแปม/ข้อมูลส่วนตัวของคนอื่น:** content filter เบื้องต้นเตือนก่อน submit และยังต้องผ่าน Moderation อีกชั้น
- **E3 — Community Service (schema `community`) ล่มตอน submit:** Frontend เก็บ draft ที่ผู้ใช้พิมพ์ไว้ฝั่ง client แล้ว retry ให้อัตโนมัติเมื่อ service กลับมา ไม่ทิ้งเนื้อหาที่พิมพ์ไปเฉยๆ — เมื่อบันทึกสำเร็จรีวิวจึงเข้าสถานะ "รอตรวจสอบ" ตามปกติ (ไม่มีคิว retry ฝั่ง server เพราะ Community Service ไม่มี Edge Function ของตัวเอง ดู System Architecture หัวข้อ 4.1)
- **E4 — มีการรีวิวจำนวนมากผิดปกติ (bot/spam):** rate limit ต่อบัญชีต่อวัน

**Postcondition:** รีวิวอยู่สถานะ "รอตรวจสอบ" จนกว่า Admin จะอนุมัติผ่าน UC-A06
**Business Rule:** รีวิวที่ยังไม่ผ่าน Moderation จะไม่แสดงใน UC-G04 ต่อสาธารณะ รีวิวที่เผยแพร่แสดงเป็นชื่อเล่น/display name ที่ผู้ใช้ตั้งเอง ไม่แสดงชื่อจริงหรืออีเมลต่อสาธารณะ (Admin เห็นตัวตนจริงที่ผูกกับบัญชีได้เฉพาะตอน Moderate เพื่อความรับผิดชอบ)

### UC-U07: แจ้งข้อมูลผิดพลาด/ไม่เป็นปัจจุบัน

**Actor หลัก:** Parent/User

**Main Flow**
1. ผู้ใช้กด "แจ้งข้อมูลผิดพลาด" ในหน้ารายละเอียดโรงเรียน เลือกฟิลด์ที่ผิด + อธิบาย + แนบหลักฐานได้
2. ระบบสร้าง Ticket ผูกกับโรงเรียนและฟิลด์นั้น ส่งเข้าคิว Admin ผ่าน UC-A11

**Exception Flow**
- **E1 — มีคนแจ้งฟิลด์เดียวกันของโรงเรียนเดียวกันซ้ำ:** รวมเป็น ticket เดียว นับจำนวนครั้งที่แจ้งแทนสร้างซ้ำ ช่วย Admin จัดลำดับความสำคัญ
- **E2 — แนบไฟล์หลักฐานล้มเหลว:** ยังส่ง ticket ได้โดยไม่มีไฟล์แนบ ไม่ block การแจ้ง
- **E3 — ผู้ใช้แจ้งข้อมูลเดิมซ้ำหลายรอบโดยไม่มีเหตุผลใหม่:** จำกัดจำนวนครั้งต่อวันต่อบัญชี

**Postcondition:** Ticket เข้าคิว Admin ผู้แจ้งได้รับแจ้งเตือนเมื่อสถานะเปลี่ยน (Database Webhook บน `community.data_correction_reports.status` ยิงไปหา Ops Service `notification-sender` ตรง — ไม่ใช่ Community Service เรียกออกเองเพราะไม่มี Edge Function ของตัวเอง ดู System Architecture หัวข้อ 4.3.1)
**Business Rule:** การแจ้งไม่ทำให้ข้อมูลเปลี่ยนทันที ต้องผ่านการตรวจสอบของ Admin ก่อนเสมอ

### UC-U08: ส่งออก/แชร์ผลการเปรียบเทียบ (PDF หรือลิงก์)

**Actor หลัก:** Parent/User
**คำอธิบาย:** จากหน้าเปรียบเทียบที่บันทึกไว้แล้ว (UC-U03) ผู้ใช้เลือกได้ว่าจะ Export เป็น PDF (snapshot ตายตัว ณ ตอนสร้าง) หรือสร้างลิงก์แชร์ (ข้อมูลอัปเดตตามจริงเสมอ ให้คนอื่นเปิดดูได้โดยไม่ต้องมีบัญชี) หรือทำทั้งคู่ก็ได้ตามแต่ละกรณีใช้งาน — สองทางนี้ตั้งใจให้ต่างกัน ไม่ใช่ตัวเลือก format เฉยๆ (ดู Business Rule)

**Main Flow (Export PDF)**
1. ผู้ใช้อยู่ในหน้าเปรียบเทียบที่**บันทึกไว้แล้ว** (UC-U03) กด "Export เป็น PDF" — ต้องเป็นชุดที่บันทึกแล้วเช่นเดียวกับลิงก์แชร์ เพราะ `pdf-export` (Ops Service) ดึงชุดเปรียบเทียบผ่าน `user-data-api` ด้วย `comparison_id` ไม่ได้รับ `school_ids` มาจากหน้าเว็บโดยตรง (ดู System Architecture หัวข้อ 6)
2. ระบบสร้างงาน generate PDF แบบ async
3. เมื่อเสร็จ แจ้งเตือนผู้ใช้พร้อมลิงก์ดาวน์โหลด

**Main Flow (สร้างลิงก์แชร์)**
1. ผู้ใช้อยู่ในหน้าเปรียบเทียบที่**บันทึกไว้แล้ว**เท่านั้น (ต้องผ่าน UC-U03 ขั้น "บันทึกชุด" ก่อน — ชุดที่ยังไม่บันทึกไม่มี `comparison_id` ให้ผูก token) กด "สร้างลิงก์แชร์"
2. ระบบสุ่ม `share_token` แบบคาดเดาไม่ได้ (ถ้ายังไม่เคยมี) ตั้ง `share_enabled = true` แสดงลิงก์ให้ copy/แชร์ต่อได้ทันที
3. ผู้ใช้ปิดแชร์ภายหลังได้ตลอดเวลาโดยไม่ต้องลบชุดเปรียบเทียบ (toggle `share_enabled`) — เปิดใหม่ได้โดยลิงก์เดิมใช้ได้เหมือนเดิม ไม่สุ่ม token ใหม่ทุกครั้งที่เปิด/ปิด

**Exception Flow**
- **E1 — Generate PDF ใช้เวลานาน/ล้มเหลว:** ทำแบบ async เสมอ ไม่ให้หน้าค้าง retry อัตโนมัติ 1 ครั้งก่อนแจ้งว่าล้มเหลวจริง
- **E2 — ข้อมูลในชุดเปรียบเทียบเปลี่ยนระหว่างรอ generate PDF:** PDF ใช้ snapshot ข้อมูล ณ ตอนกดสร้าง ไม่ใช่ real-time ล่าสุด (ต่างจากลิงก์แชร์ที่ตั้งใจให้เป็น live เสมอ ดู UC-G07)
- **E3 — ไฟล์ PDF ใหญ่เกินขนาดที่ระบบอนุญาต:** บีบอัดหรือแจ้งให้ดาวน์โหลดผ่านลิงก์แทนการแนบไฟล์
- **E4 — พยายาม Export PDF หรือสร้างลิงก์แชร์จากชุดเปรียบเทียบที่ยังไม่บันทึก:** ปุ่มทั้งสองถูก disable พร้อมข้อความ "บันทึกชุดก่อนถึงจะ Export/แชร์ได้"
- **E5 — เจ้าของลบชุดเปรียบเทียบทั้งที่มีลิงก์แชร์เปิดอยู่:** ลิงก์เดิมใช้ไม่ได้ทันที (ดู UC-G07 E1)

**Postcondition:** ได้ไฟล์ PDF ดาวน์โหลด และ/หรือ ลิงก์แชร์ที่เปิดใช้งานอยู่ (แล้วแต่ทางที่ผู้ใช้เลือก)
**Business Rule:** PDF ต้องระบุวันที่สร้างรายงานกำกับไว้เสมอ เพราะเป็น snapshot — ลิงก์แชร์เป็น**คนละอย่าง**กับ PDF โดยตั้งใจ: ข้อมูลอัปเดตตามจริงเสมอ (ไม่ใช่ snapshot) เพื่อให้ลิงก์มีประโยชน์ระยะยาวแม้เปิดทีหลังผ่านไปหลายเดือน และไม่แสดงตัวตนเจ้าของชุดต่อสาธารณะ (ดู UC-G07)

### UC-U09: ตั้งกระทู้/แสดงความคิดเห็น/รายงานเนื้อหาในฟอรัม

**Actor หลัก:** Parent/User
**Precondition:** ล็อกอินและยืนยันอีเมลแล้ว (ตาม Business Rule ของ UC-G06)
**คำอธิบาย:** สร้างกระทู้ใหม่ ตอบความคิดเห็น กดถูกใจ และรายงานเนื้อหาที่ไม่เหมาะสมให้ Admin ตรวจสอบ (UC-A12)

**Main Flow**
1. ผู้ใช้กด "ตั้งกระทู้" เลือกหมวดหมู่ (Review / Question / Update / Tips) กรอกหัวข้อ + เนื้อหา และแท็กโรงเรียนได้ 1 แห่ง (ไม่บังคับ)
2. ระบบผ่าน content filter อัตโนมัติ (คำหยาบ/สแปม/ข้อมูลส่วนบุคคลของผู้อื่น) แล้ว **เผยแพร่ทันที** — ต่างจากรีวิว (UC-U06) ที่ต้องรอ Admin อนุมัติก่อน
3. ผู้ใช้อื่นแสดงความคิดเห็นต่อท้ายกระทู้ หรือกดถูกใจได้
4. ผู้ใช้คนใดก็ได้กด "รายงาน" เนื้อหาที่ไม่เหมาะสม ระบุเหตุผล → เข้าคิวให้ Admin ตรวจผ่าน UC-A12
5. เจ้าของกระทู้/ความคิดเห็นแก้ไขหรือลบของตัวเองได้ตลอด (ลบแล้วขึ้น "เนื้อหานี้ถูกลบโดยผู้เขียน" เพื่อไม่ให้บริบทของคนที่ตอบต่อหายไปทั้งเธรด)

**Exception Flow**
- **E1 — content filter ตรวจพบคำต้องห้าม:** เตือนก่อน submit ให้แก้ไขเอง ถ้ายังยืนยันส่ง ให้ตั้งสถานะเป็น `pending` รอ Admin ตรวจก่อนเผยแพร่แทนการเผยแพร่ทันที
- **E2 — ผู้ใช้โพสต์ถี่ผิดปกติ (spam/bot):** rate limit ต่อบัญชีต่อวัน ทั้งกระทู้และความคิดเห็น
- **E3 — กระทู้ถูกลบระหว่างที่ผู้ใช้กำลังพิมพ์ความคิดเห็น:** แจ้ง "กระทู้นี้ถูกนำออกแล้ว" พร้อมคืนข้อความที่พิมพ์ไว้ให้ copy ไม่ทิ้งเงียบ
- **E4 — รายงานเนื้อหาเดิมซ้ำ:** 1 บัญชีรายงานได้ 1 ครั้งต่อ 1 เนื้อหา (บังคับที่ระดับ DB) ครั้งถัดไปนับรวมเป็นจำนวนผู้รายงานแทนสร้าง ticket ใหม่ (แนวเดียวกับ UC-U07 E1)
- **E5 — Community Service ล่มตอน submit:** Frontend เก็บ draft ไว้ฝั่ง client แล้ว retry ให้อัตโนมัติ (แนวเดียวกับ UC-U06 E3)
- **E6 — เนื้อหาอ้างข้อมูลค่าเทอมที่ผิด/ล้าสมัย:** ไม่ block การโพสต์ (เป็นความเห็นส่วนบุคคล) แต่ระบบขึ้นหมายเหตุใต้กระทู้ที่แท็กโรงเรียนว่า "ตัวเลขทางการดูได้ที่หน้าโรงเรียน" พร้อมลิงก์ไป UC-G02 กันผู้อ่านเข้าใจว่าเป็นข้อมูลที่ระบบรับรอง

**Postcondition:** กระทู้/ความคิดเห็นถูกเผยแพร่ (หรืออยู่สถานะ `pending` ตาม E1) และรายการรายงานเข้าคิว UC-A12 ถ้ามีการกดรายงาน
**Business Rule:** ฟอรัมใช้ **Post-Moderation** (เผยแพร่ก่อน ตรวจเมื่อถูกรายงาน) ต่างจากรีวิว (UC-U06) ที่ใช้ **Pre-Moderation** โดยตั้งใจ — เพราะรีวิวมีผลต่อคะแนนเฉลี่ยของโรงเรียนที่แสดงในผลค้นหาโดยตรง ความเสียหายถ้าปล่อยผ่านจึงสูงกว่า ส่วนฟอรัมเป็นบทสนทนาที่ต้องการความทันทีถึงจะมีชีวิต และไม่กระทบตัวเลขใดๆ ที่ระบบแสดงเป็นข้อมูลทางการ — เนื้อหาในฟอรัม**ไม่ถูกใช้เป็นแหล่งข้อมูลของ Chatbot (UC-U05) หรือของ RAG (UC-A07) เด็ดขาด** เพราะไม่ผ่านการตรวจสอบแบบเดียวกับข้อมูลโรงเรียน

## 3.3 กลุ่ม Admin

### UC-A01: จัดการข้อมูลโรงเรียนโดยตรง

**Actor หลัก:** Admin
**คำอธิบาย:** ช่องทางที่ Admin แก้ไขข้อมูลโรงเรียนด้วยตนเอง (เช่น หลังโทรสอบถามโรงเรียนโดยตรง หรือแก้จากการตรวจพบข้อผิดพลาด) ผ่าน validation แล้ว **เผยแพร่ทันที** ไม่ต้องขออนุมัติซ้อนเพราะ Admin คือผู้อนุมัติอยู่แล้วในตัว

**Main Flow**
1. Admin เปิดหน้าแก้ไขโรงเรียน เห็น **ประวัติเวอร์ชันทั้งหมด** ของโรงเรียนนี้ (วันที่, แหล่งที่มา admin/scraper/bulk_import, ใครทำ, สรุปว่าแก้อะไรบ้างจาก diff_summary) ดึงจาก `school_versions` เรียงจากล่าสุด
2. Admin แก้ไขฟิลด์ที่ต้องการ ระบบ validate แล้วบันทึกเป็นเวอร์ชันใหม่ status=published ทันที
3. Admin เลือก "Restore" เวอร์ชันเก่าจากประวัติในข้อ 1 ได้ทุกเมื่อ ซึ่งจะสร้างเวอร์ชันใหม่ที่มีค่าเท่าเวอร์ชันเก่าที่เลือก (ไม่ใช่การลบเวอร์ชันหลังจากนั้นทิ้ง เพื่อรักษาความต่อเนื่องของ Audit Trail)

**Exception Flow**
- **E1 — Admin สองคนแก้ไขโรงเรียนเดียวกันพร้อมกัน:** ใช้ **Optimistic Locking ด้วย version number** — คนที่บันทึกทีหลังได้รับ conflict error ต้อง reload ก่อน
- **E2 — แก้ไขผิดพลาดโดยไม่ตั้งใจ:** ใช้ฟีเจอร์ "Restore เวอร์ชันก่อนหน้า" จากข้อ 3 ของ Main Flow ได้ทันที ไม่ต้องแก้ไขฟิลด์ทีละอันย้อนกลับเอง
- **E3 — Validation error:** แสดง error รายฟิลด์ก่อนบันทึก
- **E4 — ลบ/ปิดโรงเรียนที่มีข้อมูลผู้ใช้ผูกอยู่:** ใช้ **Soft Delete** เท่านั้น (สถานะ Archived) ห้าม hard delete

**Postcondition:** โรงเรียนมีเวอร์ชันใหม่สถานะ published ที่ `schools.current_published_version_id` ชี้อยู่ (อยู่ใน transaction เดียวกันตามหัวข้อ 8.5) และมีแถวใหม่ใน `audit_log`
**Business Rule:** ห้าม hard delete ข้อมูลโรงเรียนเด็ดขาด ใช้ Archived status แทนเสมอ

### UC-A02: นำเข้าข้อมูลเริ่มต้น (OPEC Scrape, Serper URL)

**Actor หลัก:** Admin
**คำอธิบาย:** Seed ข้อมูลเริ่มต้นของทุกโรงเรียนในระบบ โดยใช้ 2 แหล่งประกอบกัน: (1) ดึงรายชื่อโรงเรียนนานาชาติที่ได้รับอนุญาตถูกต้องตามกฎหมายจากฐานข้อมูลของ **สช. (สำนักงานคณะกรรมการส่งเสริมการศึกษาเอกชน / OPEC)** และ (2) ใช้ **Serper API** (Google Search API) ค้นหา URL เว็บไซต์/เพจทางการของแต่ละโรงเรียนจากชื่อ+ที่อยู่ที่ได้จาก OPEC เพื่อเตรียมเป้าหมายให้ UC-A03 ใช้ต่อ

**Main Flow**
1. Admin สั่งรัน Import Job ระบุแหล่งข้อมูล (OPEC dataset)
2. ระบบ parse รายชื่อโรงเรียนจาก OPEC ตรวจสอบความซ้ำกับข้อมูลที่มีอยู่
3. สำหรับโรงเรียนใหม่แต่ละแห่ง เรียก Serper API ค้นหาด้วย query "ชื่อโรงเรียน + ที่อยู่/จังหวัด" เพื่อหา URL เว็บไซต์ทางการที่น่าจะใช่ที่สุด
4. Admin ตรวจสอบ preview รายการก่อน confirm import จริง (โดยเฉพาะ URL ที่ Serper หาให้)
5. Confirm → บันทึกเป็นเวอร์ชัน Published เริ่มต้นของแต่ละโรงเรียน พร้อม official_website_url

**Exception Flow**
- **E1 — บางแถวข้อมูลจาก OPEC ผิดรูปแบบ/ไม่ครบ:** ประมวลผลแบบ per-row ไม่ใช่ all-or-nothing แถวที่ผิดถูกรวบรวมเป็นรายงาน error ให้ Admin แก้ไขทีหลัง
- **E2 — Serper API หา URL ไม่เจอ หรือเจอ URL ที่ไม่ใช่เว็บโรงเรียนจริง** (เช่น หน้าข่าว/Wikipedia): ไม่ auto-confirm URL ที่ความมั่นใจต่ำ ต้องให้ Admin ยืนยัน/แก้เองในขั้นตอน Preview เสมอ
- **E3 — Serper API rate limit/ค่าใช้จ่ายเกิน quota:** ทำแบบ throttled/batch พร้อม retry ภายหลัง ไม่ยิง request รัวเกิน budget
- **E4 — ไฟล์/ข้อมูล OPEC ขนาดใหญ่/ใช้เวลานาน:** ประมวลผลแบบ async job พร้อม progress bar แจ้งผลเมื่อเสร็จ
- **E5 — ข้อมูลซ้ำกับโรงเรียนที่มีอยู่แล้ว:** flag ให้ Admin เลือก merge/skip/สร้างใหม่

**Postcondition:** โรงเรียนใหม่ถูกเพิ่มเข้าระบบพร้อม official_website_url ที่พร้อมให้ UC-A03 ใช้ต่อ
**Business Rule:** URL ที่ได้จาก Serper ต้องผ่านการยืนยันจาก Admin อย่างน้อย 1 ครั้งก่อนถูกใช้เป็นเป้าหมาย Scraper จริง เพื่อป้องกัน Scraper ไปเก็บข้อมูลจากเว็บผิด

### UC-A03: เก็บข้อมูลผ่าน Web Scraping อัตโนมัติ

**Actor หลัก:** Admin | **Actor รอง:** Scraper/Crawler Service
**คำอธิบาย:** แหล่งข้อมูลหลักที่แท้จริงของระบบ รักษาความเป็นปัจจุบันของข้อมูลทุกโรงเรียนโดยไม่ต้องพึ่งพาใครติดต่อเข้ามา
**Precondition:** โรงเรียนมี official_website_url แล้ว (จาก UC-A02)

**Main Flow**
1. ระบบรัน Scraper ตามตารางเวลาที่ตั้งไว้ หรือ Admin สั่ง trigger เองเป็นรายโรงเรียน (ต้อง acquire lock เฉพาะโรงเรียนนั้นก่อนเริ่มเสมอ — ดูหัวข้อ 8.2 เรื่อง Concurrency)
2. Scraper ดึงเนื้อหาหน้าเว็บ/เพจตาม URL ที่บันทึกไว้ โดยเคารพ robots.txt และหน่วงเวลาระหว่าง request
3. แยกโครงสร้างข้อมูล (parsing) ด้วย selector แบบ rule-based หรือ LLM ช่วยอ่าน raw content พร้อมคำนวณ confidence score ต่อฟิลด์ — นอกจากค่าเทอม/ค่าใช้จ่ายแฝง/หลักสูตรแล้ว ยังนำทางไปหน้า Safety/Safeguarding Policy เพื่อสกัด**ข้อมูลความปลอดภัย**เพิ่มด้วย (ตาราง 7.10) โดยฟิลด์ที่หาไม่เจอให้เป็น `null` ห้ามเดาเป็น `false` — สำหรับฟิลด์กลุ่มค่าใช้จ่าย พยายามสกัด `source_published_at` เพิ่มด้วยแบบ best-effort (เช่น footer "Last updated", วันที่บนเอกสาร PDF) ไม่ error ถ้าหาไม่เจอในหน้านั้น เพราะเป็น optional field ตามหัวข้อ 7.3
4. เปรียบเทียบผลลัพธ์กับข้อมูล Published ปัจจุบัน หากต่างอย่างมีนัยสำคัญ (กำหนด threshold ต่อประเภทฟิลด์ เช่น ตัวเลขค่าเทอมเปลี่ยนเกิน 1% หรือ academic_year เปลี่ยน) จึงสร้างเวอร์ชันใหม่สถานะ **Pending Review** ส่งต่อ UC-A04 — หากไม่ต่างเลยหรือต่างเล็กน้อยไม่มีนัยสำคัญ (เช่น หน้าเว็บจัดใหม่แต่เนื้อหาเดิม) จะไม่สร้าง Pending Review เพื่อลด noise
5. ไม่ว่าจะพบความเปลี่ยนแปลงหรือไม่ ให้อัปเดต `schools.last_verified_at` เป็นเวลาปัจจุบันเสมอเมื่อ Scrape สำเร็จ เพื่อเป็นสัญญาณ "ตรวจสอบล่าสุดเมื่อไหร่" แยกจาก "เปลี่ยนแปลงล่าสุดเมื่อไหร่" (ดูหัวข้อ 7.3)

**Exception Flow**
- **E1 — โครงสร้างเว็บไซต์เปลี่ยนจน Selector เดิมพังใช้ไม่ได้:** Job fail แบบ graceful ไม่ commit ข้อมูลผิดเข้า Pending Review แจ้งเตือนทีมพัฒนาให้ปรับปรุง (และไม่อัปเดต last_verified_at เพราะยังไม่ได้ตรวจสอบสำเร็จจริง)
- **E2 — เว็บไซต์เป้าหมาย Block/Rate-limit:** ใช้ User-Agent ระบุตัวตนชัดเจน หน่วงเวลาและ retry แบบ backoff หยุด Scrape ชั่วคราวหากถูก Block ต่อเนื่อง
- **E3 — Scraper ตรวจพบความเปลี่ยนแปลงขณะ Admin กำลังแก้ไขโรงเรียนเดียวกันอยู่พอดี (UC-A01):** ใช้ parent_version_id เช็คเช่นเดียวกับ Optimistic Locking — ถ้า Admin บันทึกไปก่อนแล้ว Pending Review จาก Scraper ที่ base เวอร์ชันเก่ากว่าจะถูก flag ให้ re-diff ก่อน
- **E4 — เว็บไซต์โรงเรียนใช้งานไม่ได้แล้ว/โดเมนหมดอายุ:** Flag เป็น "ต้องตรวจสอบด้วยตนเอง" ให้ Admin ตามหาช่องทางใหม่
- **E5 — ผลลัพธ์จากการ Extract ผิดปกติ:** Sanity-check ทาง Backend (range validation) กรองออกก่อนเข้า Pending Review
- **E6 — เนื้อหาที่ Scrape มาอาจมีสคริปต์/โค้ดแฝง** (เว็บโรงเรียนถูกแฮ็ก หรือ URL ที่ Serper ให้มาไม่ใช่เว็บโรงเรียนจริงตาม UC-A02 E2): Sanitize/escape เนื้อหาทุกฟิลด์ (strip HTML/script tags) ก่อนบันทึกเข้า Pending Review เสมอ ไม่พึ่งพาการตรวจสอบด้วยสายตาของ Admin ใน Diff View เป็นด่านเดียว
- **E7 — โรงเรียนไม่ถูก verify สำเร็จมานานเกิน threshold ที่กำหนด** (เช่น เกิน 6 เดือน จาก E1-E4 fail ซ้ำๆ): flag ขึ้น UC-A09 Dashboard ให้ Admin ตรวจสอบด้วยตนเองว่า Scraper ยังทำงานปกติกับโรงเรียนนี้อยู่หรือไม่ ป้องกัน Silent Failure ที่ไม่มีใครสังเกตเห็น

**Postcondition:** ทุกโรงเรียนมีข้อมูลที่ค่อนข้างเป็นปัจจุบัน โดยไม่ต้องมีใครติดต่อเข้ามาเลย
**Business Rule:** ข้อมูลจาก Scraper ต้องผ่าน Admin อนุมัติเสมอ ไม่มีข้อยกเว้น

### UC-A04: ตรวจสอบและอนุมัติ/ปฏิเสธข้อมูลที่ Scraper ตรวจพบ

**Actor หลัก:** Admin

**Main Flow**
1. Admin เปิดคิวคำขอที่รออนุมัติ
2. ระบบแสดง **Diff View** เทียบข้อมูลเดิมกับข้อมูลที่ Scrape มาได้ทีละฟิลด์ พร้อม confidence score
3. Admin เลือก Approve ทั้งหมด/บางฟิลด์ หรือ Reject
4. Approve → publish เวอร์ชันใหม่ (อัปเดต `schools.current_published_version_id` ใน transaction เดียวกับการเปลี่ยน status ของ `school_versions` เป็น published — ดูหัวข้อ 8.5), invalidate cache ฝั่ง Client, Database Webhook ยิง trigger ไปยัง `re-embed-handler` ของ **AI Service** โดยอัตโนมัติ (ซึ่งจะเรียกกลับมาที่ `school-data-api` เพื่อดึงข้อความล่าสุดไปคำนวณ embedding — ดู System Architecture หัวข้อ 4.3)
5. Reject → เวอร์ชันนี้ถูกทิ้ง ไม่กระทบข้อมูล Published เดิม

**Exception Flow**
- **E1 — ข้อมูล Live ถูกแก้โดย Admin ระหว่างกำลัง Review:** ตรวจสอบ base version ที่ Scraper ใช้ตอนสร้าง Pending ว่ายังตรงปัจจุบันหรือไม่ก่อน approve ถ้าไม่ตรงต้อง re-diff ใหม่
- **E2 — `re-embed-handler` (AI Service) ล้มเหลว** (ไม่ว่าจะ trigger เองล้มเหลว หรือเรียก `school-data-api` ข้าม Service ไม่สำเร็จ): retry แบบ exponential backoff อัตโนมัติ ถ้ายัง fail ซ้ำให้ตกเข้าตาราง `failed_jobs` แจ้งเตือนทีมพัฒนา
- **E3 — Admin ปฏิเสธข้อมูลจาก Scraper ของโรงเรียนเดียวกันซ้ำหลายรอบติดกัน:** flag เป็น "ต้องตรวจสอบ Scraper Config ด้วยตนเอง" แทนวนเข้าคิวซ้ำเดิม

**Postcondition:** เวอร์ชันที่ถูก Approve กลายเป็น published พร้อม trigger re-embed ผ่าน UC-A07 — หรือเวอร์ชันที่ถูก Reject ถูกทิ้งโดยข้อมูล published เดิมไม่ถูกแตะ ทั้งสองกรณีมี Audit Trail ครบ
**Business Rule:** ทุก action ต้องมี Audit Trail ครบถ้วน

### UC-A05: จัดการบัญชีผู้ใช้ (ระงับ/ลบ)

**Actor หลัก:** Admin

**Main Flow**
1. Admin ค้นหา/เปิดดูบัญชีผู้ใช้ที่ต้องการจัดการ
2. เลือกระงับ (suspend) ชั่วคราวหรือลบ พร้อมระบุเหตุผล

**Exception Flow**
- **E1 — ระงับบัญชีที่กำลังใช้งานอยู่ (active session):** session ปัจจุบันถูก invalidate ทันที ไม่รอ token หมดอายุเอง
- **E2 — ลบบัญชีที่มีข้อมูลผูกอยู่มาก:** ใช้ Soft Delete เท่านั้น (เช่นเดียวกับ UC-U01 E5 — `account-deletion-cron` แก้ข้อมูลข้าม 3 schema ในธุรกรรมเดียวตอน Grace Period หมด ดู System Architecture หัวข้อ 4.2)
- **E3 — Admin ระงับบัญชีผิดคน:** มีปุ่ม "ยกเลิกการระงับ" คืนสิทธิ์ได้ทันที พร้อม log ไว้ audit

**Postcondition:** บัญชีอยู่ในสถานะ `suspended` หรือ `pending_deletion` ตามที่ Admin เลือก พร้อมเหตุผลที่บันทึกไว้ใน `audit_log` (การลบจริงเกิดตอน Grace Period หมดตาม UC-U01 E5)
**Business Rule:** ทุกการระงับ/ลบต้องระบุเหตุผลและถูกบันทึกใน Audit Log เสมอ

### UC-A06: ตรวจสอบและลบรีวิวที่ไม่เหมาะสม

**Actor หลัก:** Admin

**Main Flow**
1. Admin เปิดคิวรีวิวที่รอตรวจสอบ (จาก UC-U06) หรือถูก report
2. อ่านทบทวน เลือก Approve (เผยแพร่) หรือ Reject พร้อมเหตุผล

**Exception Flow**
- **E1 — Volume รีวิวเข้าคิวเยอะเกินตรวจด้วยตาทั้งหมด:** ใช้ content moderation filter อัตโนมัติคัดกรองเบื้องต้น เหลือเฉพาะเคสกำกวมให้ Admin ตรวจ
- **E2 — ลบรีวิวที่ Approve ไปแล้วในภายหลัง:** เก็บเหตุผลไว้ audit เผื่อมีข้อโต้แย้ง
- **E3 — ผู้เขียนรีวิวโต้แย้งว่าการลบไม่เป็นธรรม:** มีช่องทางยื่นอุทธรณ์ เข้าคิวให้ Admin คนละคนพิจารณาซ้ำ

**Postcondition:** รีวิวมีสถานะ approved (แสดงใน UC-G04) หรือ rejected (ไม่แสดงต่อสาธารณะแต่ยังเก็บ log ไว้) พร้อมผู้ตรวจและเหตุผลที่บันทึกไว้
**Business Rule:** รีวิวที่ Reject ไม่แสดงต่อสาธารณะเลย แต่ยังเก็บ log ไว้ภายใน

### UC-A07: จัดการฐานความรู้ของ AI (RAG)

**Actor หลัก:** Admin | **Actor รอง:** AI/LLM Recommendation Engine
**คำอธิบาย:** ทุกครั้งที่ข้อมูลโรงเรียนถูก publish (จาก UC-A01 หรือ UC-A04) ระบบต้อง trigger การ re-embed ข้อมูลนั้นเข้า Vector DB อัตโนมัติ
**Precondition:** มีเวอร์ชันของโรงเรียนถูกเปลี่ยนสถานะเป็น published สำเร็จ (จาก UC-A01 หรือ UC-A04)

**Main Flow**
1. เวอร์ชันใหม่ถูก publish → **Database Webhook** บน `school_data.school_versions` ยิง HTTP ไปหา `re-embed-handler` ของ **AI Service** อัตโนมัติ พร้อม Correlation ID เดียวกับ flow ต้นทาง (ดูหัวข้อ 8.6)
2. `re-embed-handler` เรียกข้าม Service ไปที่ `school-data-api` ของ **School Data Service** เพื่อดึงข้อความของเวอร์ชันที่เพิ่ง publish (ไม่ query schema `school_data` ตรงตาม Golden Rule)
3. คำนวณ embedding แล้ว **upsert** ลง `ai.school_embeddings` โดยใช้ `version_id` เป็น key (ต้อง idempotent เพราะ webhook เป็น at-least-once delivery — ดูหัวข้อ 8.4)
4. Admin ตรวจสอบงาน re-embed ที่ล้มเหลวได้จากตาราง `ops.failed_jobs` ผ่าน UC-A09/UC-A10

**Exception Flow**
- **E1 — Embedding job ล้มเหลว:** retry แบบ exponential backoff ถ้ายัง fail ซ้ำให้ตกเข้าตาราง `failed_jobs` (แทน Dead Letter Queue) พร้อมแจ้งเตือนทีมพัฒนา
- **E2 — pgvector (`ai.school_embeddings`) ยังไม่ถูก re-embed ตามข้อมูลล่าสุดทันที:** เพราะ **AI Service** ต้องเรียกข้าม Service ไปหา `school-data-api` ของ **School Data Service** แบบ async ผ่าน Database Webhook → `re-embed-handler` (ดู System Architecture หัวข้อ 4.3) ยอมรับ eventual consistency ในช่วงสั้นๆ (ไม่เกิน 5-10 นาที) — เป็นธรรมชาติของการแยก Service กันจริงตาม Golden Rule ไม่ใช่ bug

**Postcondition:** `ai.school_embeddings` มี embedding ที่ตรงกับเวอร์ชัน published ล่าสุดของโรงเรียนนั้น (ภายในกรอบ eventual consistency ตาม E2) หรือมีร่องรอยความล้มเหลวอยู่ใน `failed_jobs` เสมอ ไม่หายเงียบ
**Business Rule:** ห้าม embed ข้อมูลที่ยังไม่ผ่านสถานะ published เด็ดขาด — ฐานความรู้ของ AI ต้องสะท้อนเฉพาะข้อมูลที่ Admin อนุมัติแล้วเท่านั้น สอดคล้องกับ Business Rule ของ UC-A03/UC-A04

**หมายเหตุความสอดคล้องกับ System Architecture:** ปัจจุบัน (ดูหัวข้อ 8, 12 ของ System Architecture) Phase 3 ของ Data Pipeline ยัง scrape เฉพาะข้อมูล structured (ค่าเทอม/หลักสูตร/hidden cost) ไม่มีเนื้อหาข้อความอิสระให้ embed จริง ดังนั้น UC-A07 ในทางปฏิบัติตอนนี้จึง trigger ได้แต่ยังไม่มีเนื้อหาที่ทำให้ vector search มีความหมายจริงจนกว่าจะขยาย Phase 3 เพิ่ม

### UC-A08: ตรวจสอบ Log การสนทนา AI

**Actor หลัก:** Admin | **Actor รอง:** AI/LLM Recommendation Engine

**Main Flow**
1. Admin เปิดหน้า Log การสนทนา กรองตามช่วงเวลา/สถานะ (ผู้ใช้ report, ระบบตรวจพบ hallucination จาก UC-U05 E6)
2. อ่าน transcript เพื่อประเมินคุณภาพคำตอบ/หา pattern ที่ต้องปรับปรุง prompt

**Exception Flow**
- **E1 — บทสนทนามีข้อมูลส่วนบุคคลของผู้ใช้:** mask ข้อมูลอ่อนไหวก่อนแสดงให้ Admin เห็น (PDPA compliance แม้เป็น internal use)
- **E2 — Log มีปริมาณมากเกินไล่ดูทั้งหมด:** เรียงลำดับด้วย signal อัตโนมัติ (thumbs-down, hallucination flag) ให้ Admin ดูเคสสำคัญก่อน
- **E3 — Log กระทบ storage/performance:** ตั้ง retention policy (เก็บ raw transcript ไม่เกิน 90 วัน สรุปสถิติไว้ระยะยาวแทน)

**Postcondition:** Admin ได้ตรวจสอบบทสนทนาที่ต้องการ และการเข้าดูถูกบันทึกไว้ใน `audit_log` แยกจาก action ทั่วไปตาม PDPA — ไม่มีการแก้ไขเนื้อหาบทสนทนาใดๆ
**Business Rule:** การเข้าถึง Log ต้องมี audit ว่าใครเปิดดูบทสนทนาของใครเมื่อไหร่ เพราะเป็นข้อมูลส่วนบุคคล

### UC-A09: ดู Dashboard สถิติการใช้งาน

**Actor หลัก:** Admin

**Main Flow**
1. Admin เปิดหน้า Dashboard เห็นภาพรวม (ผู้ใช้ใหม่, โรงเรียนที่ถูกค้นหา/ดูมากที่สุด, อัตราการใช้ AI, คิว Pending Review ค้าง, ค่าใช้จ่าย LLM/Serper API สะสมรายวัน)
2. กรองช่วงเวลา/export ดูรายละเอียดเพิ่มได้

**Exception Flow**
- **E1 — Query สถิติหนักกระทบ production DB:** ไม่คำนวณสดทุกครั้ง — ใช้ **Materialized View** ที่ refresh ตามรอบด้วย `pg_cron` แล้วให้ Dashboard อ่านจาก view นั้นแทน (ระบบนี้ไม่มี Read Replica/Data Warehouse แยก เพราะทุก Service ยังอยู่ Postgres instance เดียวกัน ดู System Architecture หัวข้อ 4.6) ใช้ร่วมกับ cache ใน E3
- **E2 — ข้อมูลสถิติมี lag:** แสดง timestamp "ข้อมูลล่าสุดเมื่อ..." กำกับเสมอ
- **E3 — Dashboard โหลดช้า:** cache ผลลัพธ์ที่คำนวณแล้วไว้ระยะสั้น (5-15 นาที) แทนคำนวณใหม่ทุกครั้ง

**Postcondition:** Admin เห็นภาพรวมสถิติพร้อม timestamp กำกับว่าข้อมูลสดแค่ไหน — เป็น read-only ไม่เปลี่ยนแปลงข้อมูลในระบบ
**Business Rule:** Dashboard เป็น read-only ไม่มีการแก้ไขข้อมูลจากหน้านี้โดยตรง

### UC-A10: ตรวจสอบ Audit Log

**Actor หลัก:** Admin

**Main Flow**
1. Admin เปิดหน้า Audit Log ค้นหา/กรองตาม actor, action, ช่วงเวลา, entity
2. ดูรายละเอียด before/after snapshot ของแต่ละ action

**Exception Flow**

**Business Rule:** Audit Log เป็นแหล่งความจริงสุดท้าย (Source of Truth) เมื่อเกิดข้อพิพาทว่าใครทำอะไรไปเมื่อไหร่

### UC-A11: จัดการคำแจ้งข้อมูลผิดพลาดจากผู้ใช้

**Actor หลัก:** Admin

**Main Flow**
1. Admin เปิดคิว Ticket จาก UC-U07 เรียงตามจำนวนคนแจ้งซ้ำ/ความสำคัญ
2. ตรวจสอบข้อเท็จจริง (เข้าเว็บโรงเรียนเอง หรือสั่ง UC-A03 Scrape เฉพาะจุดซ้ำ) แล้วตัดสินใจ

**Exception Flow**

- **E2 — ตรวจสอบแล้วพบว่าผู้แจ้งถูกต้อง:** แก้ไขโดยตรงผ่าน UC-A01 หรือสั่ง UC-A03 เฉพาะโรงเรียนนั้นแล้วรอผลผ่าน UC-A04

**Business Rule:** ทุก Ticket ต้องมีผลสรุปและถูกบันทึกไว้ ไม่ปล่อยค้างสถานะ "รอตรวจสอบ" ไม่มีกำหนด

### UC-A12: ตรวจสอบและจัดการเนื้อหาในฟอรัม

**Actor หลัก:** Admin

**Main Flow**
1. Admin เปิดคิว "เนื้อหาที่ถูกรายงาน" เรียงตามจำนวนผู้รายงาน (จาก UC-U09 ข้อ 4) รวมกับคิวเนื้อหาสถานะ `pending` ที่ติด content filter (UC-U09 E1)
2. อ่านเนื้อหาพร้อมบริบทของทั้งเธรด
3. เลือก "คงไว้" (ปิดรายงาน ไม่แก้อะไร) หรือ "นำออก" (`rejected`) พร้อมระบุเหตุผล
4. กรณีร้ายแรง/ทำซ้ำ สั่งระงับบัญชีผู้เขียนต่อได้ทันทีผ่าน UC-A05

**Exception Flow**
- **E1 — เนื้อหาถูกรายงานเยอะผิดปกติเพราะความเห็นต่าง ไม่ใช่เพราะผิดกฎ:** จำนวนผู้รายงานเป็นแค่ลำดับความสำคัญ ไม่ใช่เกณฑ์ตัดสิน — ระบบห้ามซ่อนเนื้อหาอัตโนมัติตามจำนวนรายงานเด็ดขาด ต้องมี Admin ตัดสินเสมอ
- **E2 — เจ้าของเนื้อหาลบเองก่อน Admin ตรวจ:** ปิดรายงานอัตโนมัติพร้อมบันทึกว่า "ผู้เขียนลบเอง" ไม่ค้างในคิว
- **E3 — ผู้เขียนโต้แย้งการนำเนื้อหาออก:** ใช้ช่องทางอุทธรณ์เดียวกับ UC-A06 E3
- **E4 — Volume เนื้อหาเยอะเกินตรวจด้วยตา:** ตรวจเฉพาะที่ถูกรายงานหรือติด filter เท่านั้น ไม่ไล่อ่านทั้งฟอรัม (นี่คือเหตุผลที่เลือก Post-Moderation ตั้งแต่แรก)

**Postcondition:** เนื้อหาอยู่สถานะ `approved` (คงไว้) หรือ `rejected` (นำออก) พร้อมเหตุผลและผู้ตัดสินบันทึกไว้ และรายงานที่เกี่ยวข้องถูกปิดทั้งหมด
**Business Rule:** ทุกการนำเนื้อหาออกต้องระบุเหตุผลและถูกบันทึกใน Audit Log เสมอ เนื้อหาที่ถูกนำออกไม่ถูกลบจริงจากฐานข้อมูล (เก็บไว้เผื่อมีข้อโต้แย้ง) แต่ไม่แสดงต่อสาธารณะทุกกรณี

## 4. รูปแบบการจัดการข้อผิดพลาดฝั่ง Backend (Cross-cutting Patterns)

| Pattern | ใช้แก้ปัญหาอะไร | ใช้ใน Use Case ตัวอย่าง |
|---|---|---|
| **Retry + Exponential Backoff + Jitter** | เรียก service/API ที่ล้มเหลวชั่วคราว | LLM API, Serper API, Media Storage, Edge Function-to-Edge Function call (ดูหัวข้อ 4 ของ System Architecture — ระบบนี้ไม่มี Message Queue) |
| **Circuit Breaker** | ป้องกัน cascading failure เมื่อ service ปลายทางล่ม | External API (Maps, Serper, LLM) **และ** internal call ข้าม Service ผ่าน Edge Function (เช่น Chatbot → `school-data-api`/`user-data-api`, Re-embed handler → `school-data-api`) — ตอนนี้มี Service แยกจริงตาม schema แล้ว (ดู System Architecture หัวข้อ 4) |
| **Cache + Stale-While-Revalidate** | ลด latency และให้บริการต่อได้แม้ backend ช้า/ล่มชั่วคราว | UC-G01, UC-G02 (ทำที่ฝั่ง Frontend ด้วย SWR/TanStack Query ไม่ต้องสร้าง caching layer เอง) |
| **Optimistic Locking (version field)** | ป้องกัน conflict เมื่อแก้ไขข้อมูลพร้อมกันหลาย session | UC-A01, UC-A03, UC-A04 |
| **Database Webhook → Edge Function** (แทน Event-Driven Sync ผ่าน Message Queue) | trigger งาน async ข้าม Service (เช่น School Data Service publish → AI Service re-embed) โดยไม่ต้องมี Message Queue จริง | Re-embed handler (UC-A07) |
| **(ตัดออก) Reconciliation Job** | ยังไม่จำเป็น เพราะทุก schema อยู่ Postgres instance เดียวกัน ไม่มีความเสี่ยง network partition ระหว่าง service แบบที่ database แยก instance กันจะเจอ (ถ้าในอนาคตแยก instance จริงตาม service ค่อยพิจารณาใหม่) | — |
| **Idempotency Key** | ป้องกันข้อมูลซ้ำจากการ retry ของ client | UC-U02, UC-U06, UC-G06, UC-U09 (กดถูกใจ/รายงาน — บังคับด้วย composite PK และ unique constraint ที่ระดับ DB ดูหัวข้อ 7.13/7.21) |
| **`failed_jobs` table** (แทน Dead Letter Queue) | เก็บ job ที่ fail ซ้ำหลายครั้งไว้ตรวจสอบภายหลังโดยไม่บล็อกระบบหลัก — ไม่ต้องมี Message Queue จริง | UC-A03, UC-A07 |
| **Correlation ID** | เชื่อม Log ข้าม Edge Function ตอนเรียกข้าม Service | UC-U05 (Chatbot → School Data/User Service), UC-A07, UC-G07 (`get-shared-comparison` → School Data Service, ดูหัวข้อ 8.6) |
| **Graceful Degradation** | fallback แทน error 500 เมื่อ service ล่ม | UC-U05, UC-G03 |
| **Field-level Validation (Defense in Depth)** | ป้องกันข้อมูลผิดรูปแบบตั้งแต่ต้นทาง | ทุก Use Case ที่มีการกรอกฟอร์ม |
| **Soft Delete + Versioning + Audit Log** | ป้องกันข้อมูลหายถาวรจากความผิดพลาด รองรับการ undo | UC-A01, UC-A05, UC-U01 |

## 5. วงจรสถานะของข้อมูลโรงเรียน (Data Lifecycle)

```
[Admin แก้ไขข้อมูลโดยตรง] --(ผ่าน validation)--> Published ทันที

[Scraper อัตโนมัติ] --(ตรวจพบความต่างที่มีนัยสำคัญ)--> Pending Review --(Admin อนุมัติ)--> Published
                                                              |
                                                              +--(Admin ปฏิเสธ)--> ทิ้งเวอร์ชันนี้ (ไม่กระทบ Published เดิม)

[ระดับโรงเรียน — schools.status]
active --(โรงเรียนปิดกิจการ/Admin สั่ง Archive)--> archived
archived --(Admin สั่ง Reactivate)--> active
```

**หมายเหตุเรื่องระดับของสถานะ:** `Pending Review`/`Approved`/`Rejected`/`Published`/`Superseded` เป็นสถานะของ **`school_versions`** (หัวข้อ 7.2) ส่วน `active`/`archived` เป็นสถานะของ **`schools`** (หัวข้อ 7.1) คนละระดับกัน — การ Archive ไม่ได้ลบเวอร์ชัน published ทิ้ง แต่ทำให้โรงเรียนไม่ขึ้นในผลค้นหา (UC-G01) และหน้ารายละเอียดขึ้น banner แทน (UC-G02 E1b) ส่วนการ Reactivate คืนค่า `schools.status` เป็น `active` โดยยังชี้เวอร์ชันเดิมที่ `current_published_version_id`

**หลักการสำคัญ:** ข้อมูลที่ Guest/Parent มองเห็นต้องมาจากสถานะ **Published** เท่านั้นเสมอ Admin เป็นผู้เดียวที่ทำให้ข้อมูลเป็น Published ได้ ไม่ว่าจะแก้เองหรืออนุมัติจาก Scraper

## 6. ข้อเสนอแนะสำหรับขอบเขตโปรเจกต์ (Scoping Notes)

- สถาปัตยกรรมนี้เรียบง่ายและตรงกับ Plan จริงของทีม: **ไม่มี School Representative, ไม่มี Role/Permission หลายระดับ** — Admin มีบทบาทเดียว ทำให้ Timeline พัฒนาสั้นลงชัดเจน
- **การสร้าง/จัดการบัญชี Admin เอง ไม่ได้ทำเป็น Use Case ในระบบ** (ต่างจาก UC-A05 ที่จัดการบัญชี Parent/User) เพราะสมมติฐานคือทีมงานมีจำนวนน้อย จึงตั้งค่าบัญชี Admin ผ่านระดับ Infrastructure/Database โดยตรงแทนการทำ UI จัดการเอง — Exception ที่พูดถึง "Admin สองคน" (เช่น UC-A01 E1, UC-A06 E3) จึงหมายถึง Admin ที่ถูกสร้างไว้ล่วงหน้าแล้ว ไม่ใช่ระบบเปิดให้สมัครเอง ถ้าโปรเจกต์ขยายทีมในอนาคตค่อยเพิ่มเป็น Use Case ใหม่ทีหลังได้
- **ฟอรัมยังไม่มีการแจ้งเตือนเมื่อมีคนตอบกระทู้ — เป็นการตัดสินใจ ไม่ใช่การมองข้าม** เพราะฟีเจอร์แจ้งเตือนทั้งหมดถูกตัดออกจากเฟสนี้แล้ว (ดู bullet ถัดไปเรื่อง Notification/Saved Search) ผู้ใช้ต้องกลับเข้ามาดูกระทู้เอง ถ้าจะเพิ่มในอนาคตให้ต่อกับ `notification-sender` ของ Ops Service ที่มีอยู่แล้วผ่าน Database Webhook เหมือน UC-U07 ไม่ต้องรื้อของเดิม
- **ฟอรัม (UC-G08/UC-U09/UC-A12) ใช้ Post-Moderation ไม่ใช่ Pre-Moderation** — เลือกแบบนี้เพราะทีมมี Admin คนเดียว ถ้าบังคับให้ทุกกระทู้รอตรวจก่อน ฟอรัมจะตายตั้งแต่วันแรกและกลายเป็นภาระ Admin ที่ไม่จำเป็น ในขณะที่รีวิว (UC-U06) ยังคง Pre-Moderation ไว้เพราะกระทบคะแนนเฉลี่ยที่แสดงในผลค้นหาโดยตรง
- **AI Chatbot (UC-U05) ถูก gate ไว้หลัง Login เสมอ** และตอนนี้ครอบคลุมทั้งการตอบคำถามและการแนะนำโรงเรียนแบบจัดอันดับในที่เดียว ลดจำนวนหน้า/endpoint ที่ต้องสร้างลงจากเดิม
- **ทุก UI ในเอกสารนี้ต้องเป็น Responsive** (ตอบข้อ 5.1/8.2 ของแบบฟอร์ม คง.101) โดยเฉพาะ UC-G01 (ค้นหา/กรอง), UC-G03 (แผนที่), UC-U03 (ตารางเปรียบเทียบ) ที่มี layout ซับซ้อนบนจอเล็ก — รายละเอียดแนวทาง Tailwind CSS + breakpoint ดู System Architecture หัวข้อ 9
- **ตัดฟีเจอร์ Notification/Saved Search ออกจากเฟสนี้** *(เดิมเคยใช้เลข UC-U09 — ตั้งแต่ v6.2 เลขนี้ถูกใช้กับ Use Case ฟอรัมแทนแล้ว ไม่ใช่ Use Case เดิมที่ถูกตัด)* — ถ้าอยากทำในอนาคต ตาราง `audit_log`/schema ที่มีอยู่ไม่กระทบ เพิ่มเป็นโมดูลใหม่ทีหลังได้โดยไม่ต้องรื้อของเดิม
- Use Case ที่ทำเครื่องหมาย **Must** คือกลุ่มที่ควรทำให้เสร็จสมบูรณ์ก่อนสำหรับ demo/defend ส่วน **Should/Could** เป็นส่วนเสริมหากเวลาเหลือ
- แนะนำให้แต่ละ Exception Flow ในเอกสารนี้ถูกแปลงเป็น Test Case ของ QA โดยตรง (1 Exception Flow ≈ 1 Integration Test ขั้นต่ำ) — เป็นส่วนหนึ่งของแผนทดสอบเต็มที่ System Architecture หัวข้อ 13 (DevOps & QA Plan) ซึ่งครอบคลุม API/RLS/Security/Load Testing และ UAT เพิ่มเติมจากที่นี่ รวมถึง CI/CD Pipeline และ Centralized Logging/Error Tracking ที่ผูกกับ Correlation ID ในหัวข้อ 8.6 ด้านล่าง

### 7.3 การเก็บวันที่ 3 มิติแยกจากกัน: System Fetch, Source Published, Effective Period

ข้อมูลบางประเภท โดยเฉพาะค่าเทอม/ค่าใช้จ่าย มีมิติเวลาอยู่ **3 ชั้นที่ต้องแยกจากกันชัดเจน** (แก้ไข
จากเดิมที่เคยมี 2 มิติ เพิ่มมิติที่ 2 ด้านล่างเข้ามาใหม่ เพื่อตอบคำถาม "ต้นฉบับข้อมูลนี้เก่าแค่ไหน
กันแน่" ซึ่งมิติเดิม 2 อย่างตอบไม่ได้):

1. **System fetch timestamp** (เมื่อไหร่ที่**ระบบ**ไปดึง/ตรวจสอบข้อมูลนี้มา) — คือ
   `school_versions.created_at` (เปลี่ยนแปลงล่าสุด) และ `schools.last_verified_at` (ตรวจสอบ
   ล่าสุด แม้ไม่เปลี่ยน) — ตอบคำถาม "เราไปเช็คมาเมื่อไหร่"
2. **Source published/updated date** (เมื่อไหร่ที่**ต้นฉบับ** — เว็บไซต์/เอกสารของโรงเรียนเอง —
   ถูกเผยแพร่หรือแก้ไขล่าสุดตามที่ระบุไว้ในหน้านั้น เช่น footer "Last updated: March 2025" หรือ
   PDF metadata) — ตอบคำถาม **"ต้นฉบับเองเก่าแค่ไหน"** ซึ่งเป็นคนละเรื่องกับข้อ 1 โดยสิ้นเชิง:
   ระบบอาจ "เพิ่งไปเช็คเมื่อวานนี้" (system fetch = เมื่อวาน) แต่ตรวจเจอว่าหน้าเว็บของโรงเรียนเอง
   "ไม่เคยถูกแก้ไขมา 2 ปีแล้ว" (source published = 2 ปีก่อน) — สองตัวเลขนี้ต่างกันได้มาก และ
   เป็นสัญญาณคุณภาพข้อมูลที่ผู้ปกครองควรเห็น ไม่ใช่แค่ "ระบบเช็คล่าสุดเมื่อไหร่" อย่างเดียว
   **Nullable เสมอ** เพราะไม่ใช่ทุกหน้าเว็บ/เอกสารจะระบุวันที่แก้ไขไว้ — AI Scraper (UC-A03)
   พยายามสกัดฟิลด์นี้เป็น best-effort เท่านั้น ไม่ error ถ้าหาไม่เจอ
3. **Effective date/period** (ข้อมูลนี้ใช้กับช่วงเวลาไหนในความเป็นจริง) — เช่น ค่าเทอมที่ Scrape
   มาในเดือนสิงหาคม 2568 อาจเป็นอัตราของ**ปีการศึกษา 2567** ที่โรงเรียนยังไม่อัปเดตเว็บ หรือเป็น
   อัตรา**ปีการศึกษา 2568** ที่เพิ่งประกาศใหม่ก็ได้ — ตอบคำถาม "ตัวเลขนี้ใช้กับปีไหน" คนละคำถาม
   กับข้อ 1-2 ทั้งคู่

**แนวทาง:** ฟิลด์ในกลุ่มค่าใช้จ่าย/ค่าเทอมภายใน `data_snapshot` เก็บทั้ง `source_published_at`
(มิติที่ 2) และ `academic_year` (มิติที่ 3) กำกับตัวเองในระดับฟิลด์ ไม่ใช่ระดับเวอร์ชัน เพราะแต่ละ
รายการค่าใช้จ่ายอาจอ้างอิงคนละต้นฉบับ/คนละปีกันได้ในเวอร์ชันเดียว (เช่น ค่าเทอมมาจากหน้าที่เพิ่ง
อัปเดตสัปดาห์นี้ แต่ค่ากิจกรรมมาจากหน้า PDF เก่าที่ไม่ได้แตะมา 1 ปีแล้ว) ตัวอย่างโครงสร้างภายใน
`data_snapshot.tuition`:

```json
{
  "tuition": {
    "amount": 250000,
    "currency": "THB",
    "academic_year": "2568",
    "source_published_at": "2025-03-15",
    "source_type": "scraper",
    "confidence_score": 0.82
  }
}
```

> **Source of truth ระหว่าง JSONB กับตาราง normalize (สำคัญ — เคลียร์ใน v6.3):** ตัวอย่าง JSON
> ข้างบนคือหน้าตาของ `data_snapshot` ซึ่งเป็น **provenance ดิบ** ที่เก็บ payload ตามที่ AI คืนมา
> ทั้งก้อนไว้ตรวจย้อนหลัง/rollback **ห้ามให้ระบบอ่านไปคำนวณหรือกรองโดยตรง** — ค่าที่ระบบใช้จริง
> (แสดงผล, กรองใน UC-G01, คำนวณใน UC-U04) ต้องอ่านจากตาราง **`version_fees`** (หัวข้อ 7.14) และ
> **`version_extra_fees`** (หัวข้อ 7.15) ซึ่ง normalize ออกมาแล้วเป็นคอลัมน์ `numeric` พร้อม
> `academic_year`/`source_published_at` กำกับรายแถว เหตุผลที่ต้องแยก 2 ชั้นแบบนี้: (1) ตัวเลขใน
> JSON เป็น float ปัดเศษพลาดได้ ผิดข้อกำหนด decimal-safe ของ UC-U04 E4 (2) การกรองช่วงค่าเทอม
> ใน JSONB ช้าและเขียน query ยากกว่าคอลัมน์ปกติมาก — ทั้งสองชั้นถูกเขียนพร้อมกันใน transaction
> เดียวตอนบันทึกเวอร์ชัน จึงไม่มีความเสี่ยงว่าจะไม่ตรงกัน

ฝั่ง UI (UC-G02, UC-U04) ต้องแสดง **สูงสุด 3 บรรทัดแยกกัน** ไม่รวมเป็นประโยคเดียวเพราะสื่อความหมายคนละอย่าง: (1) "ค่าเทอมนี้เป็นของปีการศึกษา 2568" (effective period, มิติที่ 3) (2) "ตรวจสอบล่าสุดโดยระบบเมื่อ [system timestamp]" (system fetch, มิติที่ 1) (3) "ต้นฉบับอัปเดตล่าสุดเมื่อ [source_published_at]" (source published, มิติที่ 2) — **บรรทัดที่ 3 แสดงเฉพาะเมื่อ `source_published_at` ไม่ null เท่านั้น** (ซ่อนไปเลยถ้าไม่มี ไม่แสดง "ไม่ทราบ" ให้รก) และเมื่อบรรทัดที่ 3 ปรากฏพร้อมกับวันที่เก่ากว่าบรรทัดที่ 2 มาก (เช่น ต้นฉบับไม่ถูกแตะมา 1 ปีขึ้นไป) ให้ขึ้น badge เตือนสีเหลือง "ต้นฉบับอาจไม่อัปเดต" เพิ่มด้วย เพื่อเตือนผู้ปกครองว่าตัวเลขนี้แม้ระบบเพิ่งเช็คมา แต่ตัวโรงเรียนเองอาจยังไม่ได้แก้ไขมานานแล้ว

## 8. ข้อพิจารณาเชิงลึกสำหรับ Dev จริง (Concurrency & Security)

### 8.1 Authentication & Authorization

**Public-facing:** UC-G01-G05 ไม่ต้อง auth เลย ส่วน UC-U* ทุกตัวตรวจ JWT ผ่าน **Supabase Auth** โดยตรง — **Row Level Security (RLS)** ที่ระดับ table/schema ทำหน้าที่ authorization แทน API Gateway แบบเต็มรูป (ดู System Architecture หัวข้อ 1, 4)

**Anti-IDOR (สำคัญมากเพราะมีข้อมูลบุตรหลานที่เป็น PDPA):** ทุก resource ที่ผูกกับ user_id (children_profiles, favorites, saved comparisons, chat history) **ต้องมี RLS policy บังคับว่า resource นั้นเป็นของ user ที่ login อยู่จริงเสมอ** ไม่พึ่งพาการซ่อน ID ไว้ในหน้า UI — เช่น query `children_profiles` (schema `user_data`) ต้องมี policy ที่ filter ด้วย `user_id = auth.uid()` เสมอที่ระดับ database ไม่ใช่แค่ logic ฝั่ง Frontend มิฉะนั้นคนอื่นที่เดา/เปลี่ยน ID จะเห็นข้อมูลบุตรหลานของคนอื่นได้ผ่าน Auto-API โดยตรง

**ข้อยกเว้นเดียวที่ตั้งใจ — ลิงก์แชร์ผลเปรียบเทียบ (UC-G07/UC-U08):** `comparison_sets` เข้าถึงได้แบบ anonymous ผ่าน `get-shared-comparison` เมื่อมี `share_token` ที่ถูกต้องเท่านั้น — นี่**ไม่ใช่** IDOR เพราะ (1) เป็นการเปิดให้เข้าถึงโดยเจตนาของเจ้าของเอง ไม่ใช่ช่องโหว่ที่เจ้าของไม่รู้ตัว (2) `share_token` สุ่มแบบคาดเดาไม่ได้ ต่างจาก sequential ID ที่ไล่เดาได้ (3) resource ที่ expose ผ่าน token ถูกจำกัดเฉพาะ field ที่จำเป็นต่อการแสดงผลเท่านั้น (`name` ของชุด + รายละเอียดโรงเรียนที่ resolve จาก `school_ids` ผ่าน `school-data-api` แล้ว) **ไม่มี `user_id`/`comparison_id`/`share_token` เองปรากฏออกไปในเลย** — ทำผ่าน Edge Function (`get-shared-comparison`) ที่ใช้ Service Role bypass RLS อย่างตั้งใจและควบคุม field ที่คืนเองในโค้ด ไม่ใช่เปิด RLS policy กว้างๆ ให้ query ตรงผ่าน Auto-API ซึ่งเสี่ยงหลุด column อื่นออกไปด้วยโดยไม่ตั้งใจ

**Service-to-service (Internal):** ระบบแบ่งเป็น 5 Service ตาม schema จริง (School Data, Community, User, AI, Ops — ดู System Architecture หัวข้อ 4) การเรียกข้าม Service (เช่น Chatbot → `school-data-api`, Re-embed handler → `school-data-api`) ต้องผ่าน **Internal Service Secret** (custom header ที่รู้กันเฉพาะฝั่ง Edge Function) ร่วมกับ **forward JWT ของ user ต้นทาง** เพื่อให้ Service ปลายทางยังตรวจสิทธิ์ตาม user จริง ไม่ใช้ Service Role Key ข้ามสิทธิ์เต็มรูปแบบ (รายละเอียดดู System Architecture หัวข้อ 4.4) — เลือกใช้ shared secret แทน mTLS ของจริงเพราะทีมเล็กไม่มี certificate infra แต่ยังพิสูจน์ตัวตนระหว่าง service ได้

**ฟอรัม (UC-G08/UC-U09):** `forum_posts`/`forum_comments` อ่านแบบ anonymous ได้เฉพาะแถวที่ `status = 'approved'` ส่วนการเขียน/แก้/ลบ ต้องมี policy บังคับ `user_id = auth.uid()` เสมอ (เจ้าของแก้ได้เฉพาะของตัวเอง) และ `forum_reports` ต้องไม่เปิดให้ผู้ใช้ทั่วไป select เห็นว่าใครรายงานใคร — อ่านได้เฉพาะ Admin เท่านั้น

**Admin routes:** แยกฝั่ง Frontend เป็นแอปคนละตัว (Admin Dashboard) และบังคับด้วย RLS policy ที่เช็ค role admin จาก JWT claim ที่ระดับ table เสมอ ไม่ใช่แค่ซ่อนปุ่มฝั่ง Frontend

### 8.2 Scraper Concurrency: ป้องกัน Job ซ้อนกันต่อโรงเรียนเดียวกัน

**ปัญหา:** ถ้า Scheduled Job รอบใหม่เริ่มก่อนที่ Job รอบเก่าของโรงเรียนเดียวกันรันเสร็จ (เช่น เว็บโรงเรียนโหลดช้ามาก) จะเกิด 2 Job ทำงานพร้อมกันบนโรงเรียนเดียวกัน เสี่ยงสร้าง Pending Review ซ้ำหรือชน Optimistic Locking โดยไม่จำเป็น

**แนวทาง:** ระบบนี้ไม่มี Redis แยก (ทุก Service ยังอยู่ Postgres instance เดียวกัน ไม่ใช่ all-in-one แบบไม่แยก Service — ดู System Architecture หัวข้อ 4-5) จึงใช้ **Postgres Advisory Lock** แทน Redis `SETNX` — ก่อนเริ่ม Job เรียก `pg_try_advisory_lock(hashtext(school_id))` ถ้าล็อกไม่สำเร็จ (มี Job อื่นถืออยู่) ให้ข้าม Job รอบนี้ไปทำรอบถัดไปแทนการรอ/รันซ้อน ข้อดีคือไม่ต้องตั้ง TTL เองเหมือน Redis เพราะ Advisory Lock ผูกกับ session/connection ของ Postgres โดยตรง — ถ้า Worker ที่ถือ Lock crash กลางทาง connection หลุดแล้ว Postgres ปลด Lock ให้อัตโนมัติทันที ไม่ต้องรอหมดอายุเหมือน TTL — Concurrency ระหว่างคนละโรงเรียนไม่มีปัญหา เพราะคนละ Lock key กัน รันขนานได้เต็มที่ตาม Worker Pool ที่มี

### 8.3 Indirect Prompt Injection ผ่านข้อมูลที่ Scrape มา

ต่างจาก Prompt Injection ที่ผู้ใช้พิมพ์เองใน UC-U05 (E4) — นี่คือกรณีที่**เนื้อหาบนเว็บไซต์โรงเรียนเอง**มีข้อความพยายามสั่งการ LLM (เว็บถูกแฮ็กแล้วแทรกข้อความสั่งการ) เพราะข้อมูลที่ Scrape มาจะถูก inject เข้า Prompt ของ UC-U05 โดยตรงตอนตอบคำถาม/แนะนำโรงเรียน (ผ่านผลลัพธ์ที่ tool call คืนมา) — เป็นช่องโหว่แยกจาก Sanitization กัน XSS ใน UC-A03 (E6) เพราะ HTML sanitizer กรองแค่ script tag ไม่ได้กรองข้อความสั่งการที่เป็น plain text

**แนวทาง:** ข้อมูลที่ Retrieve มาจาก `school-data-api` ของ School Data Service ผ่าน tool call (`search_schools`, `get_school_details`, `compare_schools`) ต้องใส่ใน Prompt ในฐานะ "ข้อมูลอ้างอิง" ที่แยกชั้นจาก System Instruction เสมอ (หลักการเดียวกับที่แยกจาก User Input ใน E4) และผ่าน Output Filter เดียวกันก่อนตอบกลับ — apply กับทุกแหล่งข้อมูลภายนอกที่เข้าสู่ Prompt ไม่ใช่แค่ข้อความจากผู้ใช้

### 8.4 Idempotent Consumers สำหรับ Event-Driven Sync ข้าม Service

Pattern "Database Webhook → Edge Function" ในหัวข้อ 4 เป็น At-least-once Delivery (retry แบบ exponential backoff) หมายความว่า **`re-embed-handler` ของ AI Service มีโอกาสถูกเรียกซ้ำมากกว่า 1 ครั้ง** สำหรับ publish event เดียวกัน (เช่น เรียก `school-data-api` ข้าม Service สำเร็จแต่ตัว handler เอง timeout ก่อนบันทึกผล ระบบจึง retry ทั้ง flow ใหม่) จึงต้องออกแบบให้ Apply ซ้ำได้ผลลัพธ์เหมือนเดิม (Idempotent) เช่น ใช้ `version_id` เป็น Key ในการ **Upsert** ค่า embedding ลง `ai.school_embeddings` แทน Insert ตรงๆ ไม่เช่นนั้นอาจมี embedding ซ้ำหลายแถวสำหรับเวอร์ชันเดียวกัน

### 8.5 Transaction Boundary ตอน Publish

ตอน Approve (UC-A04) หรือ CRUD ตรง (UC-A01) การอัปเดต `schools.current_published_version_id` กับการเปลี่ยน status ของแถวใน `school_versions` เป็น published **ต้องอยู่ใน Database Transaction เดียวกัน** ถ้าแยกเป็น 2 Query โดยไม่มี Transaction ครอบแล้วระบบ crash ระหว่างกลาง อาจเกิดสถานะไม่ตรงกัน (version บอก published แต่ schools ยังชี้เวอร์ชันเก่า หรือกลับกัน)

### 8.6 Observability: Correlation ID

แม้ระบบนี้ไม่ใช่ true Microservices เต็มรูป (ยังอยู่ Postgres instance เดียว — ดู System Architecture หัวข้อ 4.6) แต่ตอนนี้มีการเรียกข้าม **5 Service จริง** ทาง HTTP (Edge Function เรียก Edge Function) เช่น Scraper (School Data Service) → Pending Review → Approve → Database Webhook → `re-embed-handler` (AI Service) → เรียกกลับ `school-data-api` (School Data Service) หรือ Chatbot (AI Service) → `school-data-api` + `user-data-api` (School Data/User Service) หรือ `get-shared-comparison` (User Service) → `school-data-api` (School Data Service) ตอน Guest เปิดลิงก์แชร์ (UC-G07) การ Debug ตอนมีปัญหาจริงจะยากมากถ้าไม่มีทางเชื่อมโยง Log ข้าม Service — ทุก Request/Event ควรพก Correlation ID เดียวกันตั้งแต่ต้นจนจบ Flow ผ่าน header (เช่น `X-Correlation-Id`) ทุกครั้งที่ Edge Function หนึ่งเรียกอีก Edge Function หนึ่ง (รวมถึงตอนถูกเรียกโดย Guest ที่ไม่มี JWT ก็ยังต้องมี Correlation ID เสมอ) แล้วใส่ใน Log ทุก Service (รวม `school_scrape_log`) เพื่อ trace ปัญหาข้าม Service ได้โดยไม่ต้องไล่ Log ทีละ Service แยกกัน
