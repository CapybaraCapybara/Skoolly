เอกสารนี้ไม่ใช่สเปก ถ้าอยากรู้ว่าระบบทำอะไรได้บ้างให้ดู `use_case_specification_final_v6.md`
กับ `system_architecture_explained_v6.md` ที่นี่ตอบแค่ว่า "แล้วจะทำอะไรต่อ ด้วยอะไร เรียงยังไง"

## ลำดับงานแบบย่อ

อ่านแค่ส่วนนี้ก็พอรู้ว่าต้องทำอะไรก่อนหลัง ทำทีละข้อจากบนลงล่าง
รายละเอียดวิธีทำของแต่ละข้ออยู่ในหัวข้อที่วงเล็บไว้

**ช่วงที่ 1 — เริ่มของที่ใช้เวลานานไว้ก่อน**

1. export รูป 3 ไฟล์จาก draw.io กับ Excalidraw ให้เล่มคอมไพล์ได้ (หัวข้อ 3)
2. แก้ scraper ให้เขียนผลลง `school_scrape_log` (หัวข้อ 4.1)
3. สั่งรัน scrape 60-80 โรงเรียน แล้วปล่อยรันทิ้งไว้ (หัวข้อ 4.1)
4. ระหว่างรอ กรอกค่าเทอมจริงด้วยมือ 25-30 โรงเรียนเป็นชุดเฉลย (หัวข้อ 4.2)

**ช่วงที่ 2 — ตัดสินใจและวางฐาน**

5. ตัดสินใจสองเรื่อง คือจะทำแท็บรีวิว Google หรือตัดออก และงานไหนอยู่ FastAPI งานไหนอยู่ Edge Function (หัวข้อ 4.3, 5.1)
6. เขียน RLS policy พร้อมเทสต์ pgTAP (หัวข้อ 5.4, 8.1)
7. เปลี่ยน `school_id` ในโค้ดหน้าเว็บจาก number เป็น UUID (หัวข้อ 5.3)
8. สร้างไฟล์ชนิดข้อมูลจากสกีมาจริง (หัวข้อ 5.2)

**ช่วงที่ 3 — ต่อระบบเข้าฐานข้อมูลจริง**

9. เขียน query กลางสามตัว คือค้นหา ดูรายละเอียด และเปรียบเทียบ (หัวข้อ 6.2)
10. ต่อหน้าค้นหากับหน้ารายละเอียดเข้าฐานข้อมูลจริง (หัวข้อ 6.3 ข้อ 1-2)
11. ทำแชทบอท โดยใช้ query จากข้อ 9 เป็น tool (หัวข้อ 7)
12. ทำระบบล็อกอิน แล้วต่อฟอรัม รายการโปรด เปรียบเทียบ และเครื่องคำนวณ (หัวข้อ 6.3 ข้อ 3-5, 6.4)

**ช่วงที่ 4 — วัดผลและเขียนเล่ม**

13. เทียบผล scrape กับชุดเฉลย แล้วเขียนผลความแม่นยำในบทที่ 4 (หัวข้อ 4.2, 8.2)
14. ทดสอบเส้นทางหลัก เก็บภาพหน้าจอ เขียนบทที่ 4 ส่วนที่เหลือ แล้วเขียนบทที่ 5 (หัวข้อ 8)

ข้อ 13 ไม่จำเป็นต้องรอถึงตรงนั้น ถ้า scrape จากข้อ 3 เสร็จเมื่อไหร่ก็ทำได้เลย

## 2. หลักการจัดลำดับที่ใช้ในเอกสารนี้

ตารางแผนการดำเนินการในบทที่ 1 เป็นกรอบคร่าว ๆ ที่เขียนไว้ตอนต้นภาค ไม่ได้ยึดเป๊ะ
ลำดับข้างล่างจึงเรียงตามเหตุผลทางเทคนิคล้วน ๆ ด้วยเกณฑ์สามข้อ เรียงตามน้ำหนัก

1. **งานที่กินเวลานอกเหนือจากเวลานั่งเขียนโค้ด ให้เริ่มก่อน** — การรัน scraper 60-80 โรงเรียน
   กับการกรอกชุดเฉลยด้วยมือ ใช้เวลาเดินของมันเองที่เร่งไม่ได้ ปล่อยให้รันอยู่เบื้องหลัง
   แล้วไปทำอย่างอื่นคู่ขนานได้ ถ้าเก็บไว้ทำท้าย ๆ จะกลายเป็นคอขวดที่กั้นบทที่ 4 ทั้งบท
2. **งานที่ถูกงานอื่นพึ่งพาหลายทาง ให้ทำก่อนงานที่พึ่งพามัน** — เปลี่ยนชนิด id, เขียน RLS,
   สร้างชนิดข้อมูลจากสกีมา สามอย่างนี้ถ้าทำทีหลังจะต้องรื้อของที่เขียนไปแล้ว
3. **ความเสี่ยงที่ยังไม่รู้ ให้ชนก่อนความเสี่ยงที่รู้อยู่แล้ว** — แชทบอทยังไม่มีอะไรเลยสักบรรทัด
   จึงไม่มีใครรู้ว่ามันจะติดตรงไหน ต้องเริ่มเร็วกว่างานที่ประเมินเวลาได้แม่นอย่างการต่อหน้าเว็บ

ผลที่ได้คือลำดับที่ต่างจากสัญชาตญาณอยู่สองจุด คือ **การรันระยะที่ 3 ขึ้นมาก่อนงานเขียนโค้ดทั้งหมด**
และ **แชทบอทขยับขึ้นมาคู่ขนานกับการต่อหน้าเว็บ** ไม่ใช่ตามหลัง

## 3. กลุ่มที่ 1 — งานครึ่งวันที่ปลดบล็อกได้ทันที

ทำก่อนเพราะถูกมากเมื่อเทียบกับสิ่งที่ปลดล็อก ตอนนี้เล่มยังคอมไพล์ออกมาไม่ถูกต้องเพราะเรื่องนี้อย่างเดียว

2. เปิด `report/images/user-flow.drawio` แล้ว export เป็น `user-flow.png` — ยังไม่เคยมีไฟล์นี้เลย
   `chapter3.tex` เรียกใช้อยู่แต่หาไม่เจอ
3. เปิด `report/images/system-architecture.excalidraw` แล้ว export ทับ `system-architecture.png`
   (ไฟล์ที่มีอยู่เก่ากว่าตอนแก้สามจุดเรื่องกล่อง Supabase กับลูกศรสองหัว)

## 4. กลุ่มที่ 2 — เริ่มงานที่กินเวลานานที่สุดให้เดินก่อน

งานชุดนี้ควรเริ่มวันเดียวกับกลุ่มที่ 1 เพราะมันรันอยู่เบื้องหลังได้ ไม่ต้องนั่งเฝ้า
และเป็นสิ่งเดียวที่กั้นบทที่ 4 ทั้งบทอยู่ ตอนนี้มีข้อมูลค่าเทอม 15 แถวจาก 290 โรงเรียน
ซึ่งน้อยเกินกว่าจะสรุปอะไรได้

### 4.1 รันระยะที่ 3 เป็นล็อต

ใช้ `microservices/batch_scrape_runner.py` ที่เขียนไว้แล้ว รันโดยคุม concurrency
ไม่ต้องรันครบ 290 แห่ง เป้าหมายคือให้มีกลุ่มตัวอย่างที่อ้างอิงได้ในเล่ม

- ตั้งเป้าอย่างน้อย 60-80 โรงเรียน สุ่มแบบกระจายจังหวัดและขนาด ไม่ใช่เอาแต่โรงเรียนใหญ่ในกรุงเทพ
  เพราะถ้าเลือกแต่เว็บที่ทำมาดี ตัวเลขความแม่นยำจะสวยเกินจริงและตอบคำถามกรรมการไม่ได้
- **ก่อนเริ่มรันจริง ต้องให้ scraper เขียนลง `school_data.school_scrape_log` ก่อน** ตอนนี้ยังว่าง 0 แถว
  ตารางนี้คือที่เดียวที่เก็บ reasoning กับ confidence ของ AI ถ้ารันไปโดยไม่เขียน log
  จะต้องรันใหม่ทั้งหมดตอนจะวัดผล ซึ่งเสียเวลาซ้ำสองเท่า
- เก็บ `scraped_page_url` ทุกแถวไว้ด้วย เวลาต้องเปิดตรวจย้อนว่าตัวเลขมาจากหน้าไหนจะทำได้ทันที

### 4.2 สร้างชุดเฉลยไว้วัดความแม่นยำ

ทำคู่ขนานไปกับข้อ 4.1 ได้ ไม่ต้องรอ scrape เสร็จ เพราะเป็นการเปิดเว็บจริงกรอกด้วยมือ
เลือกมา 25-30 โรงเรียน (เลือกจากรายชื่อที่จะ scrape ไว้ล่วงหน้า)

- ไฟล์เฉลย `data/ground_truth_fees.json` (คู่ `opec_school_code` กับค่าที่กรอกเอง)
- สคริปต์เทียบ `microservices/eval_extraction.py` รายงานสามตัวเลข คือ
  สกัดเจอกี่ฟิลด์ ถูกกี่ฟิลด์ และ confidence ที่ AI ให้สัมพันธ์กับความถูกจริงแค่ไหน
- ตัวสุดท้ายสำคัญที่สุด เพราะ UC-14 ให้ผู้ดูแลระบบตัดสินใจจาก confidence
  ถ้าเลขนั้นเชื่อไม่ได้ กระบวนการอนุมัติทั้งอันก็ไม่มีความหมาย

### 4.3 ตัดสินใจเรื่องรีวิวจาก Google

`google_place_id` ตอนนี้ว่างทั้ง 290 แถว แปลว่าแท็บรีวิวใน UC-02 ยังใช้งานไม่ได้เลยสักโรงเรียน
ตัดสินใจตอนนี้เลยเพราะมันเปลี่ยนขอบเขตของงานหน้าเว็บในกลุ่มที่ 4

- ทำต่อ: เขียนสคริปต์จับคู่โรงเรียนกับ Place ID ด้วย Places API แบบ Text Search
  ใช้ชื่อภาษาอังกฤษ + จังหวัด แล้วให้ผู้ดูแลระบบยืนยันเหมือนที่ทำกับ URL เว็บไซต์
- เลื่อนออก: ปรับ UC-02 ให้ระบุว่าแท็บรีวิวเป็นส่วนขยายที่ยังไม่เปิดใช้ในเฟสนี้
  แบบเดียวกับที่ทำกับ RAG ในหัวข้อ 3.4 แล้วตัดออกจากขอบเขต demo

ถ้าเวลาไม่พอ ทางที่สองไม่เสียหาย เพราะเอกสารมีแบบแผนการเขียน "ออกแบบไว้แต่ยังไม่เปิด" อยู่แล้ว

## 5. กลุ่มที่ 3 — วางรากฐานที่งานอื่นพึ่งพา

สามอย่างในกลุ่มนี้ถ้าทำทีหลังจะต้องรื้อของที่เขียนไปแล้ว จึงต้องเสร็จก่อนแตะโค้ดหน้าเว็บสักบรรทัด

### 5.1 ตัดสินใจเส้นแบ่ง FastAPI กับ Edge Function

เอกสารสถาปัตยกรรมบอกว่าระบบผู้ดูแลระบบเรียก Supabase Auto-API ตรง แต่โค้ดจริงเรียก FastAPI
ใน `microservices/opec_service.py` ซึ่งมี endpoint อยู่กว่า 25 เส้นและใช้งานได้จริงอยู่แล้ว
สองอย่างนี้ไม่ได้ขัดกันเสียทีเดียว เพราะ FastAPI ตัวนั้นคือหน้าควบคุมของ Data Pipeline
ซึ่งเอกสารก็นับเป็นส่วนหนึ่งของ School Data Service อยู่แล้ว แต่ต้องเขียนให้ชัดว่าเส้นแบ่งอยู่ตรงไหน

ข้อเสนอคือแบ่งแบบนี้ แล้วเขียนกลับเข้า `system_architecture_explained_v6.md` หัวข้อ 4

- งานที่ต้องสั่งรัน Python (ดึง สช., หา URL, เติมพิกัด, สั่ง scrape) → อยู่ที่ FastAPI ต่อไป
  เพราะย้ายไป Edge Function ไม่ได้อยู่แล้ว Deno รัน Playwright กับ pdfplumber ไม่ได้
- งานอ่าน/เขียนข้อมูลธรรมดาที่เว็บสาธารณะใช้ → Supabase Auto-API + RLS ตามที่ออกแบบไว้
- งานที่ต้องข้าม Service หรือมีความลับ (แชทบอท, PDF, ลิงก์แชร์) → Edge Function ตามที่ออกแบบไว้

### 5.2 สร้างชนิดข้อมูลและสัญญา API จากสกีมาจริง

ตอนนี้เอกสารบอกแค่ชื่อฟังก์ชันกับชื่อ tool ยังไม่มี request/response ของจริงสักตัวเดียว
ให้เขียนสัญญาออกมาเป็นไฟล์ที่โค้ดใช้ต่อได้จริง ไม่ใช่ตารางในเอกสารเฉย ๆ

| ทำอะไร | ใช้อะไร | ไปอยู่ที่ไหน |
|---|---|---|
| ชนิดข้อมูลกลางของทั้งระบบ | สร้างจากสกีมาจริงด้วย `supabase gen types typescript` | `src/types/database.ts` |
| สัญญาของ Edge Function 6 ตัว | เขียน `type` ของ request/response คู่กัน แล้วให้ทั้งสองฝั่ง import ตัวเดียวกัน | `src/types/api.ts` |
| สัญญาของ tool ที่แชทบอทเรียก | JSON Schema ของ `search_schools` / `get_school_details` / `compare_schools` | `src/types/tools.ts` |
| สัญญาของ FastAPI ที่มีอยู่ | FastAPI สร้าง OpenAPI ให้ฟรีอยู่แล้วที่ `/openapi.json` แค่ export เก็บไว้ | `reference/api/opec-service.json` |

ทำก่อนเพราะทั้งงานหน้าเว็บ (กลุ่มที่ 4) และงานแชทบอท (กลุ่มที่ 5) import ไฟล์ชุดนี้ทั้งคู่
ถ้าไม่มี สองฝั่งจะเดาชื่อฟิลด์กันเอง แล้วมาเจอกันตอนท้ายว่าไม่ตรง

### 5.3 เปลี่ยน `school_id` จาก number เป็น UUID

โค้ดหน้าเว็บตอนนี้ใช้ `number` (เห็นได้จาก `compareIds: number[]` ใน `App.tsx`
และคีย์ของ `SCHOOL_DETAILS_SEED`) แต่ฐานข้อมูลจริงใช้ UUID ทั้งหมด
ต้องเปลี่ยนให้ทั่วทั้ง `src/types/` `src/api/` `src/pages/` และ `src/components/` ก่อนต่อ Supabase

ข้อดีคือ TypeScript จะชี้จุดที่ต้องแก้ให้เองทั้งหมด เปลี่ยนนิยามในไฟล์ `types` แล้วรัน
`npx tsc --noEmit` ไล่ตาม error ไปทีละจุดจนหมด งานนี้น่าเบื่อแต่ตรงไปตรงมา ทำครั้งเดียวจบ

### 5.4 เขียน RLS policy

ตอนนี้ยังไม่มีสักข้อ ซึ่งแปลว่าวินาทีที่เปิด anon key ให้หน้าเว็บใช้ ข้อมูลทุกคนหลุดทันที
จึงต้องเสร็จก่อนข้อ 6.1 เสมอ อย่างน้อยต้องมีสี่ชุด

- `children_profiles` / `favorites` / `comparison_sets` — `user_id = auth.uid()` ทุก operation
- `forum_posts` / `forum_comments` — อ่าน anonymous ได้เฉพาะ `status = 'approved'`
  เขียน/แก้/ลบ ต้อง `user_id = auth.uid()`
- `forum_reports` — ห้าม select จากผู้ใช้ทั่วไปเด็ดขาด เห็นได้เฉพาะ admin
- ทุกตารางใน `school_data` — อ่านได้ทุกคน เขียนได้เฉพาะ service role กับ admin

เขียนลง `db/policies.sql` แยกไฟล์จาก `schema.sql` เพื่อให้แก้ policy ได้โดยไม่ต้องรัน schema ใหม่ทั้งก้อน

## 6. กลุ่มที่ 4 — ชั้นอ่านข้อมูลจริง (ใช้ร่วมกันทั้งหน้าเว็บและแชทบอท)

จุดที่ประหยัดเวลาได้มากที่สุดของแผนนี้ คือหน้าค้นหาใน UC-01 กับ tool `search_schools`
ของแชทบอท เป็น query ตัวเดียวกัน ต่างกันแค่ใครเรียก เช่นเดียวกับหน้ารายละเอียด UC-02
กับ `get_school_details` จึงควรเขียนชั้นนี้ครั้งเดียวแล้วแตกไปใช้สองทาง ไม่ใช่เขียนสองรอบ

### 6.1 เตรียมของก่อน

`.env` ตอนนี้มีแค่ `DATABASE_URL` ซึ่งเป็นสายตรงเข้า Postgres ใช้กับฝั่งเบราว์เซอร์ไม่ได้
ต้องเพิ่มสองค่าจากหน้า Project Settings ของ Supabase

```
VITE_SUPABASE_URL=https://<ref>.supabase.co
VITE_SUPABASE_ANON_KEY=<anon key>
```

แล้วติดตั้งของที่ยังไม่มีใน `package.json`

```bash
npm i @supabase/supabase-js swr
```

`swr` จำเป็นเพราะเอกสารอ้าง stale-while-revalidate เป็นทางแก้ของ UC-01 E1 และ UC-02 E3
ถ้าไม่มีจริง Exception พวกนั้นจะไม่มีอะไรรองรับ

### 6.2 เขียน query กลางสามตัว

เขียนเป็นฟังก์ชัน TypeScript ธรรมดาใน `src/api/` ก่อน ยังไม่ต้องเป็น Edge Function

- `searchSchools(filters)` — ใช้ `pub_tuition_min_thb` กับ `curriculums && ARRAY[...]`
  ที่มี index รออยู่แล้ว เป็นตัวที่พิสูจน์ว่าการต่อฐานข้อมูลใช้ได้จริง
- `getSchoolDetails(id)` — ต้องอ่าน `version_fees`/`version_extra_fees`/`version_safety`
  ผ่าน `current_published_version_id` เป็นจุดที่โครงสร้าง versioning จะถูกทดสอบจริงครั้งแรก
- `compareSchools(ids)` — เรียก `getSchoolDetails` หลายตัวแล้วจัดรูปเป็นตาราง

ทดสอบด้วยการเรียกตรงจนมั่นใจว่าคืนค่าถูกก่อน แล้วค่อยเอาไปเสียบทั้งหน้าเว็บและแชทบอท

### 6.3 สลับหน้าเว็บทีละหน้า

`src/api/schoolsApi.ts` และ `forumApi.ts` เป็นรอยต่อที่เตรียมไว้อยู่แล้ว หน้าจอเรียกผ่านสองไฟล์นี้
ไม่ได้ import ข้อมูลจำลองตรง ๆ จึงเปลี่ยนไส้ในได้โดยไม่ต้องแตะหน้าจอมากนัก
ทำทีละหน้าและทดสอบให้ผ่านก่อนไปหน้าถัดไป อย่าเปลี่ยนรวดเดียวทั้งหมด

1. หน้าค้นหา (UC-01) — เสียบ `searchSchools` ที่เขียนไว้แล้ว อ่านอย่างเดียว ความเสี่ยงต่ำสุด
2. หน้ารายละเอียด (UC-02) — เสียบ `getSchoolDetails`
3. เครื่องคำนวณ (UC-07) — คำนวณฝั่งหน้าเว็บได้ แต่ตัวเลขต้องมาจากฐานข้อมูล
4. ฟอรัม (UC-05) — เป็นหน้าแรกที่ต้องเขียนลงฐานข้อมูล จึงต้องมี Auth ก่อน
5. รายการโปรดและเปรียบเทียบ (UC-03, UC-06) — ต้องมี Auth และ RLS ครบแล้วเช่นกัน

### 6.4 Auth

ใช้ Supabase Auth ตรง ๆ ไม่ต้องเขียน backend เอง สมัคร/ล็อกอิน/ยืนยันอีเมลมีให้ครบ
แถวใน `user_accounts` ถูกสร้างอัตโนมัติด้วย trigger `on_auth_user_created` อยู่แล้ว ไม่ต้องเขียนโค้ดเพิ่ม
งานที่เหลือคือหน้าจอล็อกอินกับการส่ง session ไปกับทุก query ซึ่ง client ของ Supabase ทำให้เอง

## 7. กลุ่มที่ 5 — แชทบอท (UC-08)

เริ่มทันทีที่ข้อ 6.2 เสร็จ ไม่ต้องรอหน้าเว็บทำครบทุกหน้า เพราะสิ่งที่แชทบอทต้องใช้คือ query สามตัว
กับสัญญา tool ใน `src/types/tools.ts` เท่านั้น ทำคู่ขนานกับข้อ 6.3 ได้เต็มที่

เหตุผลที่ต้องเริ่มเร็วทั้งที่งานหน้าเว็บยังไม่เสร็จ คือตอนนี้ยังไม่มีโค้ดสักบรรทัด
จึงไม่มีใครรู้ว่ามันจะติดตรงไหน ต่างจากการต่อหน้าเว็บที่ประเมินเวลาได้ค่อนข้างแม่น
และมันเป็น Must ตัวเดียวที่ยังไม่ได้เริ่ม ทั้งที่เป็นจุดขายหลักของหัวข้อโครงงาน

ข้อดีคือเอกสารตัดสินใจไปแล้วว่าไม่ใช้ vector search ใช้ function calling บนข้อมูล structured แทน
จึงไม่ต้องรอ embedding อะไรทั้งนั้น ทำได้เลย

1. ต่อ LLM ด้วย tool calling โดยส่งสาม query จากข้อ 6.2 เป็น tool
   ใช้ Claude หรือ Gemini ก็ได้ ทั้งคู่รองรับ structured output ที่ต้องแยก `answer`
   กับ `suggested_replies` ตาม UC-08 ข้อ 6
2. ทำ Guided Prompts เป็นชุดปุ่มที่ผูกกับ intent ตายตัวตาม UC-08 ข้อ 2
   ข้อนี้สำคัญเพราะ Business Rule ข้อ 2 ห้ามมีปุ่มที่กดแล้วไม่มีข้อมูลตอบ
   จึงต้องเช็คก่อนแสดงปุ่มว่าข้อมูลกลุ่มนั้นมีจริงในฐานข้อมูล
   ซึ่งตอนนี้สำคัญเป็นพิเศษเพราะข้อมูลค่าเทอมยังไม่ครบทุกโรงเรียน
3. ทำหน้าจอแชท เพิ่มเข้าไปในเว็บสาธารณะ (ไม่ใช่แอปแยก ตามรายงานหัวข้อ 3.7)
4. ย้ายไปเป็น Edge Function `chatbot-api` เพื่อไม่ให้คีย์ LLM หลุดไปอยู่ฝั่งเบราว์เซอร์
   ขั้นนี้ห้ามข้าม ถ้าเรียก LLM จากหน้าเว็บตรง ๆ คีย์จะอยู่ในโค้ดที่ใครก็เปิดดูได้

ใส่ rate limiter ตั้งแต่วันแรกที่ต่อ LLM ได้ ไม่ใช่ทำทีหลัง เพราะ UC-08 E8 กับ UC-19
พูดถึงต้นทุน LLM ไว้ทั้งคู่ และค่าใช้จ่ายบานเป็นเรื่องที่แก้ย้อนหลังไม่ได้

## 8. กลุ่มที่ 6 — ทดสอบและเขียนเล่ม

### 8.1 ชุดทดสอบขั้นต่ำ

เอกสารหัวข้อ 13 ของ System Architecture วางแผนทดสอบไว้ 6 ประเภท ซึ่งเกินกำลังถ้าจะทำครบ
เลือกสองอันที่คุ้มที่สุดก่อน

- **RLS policy test ด้วย pgTAP** — คุ้มที่สุดเพราะถ้า policy ผิด ข้อมูลบุตรหลานหลุด
  ซึ่งเป็นความเสี่ยง PDPA ที่พูดถึงไว้หลายจุดในเอกสาร เขียนเป็นเคสตรง ๆ ว่า
  "ผู้ใช้ ก ต้อง query `children_profiles` ของผู้ใช้ ข ไม่ได้" แล้วรันทุกครั้งที่แก้ policy
  ทำทันทีหลังข้อ 5.4 เสร็จ ไม่ต้องรอถึงกลุ่มนี้
- **Integration test ตาม Exception Flow** — เอกสารมี 123 Exception Flow ซึ่งเป็น test matrix สำเร็จรูป
  ไม่ต้องทำครบ เลือกเฉพาะของ UC-01 UC-02 UC-08 ก่อน เพราะเป็นเส้นทางที่ demo จริง

ตอนนี้ repo ยังไม่มี test runner เลย ต้องเพิ่ม vitest ก่อน (`npm i -D vitest`)
ส่วน pgTAP ติดตั้งผ่าน `create extension pgtap` บน Supabase local ที่รันด้วย Docker

### 8.2 บทที่ 4

เขียนได้เมื่อกลุ่มที่ 2 ให้ผลออกมา ไม่ต้องรอให้โค้ดเสร็จหมด เนื้อหาที่ควรมีตาม TODO ที่เขียนไว้เอง

- ผลการวัดความแม่นยำของการสกัดด้วย AI — มาจากข้อ 4.2 ตรง ๆ เขียนได้ก่อนเพื่อนเลย
- หน้าจอระบบที่พัฒนาได้ — ใส่ภาพหน้าจอจริง ไม่ใช่ mockup รอกลุ่มที่ 4-5
- ผลการทดสอบอัตโนมัติ — มาจากข้อ 8.1
- ผลการทดสอบ UAT — ถ้าเวลาไม่พอ ทำแบบย่อกับผู้ปกครอง 5 คนก็ยังดีกว่าไม่มี

ข้อควรระวังเรื่อง PDPA ถ้าทำ UAT จริง จะเกิดข้อมูลบุตรหลานของคนจริงในฐานข้อมูล
ซึ่งเป็นเงื่อนไขที่เอกสารหัวข้อ 13.2 ระบุไว้เองว่าต้องแยก Supabase project เป็นสองตัวก่อน

### 8.3 บทที่ 5

เขียนท้ายสุด สรุปตามวัตถุประสงค์สามข้อในบทที่ 1 แล้วพูดข้อจำกัดตรง ๆ
ข้อจำกัดที่มีอยู่จริงและควรเขียนไว้ ไม่ต้องกลัวว่าจะดูไม่ดี

- RAG ออกแบบไว้แต่ยังไม่เปิดใช้ เพราะข้อมูลที่เก็บได้เป็น structured ล้วน
- Phase 3 อ่านเว็บที่แสดง PDF เป็นภาพไม่ได้ และเข้าเว็บที่มี Cloudflare ไม่ได้
- ไม่ได้เป็น True Microservices เต็มรูป ด้วยเหตุผลที่อธิบายไว้ในหัวข้อ 4.6
